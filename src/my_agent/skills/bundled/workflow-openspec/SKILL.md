# OpenSpec 变更驱动 / Change-driven development

这是本 Harness 的方法适配，具体来源及差异见 `SOURCE.md`。读取请求中的任务流程快照及本会话阶段，执行当前授权工作；只加载与当前阶段有关的产物。不要在每轮重新建立目录或整套规范。

## 一次变更使用一份事实源

先查看项目已有约定。已有 OpenSpec 项目沿用 `openspec/changes/<change>/` 和 `openspec/specs/`；没有既定位置时，可在用户授权写计划或实现的范围内采用上述目录。阶段处于只读讨论或 Plan 模式不允许写文件时，在回答里给出建议，工具权限不因加载方法变化。选择模板本身不会创建文件。

记住实际变更目录，下一会话从任务记录和该目录接续。任务清单以其中的 `tasks.md` 为准，本地 WorkItem 引用该文件与条目，不另写第二套独立清单。产物按需要生成；没有某份文档不构成停止实现的理由。

## 按当前阶段推进

- 探索 / 提案：核对现有行为，说明改变的原因、范围、影响及未知项；相关结论已确认时直接复用。
- 规范与设计：描述 ADDED / MODIFIED / REMOVED 的需求以及 WHEN / THEN 场景。MODIFIED 保留修改后完整需求，避免归档丢失旧场景；技术选择及权衡另写设计，简单变更不强制 design.md。
- 任务 / 实施：将行为变化对应到代码与最小验证，完成真实工作后更新同一清单。范围变化先同步相关规范，避免代码和文档表达不同目标。
- 核对：检查实现与场景是否一致，分别报告通过、失败、未验证；只有本次授权包含修复才继续修复。
- 归档：在用户要求收尾时读取当前长期规范，合并确认的增量，保留其他变更，再把本次变更移入历史目录。目标已存在时报告并保留两份内容，不覆盖历史。未授权归档时只给出待办。归档不等于 Git 提交或推送。

需要产物示例时读取 `references/artifacts.md`。工具参数使用宿主真实 schema；没有 OpenSpec CLI 时直接处理文档，不把 `/opsx:*` 当成本应用已实现的命令。普通模式完成当前请求后返回，Goal 按原授权继续；流程阶段不会自行赋予审批或自动创建会话的权限。
