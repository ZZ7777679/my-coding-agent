# 定位原因 / Diagnose the cause

从可观察事实缩小问题，而不是连续叠加猜测性修改。方法的价值在于减少无效尝试，不在于把每个小问题扩成一套流程。使用用户当前语言。

本应用适配版，来源和修改说明见 `SOURCE.md`。

## 描述真正发生了什么

核对预期行为、实际行为、触发输入、执行环境、首次出现时机与最近相关改动。阅读完整的相关错误，不把 UI 状态文字或模型自述直接当成根因。记录已知事实与推测的区别。

能用已有日志或一次简单重现解释的问题，直接处理；不要求先写自动化用例才能分析或修复。难以重现时说明条件和证据缺口，选择能区分原因的观察。

## 沿数据流找偏差发生的位置

从失败点追向它的输入：值从哪里产生，经过哪些转换，哪一步开始与预期不同。对比同一路径中正常工作的例子、最近差异和实际依赖版本。

跨组件问题只在有疑点的边界记录必要信息，例如请求何时开始、何时有响应头、何时收到正文、UI 何时渲染。不要默认给每一层增加相同校验或记录完整环境 / 凭据。

例：回答很慢不等于模型思考慢。将“本地组装 → 发送 / 建连 → 首包 → 首个正文片段 → 界面更新”对齐；若已持续收到正文而界面不更新，应检查缓冲和渲染，而不是直接改 VPN 或加大模型超时。

## 选择最便宜的辨别实验

写明“怀疑 X，因为观察到 Y；如果是 X，检查 Z 应该看到什么”。每次尽量只改变一个影响因素。优先只读检查、现有用例或小范围重现，避免一个补丁同时改网络、提示词和 UI 导致无法判断哪项有效。

实验没有支持假设时更新判断，不把补丁继续堆在上面。不设固定尝试次数门槛；若证据指向共同的架构问题，再讨论那个具体边界，而不是仅因失败几次就重构整个系统。

## 按用户范围处理

仅诊断时输出原因、依据和修复建议；已要求修复时修改造成偏差的最小位置。环境或第三方服务问题应如实指出，不通过修改系统代理、权限或静默更换环境掩盖。

实际工具调用故障按宿主失败语义处理；不通过循环自动重试改变它。可选工具不可用只影响相应诊断，不挡住无关工作。

## 报告结论

说明已确认原因、仍可能的解释、采取的改动和直接验证结果。未复现或未验证就明确写出；可保留后续观察点，但不默认增加常驻监控或多层防御检查。修复完成以原触发条件得到预期结果为依据，而非单看代码看起来合理。
