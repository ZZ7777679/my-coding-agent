# Spec Kit 规范驱动 / Specification-driven development

这是本 Harness 的方法适配，来源与差异见 `SOURCE.md`。按任务提供的当前阶段处理相应工作；切换阶段不等于启动 Goal。已有明确需求与计划可直接实施，不把生成文档当作普通代码任务的硬性前提。

## 项目原则与一次功能

优先读取项目现有 AGENTS.md、方案与相关规范。已有项目原则直接引用；仅在用户要求建立或调整原则时更新对应文档，不制造另一份冲突的全局规则。

一次功能采用同一目录下的 `spec.md`、`plan.md`、`tasks.md`。已有 Spec Kit 项目沿用 `specs/<feature>/`；其他项目优先既有约定，无约定时再建议该目录。先查已有功能目录，避免每轮生成新的编号或分支。产物只在当前任务允许写入时创建；只读阶段在回答中提供内容。

## 分开表达需求与实现

- 需求规范：写用户场景、可观察行为、非目标及验收例子，不提前把技术选型冒充用户需求。
- 澄清：只针对会改变结果的缺失信息询问；用户确认的结论更新到同一规范，没有未决项直接继续。
- 技术计划：结合真实源码、接口和运行环境提出实现路径；需要比较方案时再写研究，不预设新框架。
- 任务：把计划拆成可交付单元并对应规范中的场景。只维护一份 tasks.md，WorkItem 引用条目，避免两套任务清单漂移。
- 实施：按当前授权完成任务并记录真实状态。用户改需求时更新有关规范和计划，而不是静默沿旧目标执行。
- 收敛：核对需求、代码和实际验证是否对应，列出缺口。当前授权包含修复时才进入修复；普通请求返回结果，Goal 在授权内继续。未验证不能标成通过，也不因缺一张报告而阻断实现。

需要示例时读取 `references/artifacts.md`。本应用没有安装 specify CLI、原生扩展或 `/speckit-*` 命令；直接用现有读写、执行和协作工具完成当前阶段。不自动创建分支、工作副本、正式会话或推送，不机械套用上游整套审批与检查。
