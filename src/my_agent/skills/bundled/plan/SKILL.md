# 实施规划 / Implementation planning

让接手者无需重读整场对话，也知道要交付什么、改动在哪里、先后关系和如何确认结果。计划服务于实施，不把每次工具调用拆成一个阶段。使用用户当前语言。

本应用适配版，来源和修改说明见 `SOURCE.md`。

## 先读当前事实

核对用户要求、已有方案、相关源码、当前进度和可复用入口。将已确认约束写清楚；尚不确定的接口、版本或运行方式标为需要核实，不凭空编造文件与命令。已有实现不要重复安排。

## 以可体验结果拆分

每个工作单元交付一个有意义的结果；配置、后端、前端和说明尽量围绕同一功能一起完成。只有成果依赖才决定先后顺序，不因目录层次强行把所有后端和所有前端拆成两大批。

在相关单元内说明：

- 用户会得到的行为，以及这次不处理什么。
- 涉及的真实文件或模块、谁负责保存 / 读取 / 执行。
- 消费哪个已有接口，提供什么结果给后续工作。
- 影响用户的异常或兼容问题，以及最小必要验证方式。

很小的改动可用短段落表达，不强制套完整模板。工期不按固定分钟数拆分，也不机械为每个步骤安排提交或评审。

## 让验证对应目标

复用已有验证入口；只有行为变化或明确缺陷需要时才安排新用例。描述具体触发条件和预期行为，避免“完善校验”“加充分测试”之类无法执行的措辞。正常流程及最有影响的边界足够，不默认全量回归。

例如“选择网站后才加载”：首次进入为空；用户选择后加载该站；离页再返回保留选择。验证这条交互即可，不把整套浏览器、账号和所有聚合网站都变成该修复的验收条件。

## 检查计划是否自洽

需求是否有对应交付？上下游对同一字段 / 状态的含义是否一致？可选依赖缺失是否错误地挡住无关功能？有没有为了尚未出现的问题引入运行时、通用框架或审批步骤？只修正发现的实际问题，不制造额外评审循环。

## 保存与接续

在当前模式允许写计划且已有约定位置时保存文档，否则在回答中提供计划。沿项目已有方案 / 进度目录组织，不强制建立某个上游工具的目录体系。

说明第一项具体工作、真正需要用户决定的取舍和未验证假设。Plan 模式的工具能力按当前模式执行；载入此 Skill 本身不切换模式、创建 Goal、创建工作副本或授权实施。已有明确实施请求可在其允许范围内接续，无需另选执行引擎。
