# 讨论与设计 / Discuss and design

将模糊想法变成双方能理解、能够实施的选择。细节取舍服务于用户要得到的结果；方法的深度随问题变化。使用用户当前语言。

本应用适配版，来源和修改说明见 `SOURCE.md`。

## 先形成共同理解

从用户问题、现有代码和任务资料中确认：给谁用、要完成什么、现在怎样做、希望改善什么、有哪些已确定约束。区分用户已经确认的事实、你提出的建议和仍需验证的假设。

信息已明确时直接概括，不重新采访用户。缺失信息会改变下一步时，提出最有影响的具体问题，说明选项各自的实际结果；能查到的项目事实先查。未知项不影响的工作可以继续。

## 按实际问题选择深度

- 简单问题：直接回答，并给必要依据。
- 局部改动：围绕现有行为说明改在哪里、改变什么、对使用者有什么影响。
- 新能力或架构：梳理用户路径、数据流、模块职责、已有系统可以复用什么；对关键取舍比较可行方案。
- 可行性探索：明确待验证的假设和最省事的辨别方式；探测产物与准备长期保留的实现分别说明。

这些是组织讨论的方法，不是必须依次完成的审批阶段。

## 比较能真正落地的方案

选有实质区别的方案，比较其用户体验、实现成本、已有依赖、维护复杂度和调整余地；先说明推荐哪种以及理由。不为凑选项描述一个明显不可用的方案。

检查边界：谁负责保存状态，何时刷新，哪一层负责实际失败，已有能力能否直接复用。删除只为假设中的未来准备的框架。模块边界应让调用者理解“做什么、怎么用、依赖什么”，而不必读完内部实现。

## 收敛为可接续的结论

复杂讨论可按需要保留：目标和范围、主要用户流程、核心选择及理由、未决问题、下一项具体行动。引用已有文档，不复制整个历史。需要用户决定的内容明确提出；已确定选择直接沿用。

例如“导入 Skill”讨论应先确定用户想浏览网站还是输入仓库，再明确安装目的地、同名处理与如何使用；不能只讨论搜索 API，却漏掉用户实际要操作的网页。

当前模式与用户请求决定是否实施。只要求讨论时交付结论；已要求讨论后实现且关键选择已明确时，按现有授权继续，不增加一轮形式确认。
