# 代码审查 / Review code against intent and quality

分别判断“做的是不是用户要的”和“实现能否可靠工作”。两者不能互相替代：符合规范的代码可能做错需求，功能做对也可能留下明确回归。使用用户当前语言。

本应用适配版，来源和修改说明见 `SOURCE.md`。

## 界定审查对象

采用用户指定的提交基线、文件或修改记录；有 Git 时读取对应差异，无 Git 时使用保存的变更和当前文件。保留当前未提交改动，不为了获得干净状态执行重置或创建副本。

查看与差异直接相关的调用方、数据定义、提示词和文档；不无理由扩成全仓审计。基线无法解析时说明并取得明确范围。没有书面规格时按用户要求与已确认任务目标审查，缺少规格不阻止代码质量判断。

## 角度一：需求与使用结果

- 用户要求是否完整覆盖，是否有只有接口或后端而缺少实际入口的功能？
- 真实行为是否与提示词、注释、界面状态及说明一致？
- 是否额外改变用户未要求的工作方式，例如自动创建会话、提交代码或修复 Review 发现的问题？
- 旧任务、旧数据和既有使用方式是否仍可用？发生失败时用户能否理解实际状态？

## 角度二：正确性与结构

从具体触发条件检查数据流、状态刷新、取消 / 清理、并发归属和错误处理。检查不可配置的本机路径、把默认值当唯一合法值、可选依赖成为启动门槛等实际阻断。

结构上留意：同一规则散落多处、一次业务变化需要修改过多模块、只为未来准备的抽象、仅做转发的中间层、名称无法表达含义、对象职责与依赖不匹配。它们是启发式线索，不是必须重构的判定。项目现有约定与这次需求优先，不强行套用多态、依赖注入或“消除每个重复”。

校验应由负责该边界的层完成；报告具体遗漏或重复造成的影响，不以泛泛的“安全性”要求每层再审查一次。已有工具能发现的纯格式问题不挤占评审重点。

## 给出可行动发现

每个发现写明位置、触发条件、用户影响和最小修正方向；用实际代码或需求支撑。区分确认的缺陷、待验证假设和可选改进。按实际影响排序，可以标记属于“需求”或“工程质量”，不要求固定数量。

例如：“切换到项目 B 后，项目 A 的迟到响应覆盖列表，导致显示错误项目的 Skill；应将返回值与请求时的项目身份关联。”比“注意异步安全”更有用。

默认在本会话完成审查；已安排独立角色时可按既有协作方式返回结果。不要自动创建正式会话或强制派生两个子 agent。Review 本身不授权修改代码；检查范围保持最小。没有发现时直接说明，并列出真正未验证的部分，不将“没发现问题”说成完整验收通过。
