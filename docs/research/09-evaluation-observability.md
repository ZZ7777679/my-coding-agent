# 评测与可观测性：怎样知道 Agent 真的完成了工作

> 调研截止与访问日期：2026-09-16。本篇分析公开基准、实验设计、轨迹观测和实际生产收益；没有在本机运行这些基准。关联：[Harness](06-harness.md)、[自进化与 RSI](03-self-evolution.md)、[执行安全与恢复](10-security-recovery.md)。

## 1. 从一个容易误判的成功开始

假设 Agent 接到“修复取消导出后仍有后台写入”的任务。它改了一个函数，运行现有测试，得到绿色结果，最后说“已修复”。此时至少有四个不同问题：修改是否符合预期、测试是否覆盖取消后的子进程、这次运行是否留下了后台任务、用户是否减少了后续排错时间。一个通过率无法同时回答它们。

评测负责按照预先定义的标准判断结果；可观测性负责把运行中的事实保存下来，使我们能解释结果。缺少评测，轨迹再漂亮也不能证明有用；缺少轨迹，分数下降时又不知道应该改模型、检索、工具还是运行环境。

本文沿一个自拟的取消任务解释设计，再比较公开项目。教学场景与建议不是本项目已经完成的实验，也不是对第三方产品的复现结果。

## 2. 先明确正在评测哪一个对象

| 对象 | 问题 | 必须尽量固定什么 |
| --- | --- | --- |
| 模型 | 同样上下文和动作接口，哪个模型更能解决问题 | Harness、提示、工具、任务集、资源与尝试预算 |
| Harness | 同一模型换运行系统是否更可靠 | 模型版本、任务、预算；说明改变了哪些运行能力 |
| 检索 / 记忆 | 提供的信息是否改善最终行为 | 原任务与执行器；记录是否真正取到并使用正确证据 |
| 推理模式 | 规划、搜索、多 Agent 是否值得额外开销 | 总成本、并发资源、候选数量与终止标准 |
| 产品 | 用户能否稳定得到可接受的交付 | 用户任务分布、接管方式、质量要求与后续返工 |

这些对象可以共同评价，但不能混淆归因。给方案 B 更多模型调用、更长时间和更多并行工作区，最后 B 成功率更高，只能证明整个配置更强；不能单独证明其中的规划提示更好。

一个可重复比较的单位至少是：`任务版本 × 初始环境 × 模型版本 × Agent版本 × 配置 × 预算 × 一次尝试`。API 名称相同也可能对应后端更新；无法固定时，应保存执行日期与可见版本标识，并将这一点列为限制。

## 3. 公开基准的发展：从补丁答案到完整执行环境

### 3.1 SWE-bench：真实仓库问题，但仍是有边界的任务

SWE-bench 把真实 GitHub 问题与仓库基线连接起来，让 Agent 产生可以接受测试的修改。它比单函数补全更接近工程工作，因为定位问题、理解已有接口和兼容旧行为都影响结果。官方当前区分 Full、Verified、Lite、Multilingual、Multimodal；默认 Verified 的 Bash Only 视图将模型置于同一 mini-SWE-agent 环境，意在减少 Agent 差异。不能把这一视图与另一个自定义 Harness 排行直接混排。[官方基准与排行榜说明](https://www.swebench.com/)

从工程角度看，任务可形式化为：给定仓库状态 S、问题 I、允许的环境 E，产生修改 Δ，使原有必要行为保持，同时目标失败转为通过。这种定义便于自动验证，却没有完整覆盖“需求本身模糊”“用户中途改变目标”“跨数天维护多个服务”等问题。

因此，适合用它检查 Agent 是否具备基本的仓库修复能力，不宜仅凭分数推出桌面交互、恢复能力或真实团队生产率。测试也只是验收代理：如果需求与测试不一致，Agent 会被错误惩罚，或者通过不符合需求的捷径获得奖励。

官方站点在 2026 年 5 月列出 ProgramBench。本次复查已补读原始论文的方法与任务构建，分析见第 12 节；此前独立站无法读取造成的机制覆盖缺口已经部分解决，未运行基准。[SWE-bench 官方动态](https://www.swebench.com/)、[ProgramBench 论文](https://arxiv.org/html/2605.03546v1)

### 3.2 Terminal-Bench：截至本次检索已经是 4.0

Terminal-Bench 衡量 Agent 在终端环境中完成实际工作的能力。它不是只比“生成的字符串是否像标准答案”，而是让执行后的环境和产物接受验证。官方版本页显示：2.0 发布于 2025-11-07，2.1 于 2026-05-06，3.0 于 2026-07-30，4.0 于 2026-08-28；另有 Challenges 与 Science 路线。把 2.0 当作当前全貌会遗漏近几个月的重要变化。[版本总览](https://www.tbench.ai/benchmarks)

3.0 将范围扩展到更丰富的任务和环境，并强调持续维护任务、隔离评分和保留产物。它的价值在于让多步骤工具使用进入可审查的环境，而不是仅保存最终回答。[3.0 发布说明](https://www.tbench.ai/news/terminal-bench-3-0)

4.0 对时间、CPU、内存重新校准，移除 8 个任务并修正 19 个任务；统一的 8 小时 Agent 超时是该基准的实验设置，不能直接用作个人桌面 Agent 的默认预算。维护者也明确区分：环境或任务变化需要重新运行；评分器变化可能允许重新评分；纯元数据修订可能复用既有结果。[4.0 发布说明](https://www.tbench.ai/news/terminal-bench-4-0)

这个版本制度值得迁移到自己的评测集。假如只修正了“取消后不应再写入”的评分脚本，而旧实验完整保存了相关事件，可以重新评分；如果任务新要求同时取消孙进程，旧 Agent 当时根本没收到该要求，就必须重跑。两种变化产生的新分数有完全不同的解释。

### 3.3 基础设施会改变分数

Anthropic 2026-02-05 的实验报告指出，在其 Terminal-Bench 2.0 设置中，资源配置差异可造成数个百分点的变化，极端配置之间达到 6 个百分点。其关键发现是：指定推荐资源与实际执行资源限制并不相同，容器被杀、内存压力、时间限制会进入最终分数。[原始工程报告](https://www.anthropic.com/engineering/infrastructure-noise)

对本项目的含义是，Windows 进程管理、终端输出消费、取消传播和文件系统性能都可能表现为“模型失败”。例如模型已经给出正确修复，但检查进程因日志管道阻塞超时；此时换提示词未必有用。评测至少应分别记录 `任务未解决`、`Agent预算耗尽`、`执行基础设施失败`、`评分基础设施失败`，同时公开总样本数与排除规则，不能为了漂亮分数悄悄删去失败任务。

## 4. Harbor：如何组织一次可以重看、重评的实验

### 4.1 对象与生命周期

Harbor 的核心对象将实验拆成 Task、Dataset、Agent、Sandbox、Verifier、Trial、Job 和 Trajectory。Task 描述要求、环境与评分器；Trial 是一个 Agent 对一个任务的一次尝试；Job 组织多次尝试。这个区分避免把“任务定义”“一次运行”和“整批实验”混成一份日志。[当前核心概念](https://docs.harborframework.com/core-concepts)

将本文的取消例子映射进去，可以构造这样的实验，以下为设计示例：

```text
Task：一个包含取消缺陷的项目快照 + 明确的预期行为
Environment：隔离工作副本 + 指定进程与文件系统条件
Agent：指定模型、工具接口、上下文和预算的运行程序
Trial：从原始快照开始的一次完整修复尝试
Artifacts：补丁、进程事件、输出文件状态、必要日志
Verifier：检查取消后的写入、重复导出与既有功能
Job：对不同 Harness 配置进行同条件、多次尝试的比较
```

每个 Trial 都从同样的基线开始，是为了防止前一轮修复、缓存、留下的进程或长期记忆污染后一轮。研究记忆本身时可以有意保留学习状态，但必须明确哪些数据可以流入下一轮，并将测试任务答案隔离。

### 4.2 独立评分器究竟隔离了什么

Harbor 当前允许在单独环境中运行 Verifier。新的评分环境不会天然继承 Agent 的全部文件修改，需要把声明的产物转移过去；产物按原始路径恢复。这个机制将“允许 Agent 操作的空间”和“决定奖励的程序”分开，同时迫使任务作者说清楚什么是交付物。[Separate verifier](https://docs.harborframework.com/core-concepts/tasks/separate-verifier)

在教学例子中，若评分器只收到代码补丁，却没有收到取消期间的进程记录，就不能凭空推断那次真实进程已退出。反过来，只看 Agent 写出的“测试成功.json”也不能证明成功，因为这个文件可能由被评估者直接生成。可信评价需要评分器自己执行检查，或者核验由受信运行设施产生的记录。

独立容器也不是万能保证。若评分器执行 Agent 交付的代码，仍然需要隔离该代码的权限；若两个环境共享了可写目录或过强网络服务，隔离边界可能重新连接。设计时应画出真实数据流，而不是只在架构图上画两个方框。

### 4.3 产物收集与重新评分

Harbor 的产物清单记录源、目标和收集结果；文档特别说明收集是 best effort，收集失败本身不使 Trial 自动失败。这是很容易影响解释的细节：一次运行可以有分数，却缺少后来排错所需的证据。[Artifact collection](https://docs.harborframework.com/core-concepts/jobs/artifact-collection)

重新评分在新评分环境中读取旧产物，不重新启动 Agent，因此可以避免再次消耗模型成本。但它要求旧产物完整存在且满足新版评分器输入要求；如果新版检查所需的信息从未被记录，就必须承认无法重评。[Regrade](https://docs.harborframework.com/core-concepts/jobs/regrade)

工程建议是把产物分成“缺失则结果不可判定”的必要证据和“帮助诊断但允许缺失”的辅助材料。比如取消任务的必要证据是目标进程组的终态和文件变化，漂亮的轨迹截图只是辅助材料。该分级是本文建议，不是 Harbor 默认替任务作者完成的判断。

### 4.4 多步骤任务如何避免平均分掩盖失败

Harbor 当前支持多步骤任务与逐步评分，并提供 mean、final 等奖励聚合选择。[Multi-step tasks](https://docs.harborframework.com/core-concepts/tasks/multi-step)

假设一个任务有“修复、验证、取消、恢复”四步，前三步通过、最后一步重复执行外部动作。平均 75% 在数学上没有错，但不适合表达这个任务是否可交付。对于关键约束，应分别报告维度分数与整体完成条件。例如“功能分 3/4，恢复约束未通过，整体未完成”。不能用大量轻量检查稀释一个决定性的失败。

## 5. 建立能支持归因的本地实验

### 5.1 任务集应覆盖机制，而不是复制实现

一个个人 Coding Agent 的小型评测集可以优先覆盖五类真实困难：定位跨文件缺陷、理解生成文件与源定义关系、处理用户改变要求、在工具失败后调整计划、在取消或崩溃后恢复。每类保留原始问题、可检查的目标、必要环境和不应破坏的条件。

这不是要求现在为文档任务增加测试。它是后续产品进入相应实现阶段时的研究设计。样例数量应服从需要回答的问题；复制十个几乎一样的补丁题，不如增加一个真正会暴露状态错误的取消题。

### 5.2 预算匹配与消融

比较普通 ReAct 与 Plan–Execute–Replan 时，至少可以做两种不同实验：

1. **固定总预算**：两者允许相同总成本和最长时间，观察成功率、返工和成本分布。这回答用户在同样资源下应选什么。
2. **固定目标质量**：允许各自寻找达到某种成功率所需的预算，比较成本和延迟。这回答某个模式是否更经济。

消融则用于解释原因。对“规划 + 记忆 + 检索子 Agent”的完整配置，分别去掉一个组件，检查改善是否仍存在。不能一口气改五个组件，再把收益全部归功于最新加入的那个术语。

重复尝试要覆盖随机性，但不能挑最成功的一次当作默认表现。`pass@k` 表示多次候选中是否存在成功解；它不意味着产品有能力在不知道答案时选中成功解。若产品增加选择器，选择器自己的调用成本和误选率也必须计入。

### 5.3 从总分下钻到错误机制

建议记录下面这些相互可区分的失败原因：没有找到必要证据；找到了但解释错误；计划依赖错误；工具参数错误；工具实际失败；改变了无关文件；完成状态判断错误；评分器无法判定。一个 Trial 可以包含多个原因，但应区分首先发生的关键失败与后续连锁反应。

例如，Agent 改错文件后测试失败，不能只分类为“测试失败”。如果它确实拿到生成来源信息，却仍直接改生成物，这是策略问题；如果检索从未返回来源信息，是上下文问题；如果正确补丁被并发任务覆盖，是写入一致性问题。三个问题需要完全不同的改进。

## 6. 可观测性：从文本日志到有因果关系的运行记录

### 6.1 Trace、Span、事件和业务状态

Trace 表示一次相关操作的整体轨迹，Span 表示其中一个有开始和结束的步骤，事件记录某个时刻发生的变化。它们是观测结构。业务中的 task、session、run、tool call 则是工作对象，生命周期未必与 Trace 一一对应。

一个持续数天的任务可能包含许多 run 和 traces；一次重试也可能产生新的模型调用 span，却仍属于同一个业务步骤。强行让一个 Trace ID 同时承担所有身份，会让恢复、费用、用户界面和诊断互相干扰。

```text
任务：修复取消语义
  运行 A
    上下文构建 → 文件检索 → 模型请求 → 参数验证 → 修改 → 检查
    用户补充要求 → 保存待续状态
  运行 B
    恢复核验 → 重规划 → 模型请求 → 检查 → 交付
```

并行子任务可以形成多个相关分支。需要保留因果关系和业务 ID，但不能把并行耗时简单相加后当作用户等待时长。成本、CPU 时间、模型耗时与墙钟时间应分别记录。

OpenTelemetry 提供跨工具传输和解释遥测的公共语义方向。截至检索日，旧 GenAI 文档已经提示迁移到独立仓库，Agent spans 文档仍标为 Development。接入时应固定采用的约定版本，在适配层处理变化，不能将其称为已经完全稳定的 Agent 标准。[迁移说明](https://opentelemetry.io/docs/specs/semconv/gen-ai/)、[当前 Agent span 约定](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)

### 6.2 保存什么，才能解释一次失败

每个模型请求至少需要知道采用了哪个模型、哪些上下文来源、什么工具集合、哪些预算和策略版本；每个工具步骤需要知道校验、开始、结束和结果状态。上下文可以保存受控快照或可恢复的版本引用，不意味着必须把所有用户数据复制进观测服务。

本文建议优先保存这些因果关系：某条检索证据进入了哪次请求；某个补丁基于哪个文件版本；哪个检查对应哪个补丁；最后的完成声明引用哪些实际结果。这样才能回答“模型为什么这样做”和“系统凭什么说做完”。单纯记录 token 数和最终回答无法提供这种解释。

观测输出必须脱敏并受访问控制。模型密钥、完整环境变量、用户私有文件不能因为调试方便进入通用 Trace。需要保存代码片段时，应有明确作用域、保留期限和删除方式；追踪服务的租户隔离不能由业务方的 `project_id` 字段自动保证。

### 6.3 Langfuse：轨迹、评分与实验如何连接

Langfuse 将 observations 按 trace 组织，再用 session 关联多条 trace。这个结构适合将模型、检索、工具等步骤放在同一工作过程里，同时观察多轮交互。[轨迹实践](https://langfuse.com/docs/observability/best-practices)

其实验模型连接 Dataset、DatasetItem、DatasetRun、DatasetRunItem 与 Trace：对一个样本运行 Agent，得到一条运行轨迹，再将评分关联回来。评分可针对 trace、observation、session 或整次实验，因而“检索质量”和“任务完成质量”可以保存为不同对象上的分数。[实验数据模型](https://langfuse.com/docs/evaluation/experiments/data-model)、[评分数据模型](https://langfuse.com/docs/evaluation/scores/data-model)

这对自进化很有用：演化器不只看到一个总分，还能读取失败步骤，提出候选修改，再在同一数据集版本上比较。与此同时，当前实验文档说明同一实验中每个数据项按一次出现处理，重复支持仍有跟踪事项。若要做多次随机尝试，应设计明确的 trial 标识或独立实验，不假定界面会自动正确汇总重复样本。

Langfuse 的核心代码与可选企业治理部分存在许可边界；本轮查到其官方说明将常规产品功能与 SCIM、审计、细化治理等商业能力区分。自托管也意味着自己承担备份、升级、资源和隐私运维，而不是下载后自动具备生产可靠性。[开源政策](https://langfuse.com/handbook/chapters/open-source)、[官方澄清](https://langfuse.com/resources/engineering/clarifications)

### 6.4 Phoenix：开放遥测生态，但必须准确描述许可

Phoenix 提供追踪、数据集、实验和评估能力，支持基于 OpenTelemetry / OpenInference 的接入。适合在已有 Python 与遥测管线中分析模型、检索和工具步骤。[官方文档](https://arize.com/docs/phoenix)

截至检索日，其仓库 LICENSE 是 Elastic License 2.0，包含提供托管服务的限制。不能因为可以看到源码、可以自托管，就把整个项目写成与 MIT 完全同类的许可。个人内部分析和把它嵌入对外托管产品，是不同的使用情形；具体采用时仍应按实际组件及版本核查条款。[当前 LICENSE](https://github.com/Arize-ai/phoenix/blob/main/LICENSE)

### 6.5 LangSmith：把多轮追踪、调试和评价接成改进过程

#### 6.5.1 定位与对象：不依赖 LangChain 才能使用

LangSmith 是观测、评测和 Agent 工程平台。它与 LangChain / LangGraph 有直接集成，也支持给普通函数手动埋点，以及接收其他框架的 OpenTelemetry 数据。因此，采用本项目自己的 Python Agent 循环，不会自动排除 LangSmith；使用 LangGraph 也不等于必须把业务状态交给 LangSmith。[手动追踪与对象定义](https://docs.langchain.com/langsmith/observability-concepts)、[OpenTelemetry 接入](https://docs.langchain.com/langsmith/trace-with-opentelemetry)

当前文档区分四个观测对象：run 是一次模型、工具或检索步骤；trace 收集一次操作的 runs；thread 连接多轮 traces；trajectory 将会话投影为去重、有序的消息序列。最后一种适合阅读对话经过，但移除了执行树的嵌套，不能代替分析并行关系和耗时的 trace 视图。Messages view 当前仍标为 beta。

这些名称容易与产品对象混淆。LangSmith 的观测 run 更接近 span，并不等于本项目“一次持续 Agent 运行”的 `run_id`。接入时应保留业务身份，再把它映射为 metadata；不能为了套平台字段改变已有领域对象。

以本文的取消任务为例，第一轮读文件、修改、测试构成一个 trace，用户补充“还要终止孙进程”后形成另一轮 trace。两个 trace 属于同一 thread。只看最后一轮，会漏掉先前为什么选择某个实现；只看平铺 trajectory，又可能看不出测试和后台任务实际同时运行。不同视图解决不同排错问题。

#### 6.5.2 从线上失败走到离线实验

LangSmith 的 offline evaluation 使用数据集及样本，可以提供参考输出；online evaluation 面向真实 runs / threads，通常没有标准答案。前者适合比较候选版本，后者适合发现异常和收集新案例。数据集具有版本与分割能力，便于固定实验输入。[评测概念](https://docs.langchain.com/langsmith/evaluation-concepts)

一个完整的使用过程可以是：线上发现取消任务反复重试，将相关 trace 交给人工判定；把确认后的问题整理成带原始环境说明的样本；在固定数据集版本上分别运行旧、新 Harness；比较完成率、残余进程、模型成本与人工接管；发布后继续观察同类问题是否减少。这里平台提供的是连接样本、轨迹与评分的设施，取消是否真的生效仍需要执行环境产生证据。

人工标注并非只能在日志旁点一个赞。LangSmith 提供单 run 与成对比较队列，可配置 rubric、分配评阅者、管理保留与完成状态，并把整理后的案例送入数据集。这有助于把“新版本感觉更好”转为针对同一标准的比较。[Annotation queues](https://docs.langchain.com/langsmith/annotation-queues)

本项目若以后研究 Skill 自进化，可以用成对比较评价两种交付说明的清晰度，用确定性检查评价补丁行为，再把两种结果分别保留。不能让“解释更清晰”掩盖真实取消失败，也不能让优化器接触隐藏测试的标准答案。

#### 6.5.3 Studio 调试与业务恢复的区别

LangSmith Studio 可以从追踪记录进入调试流程，并将相关会话历史带到本地 Agent 中分析。[Studio 可观测性](https://docs.langchain.com/langsmith/observability-studio)

它降低的是复现问题时整理上下文的成本。对于具有副作用的 Coding Agent，这不等于外部世界已经回到原状态：工作区代码可能改变，远程请求可能已完成，测试服务可能已经关闭。因此，“导入历史继续运行”应在隔离环境里建立对应基线；不能把历史轨迹当成对真实用户目录重新执行动作的授权。

这也是选择观测平台时必须检查的界限。能重看轨迹、能构建调试分支、能恢复生产任务，是三个不同能力。前两个很有价值，但不能替代 Harness 的操作状态与幂等设计。

#### 6.5.4 SmithDB：为什么 Agent 追踪需要特殊数据组织

LangChain 在 2026-05-13 发布 SmithDB 介绍：以对象存储保存追踪数据，用小型 Postgres metastore 保存段元数据，配合无状态的摄入、查询和压缩服务；实现使用 Rust、DataFusion 和 Vortex，并针对 Agent 的树形查询、全文搜索、延迟到达的 run 更新等负载做处理。发布时描述的是当时云服务迁移状态，不代表所有历史自托管版本自动使用同一架构。[SmithDB 工程文章](https://www.langchain.com/blog/introducing-smithdb)

其架构价值可以从本文的长任务推导：一个步骤开始与结束相隔很久，完整 Trace 不能等最后结束才变得可查询；错误线索可能出现在某个子步骤的任意 JSON 字段里；一个用户任务又可能跨多个 trace。传统“按时间追加日志后全文搜索”的方式虽然能保存文本，却难以同时快速支持这些查询。

对个人桌面项目，这并不意味着要复刻一个分布式数据库。值得借鉴的是先保存稳定身份、父子关系、版本与增量更新语义，避免将未来可查询性锁死在一段巨大聊天字符串里。厂商文章中的性能倍数属于其负载下的自报结果，本文不据此宣布其普遍快于其他平台。

#### 6.5.5 2026 年近期变化：评价与请求治理已经分成产品能力

2026-07-30 的 LLM Gateway 公测说明将花费限制、速率限制、模型 fallback 和敏感数据处理放在模型请求路径上，并把控制事件关联到 LangSmith traces。这是实际请求治理，与事后观察不同。可用套餐与部分数据保护能力还有条件，应按采用时文档核查。[公测说明](https://www.langchain.com/blog/langsmith-llm-gateway-runtime-controls-for-production-agents)

对于本项目，这说明观测平台正在向运行控制扩展，但不构成更换已确认 Go 网关或增加静默模型切换的理由。自动 fallback 可能改变推理语义、成本和结果可复现性；是否允许必须由产品策略决定，不能因为平台支持就默认打开。

2026-08-18 发布的 Tuned Evaluators 首先提供 Perceived Error：由托管的专用评价器对满足条件的会话附加反馈。发布说明写明它需要一定会话轮次与空闲条件，并在达到条件后异步完成评价；它不是每次动作前的实时安全阻断器。文章包含 Vanta 作为早期合作方的使用反馈，但没有公开可独立复现的客户对照实验。[发布说明与适用条件](https://www.langchain.com/blog/introducing-langsmith-tuned-evaluators-starting-with-perceived-error)

这类评价器的落地价值在于发现没有系统异常、也没有用户显式打差评的失败会话。本文的分析是，应将其作为待调查信号：对“用户感知到问题”的判断不能代替编译、行为正确性或外部操作事实。托管 judge 的版本变化也需要进入实验记录，避免把评分器变化误认为 Agent 进步。

#### 6.5.6 开源、商业与自托管边界

LangChain / LangGraph 框架、LangSmith SDK、LangSmith 服务端平台是不同对象。存在公开 SDK 与部署资料，不表示整个服务端是可按开源框架方式自由部署的产品。当前官方自托管文档明确将其列为 Enterprise 的附加能力，需要相应许可；也可以只采用观测与评测，不同时使用 Agent 部署。[当前自托管说明](https://docs.langchain.com/langsmith/self-hosted)

选择时应分别核对：数据是否出本地、哪些服务需要自行运维、是否需要企业许可、区域与保留策略、能否导出原始数据，以及退出平台后实验历史如何保留。只比较“是否有 self-hosted 选项”会隐藏实际部署成本和条件。

### 6.6 LangSmith、Langfuse、Phoenix：在同一组问题上比较

下面比较的是本文核查的产品结构与采用条件，不是未经运行的性能排名；三者均有跨框架接入路径，不能将 LangSmith 简化为 LangChain 专用。

| 维度 | LangSmith | Langfuse | Phoenix |
| --- | --- | --- | --- |
| 追踪组织 | run / trace / thread / trajectory，区分执行树与消息投影 | observation / trace / session，连接提示、调用与评分 | 以 traces / spans 和 OpenInference 语义组织模型、检索与工具 |
| 改进过程 | 线上评价、人工队列、数据集版本、实验、Studio 调试衔接 | traces、scores、数据集、实验与提示管理连接 | 遥测检查、标注、数据集、评估与实验衔接 |
| 自定义 Python Agent | 手动埋点或 OTel，无须采用 LangChain 核心 | SDK / OTel 接入，业务语义需要自己映射 | OTel / OpenInference 接入，需核查具体集成与属性 |
| 许可与部署 | 商业平台；自托管有 Enterprise 条件 | 核心 MIT 与可选企业治理部分区分 | 当前仓库 ELv2；可自托管但有许可限制 |
| 本文重点看到的差异 | 多轮调试与人工评价流程；2026 年 SmithDB、Gateway、专用 judge | 数据模型直接连接自建评估循环；核心自托管路径 | 开放遥测语义与检索 / 模型分析生态 |
| 采用前仍需实测 | 实际数据量、费用、导出、区域、长任务与自托管版本 | 自托管资源、重复实验建模、权限与保留策略 | 运行负载、部署运维、组件许可和目标框架兼容 |

具体判断应从工作方式出发。已有 LangGraph 团队需要把多轮排错、人工队列、实验与托管运行相连时，LangSmith 是必须认真评估的候选；坚持自己掌握核心部署、希望直接组织追踪与评分数据时，Langfuse 值得比较；已有 OpenTelemetry / OpenInference 管线并关注检索与模型过程分析时，应同时评估 Phoenix。上述都是选型假设，需要用自己的数据验证，并非平台的排他能力。

对于本项目，当前最合理的架构决策是保留可导出的运行事实和薄适配层，而不是马上选定平台。选型实验可以把同一批脱敏轨迹送入候选系统，检查能否准确还原多轮任务、并行步骤、取消、重试费用和人工反馈，再比较操作负担。

三者都不能替使用者定义“成功”。平台能存评分，但如果评分规则奖励长回答、更多文件或更多测试数量，平台只会更准确地记录错误目标。

## 7. LLM-as-a-Judge：适合补充判断，不能吞掉外部事实

对于文档清晰度、界面一致性和需求覆盖，单一确定性测试可能不足，模型评分器能帮助分层判断。但它应阅读需求和可核验证据，而不只阅读生成者的自我总结。

一个可用的评分输出应包含具体标准、结论、证据位置和无法判断的事项。例如“取消后无新增写入”应引用进程与文件观测；“说明便于用户理解”可以由模型或人工评阅。把两者都交给一句“请打 1–10 分”，会掩盖依据差异。

常见误差包括偏爱长答案、认同相似措辞、被候选答案中的指令影响、在答案顺序变化后改判，以及与生成者共享盲点。可以通过交换顺序、盲去模型名称、人工标定样本和独立事实检查降低风险。涉及安全与关键正确性的硬约束，应单独报告，不能被文风高分抵消。

评测任务也需要反向验证：已知正确解应通过，已知错误解应失败，删掉关键行为的投机解不应获得高分。否则自进化系统会越来越擅长满足评分器，而真实能力没有同步改善。Agent 评测的任务、尝试、轨迹、评分器和结果分离也见 Anthropic 的工程综述。[Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 8. 企业与真实开发：生产率证据为什么互相看似矛盾

### 8.1 METR：旧结论不能直接代表 2026 年

METR 的早期研究得到经验丰富的开源开发者使用当时 AI 工具后完成任务变慢的结果。2026-02-24 更新明确说明，后续研究出现参与者和任务选择偏差，且多 Agent 并行使时间记录更难解释；作者认为新数据对当前加速幅度只提供很弱证据。不能把旧研究写成“今天 AI 普遍降低效率”，也不能把新样本的点估计写成确定的普遍提速。[METR 更新原文](https://metr.org/blog/2026-02-24-uplift-update/)

这个案例揭示一个测量问题：使用 AI 后，开发者可能开始选择过去不愿做的任务，同时在等待期间推进其他工作。只比较单个任务的墙钟时间，会遗漏任务选择、注意力分配和质量要求的变化。真实收益应结合交付量、人工投入、审查成本、返工和缺陷一起解释。

### 8.2 大规模会话观察也不是随机对照实验

Anthropic 2026-06-16 报告分析了约 40 万次、发生于 2025-10 至 2026-04 的 Claude Code 会话，研究人类与 Agent 的规划、执行分工及成功信号。它明确说明无法直接观察用户全部现实结果，而是依赖会话分类和测试、提交等证据。因此可用于理解使用方式，不能把模型分类出的会话成功率直接等同于企业投资回报。[原始研究](https://www.anthropic.com/research/claude-code-expertise)

将两类证据放在一起，更合理的问题是“哪些人在什么任务上，以怎样的交互方式获益”。个人 Agent 的产品分析也应保留任务类型、用户接管与失败恢复信息，而不是只统计一周生成了多少行代码。

### 8.3 社区讨论应该怎样进入结论

社区会把复杂研究压缩成“AI 更慢”或“AI 已经快 20%”的标题。关于 METR 更新的讨论就出现了这类解读。讨论可帮助发现用户关心的指标、等待与审查负担，但准确结论仍应回到研究原文的样本和限制。[相关讨论](https://www.reddit.com/r/ExperiencedDevs/comments/1tlqzld/update_study_2025_study_shows_experienced_devs/)

本文不把点赞数、开发者自报倍数或商业客户案例当作可直接横向比较的实验结果。它们回答的是采用体验和可能价值，标准化基准回答的是受控能力，实际业务评估回答的是用户净收益，三者需要相互补充。

## 9. 对本项目的可执行研究结论

先让已有运行事实可以被准确关联，再增加评分设施。优先保存任务与运行身份、模型请求预算、工具终态、补丁基线和实际检查结果；这些也是恢复能力的基础，不应为了接入某个观测平台复制第二套业务状态。

当相应 Coding Agent 闭环进入实现阶段后，用少量有代表性的隔离任务比较朴素基线与新设计。先验证一次任务能被正确判定，再扩展重复实验、公共基准和自进化。Windows 桌面行为需要自己的真实环境证据，Linux 容器基准通过不能代替它。

采用顺序应由问题决定：需要定位失败时接入轨迹；需要比较策略时引入版本化任务集；需要跨实验分析时比较 LangSmith、Langfuse、Phoenix、Braintrust、Weave 与现有遥测栈；需要演化时才让评分器参与候选选择。评测平台不是先装上就会带来质量，可靠的任务定义、证据与结果解释才是共同前提。

## 10. Braintrust：把生产问题转成可重复的质量实验

### 10.1 对象关系与开发流程

[Braintrust 当前评测文档](https://www.braintrust.dev/docs/evaluate) 将可变 playground 与不可变 experiment 区分，并连接线上轨迹、人工标注、数据集和评分。评价由输入数据、待测 task 和 scorer 组成；一次观察到的失败可以进入数据集，在后续版本中再次比较。它的落地价值是缩短“发现问题—形成样本—检查改进”的路径，而不只是绘制 token 图表。

用一个 coding agent 的例子说明：用户反馈“修复后构建仍失败”。有用的实验样本应保存初始仓库版本、任务要求、环境条件与预期结果，而不是只截取最后一句回答。task 运行被测 Agent，scorer 检查补丁和构建产物。若只把最终文本交给语言模型打分，就可能把解释流畅的失败补丁选为更优版本。

### 10.2 重复实验与轨迹树

[高级评测文档](https://www.braintrust.dev/docs/evaluate/advanced-evaluations) 支持全局与逐样本 trial count，适合观察随机输出方差；文档同时说明逐条 `experiment.log()` 与增量 tracing 混用可能产生错误父子关系。[轨迹查看说明](https://www.braintrust.dev/docs/observe/examine-traces) 则将嵌套模型、工具和其他操作放到同一次任务下查看。

这两个机制必须一起理解。对一个偶发失败重复五次，如果每次初始工作区不同，方差可能来自环境而非模型；如果重试 span 被记录为另一个根任务，费用与成功率也会失真。本研究建议用独立 `trial_id` 关联模型调用、执行环境与最终评分，再明确样本级和试次级聚合方式。

平台可以组织这些记录，但不会替应用决定“用户取消”算失败、缺失评分算零分还是未评估。线上异步评分也适合发现问题，不能自动成为执行前的批准机制。采用时应核查数据保留、代码与模型内容的脱敏、接入语言和部署条款；本文未给出未经核实的自托管或全栈开源承诺。

## 11. W&B Weave：将调用记录绑定到应用对象版本

### 11.1 Op、Call 与 Object 分别代表什么

[Weave 概念文档](https://docs.wandb.ai/weave/concepts/what-is-weave) 通过被追踪的 Op 记录实际 Call；[对象文档](https://docs.wandb.ai/weave/guides/tracking/objects) 对模型配置、提示和数据集等可序列化对象进行版本管理。这里的 Model 可以描述应用逻辑及配置，不必是可下载权重文件。[Model 教程](https://docs.wandb.ai/weave/tutorial-weave_models)

为什么应用对象版本有价值？同样叫“检索问答”的函数，可能换过提示、检索器参数和模型。只记录函数名与时间，很难解释质量为何变化。将调用绑定到对象版本，可以追踪是哪种组合参与了某次评价。不过外部向量索引若只保存一个 URL，索引内容变化仍未被完整冻结；版本化应用配置不是自动冻结全部依赖。

### 11.2 从评价对象回到原因

[Weave Evaluation 教程](https://docs.wandb.ai/weave/tutorial-eval) 将数据集、待评对象和 scorer 连接为评价。对 coding agent，可将检索方法、上下文政策、模型配置和补丁策略作为受控配置，比较同一任务集上的行为，再从失败 Call 回到具体调用。

本研究建议同时保留源码 commit 与应用对象版本。前者说明工程实现，后者说明运行配置；再加数据集和评分器版本，才能判断分数变化来自程序改动、参数选择还是评价变化。若评价器也用模型，评价器自己的版本与输入应能被追踪。

当前文档明确部分 Python 与 TypeScript 对象能力不同，不能因两种 SDK 都存在就推断功能完全对齐。本文核对公开文档，没有安装服务，也不以 SDK 仓库许可推断整个商业平台的许可。

### 11.3 五个平台用同一问题比较

下表是本研究基于前述文档的选型问题，不是独占能力或优劣排名。

| 平台 | 本文重点验证的切入点 | 同一个 coding 失败应怎样追踪 | 采用前仍需核查 |
| --- | --- | --- | --- |
| LangSmith | 轨迹、数据集、调试与评价闭环 | 从 thread / run 到问题样本与实验 | 产品版本、商业部署与数据策略 |
| Langfuse | 观测对象、prompt 与实验关联 | 将业务任务身份映射到 trace 和评价 | 重复试验组织、云端与自托管能力差异 |
| Phoenix | OpenInference / 遥测和评价分析 | 跨框架保留调用层级与检索证据 | 当前许可、导出与集成覆盖 |
| Braintrust | task / scorer / experiment 与生产反馈 | 把一次失败形成可重复的 task 样本 | 试次聚合、记录方式和服务边界 |
| Weave | 调用与应用对象版本 | 将异常 Call 关联到配置、数据与 scorer | 外部依赖是否真的固定、语言能力差异 |

共同缺口也要看清：它们都不能仅凭一条 span 证明外部文件修改已落盘，不能替代产品恢复台账；统一 OTel 接入也不保证不同平台对 Agent 特有状态的理解一致。最有价值的接入验收，是沿一条真实失败从用户任务走到执行证据、评价结论，再走回可重现条件。

## 12. ProgramBench：从修复已有仓库到复原可观察行为

[ProgramBench 原始论文，2026-05](https://arxiv.org/html/2605.03546v1) 构造 200 个完整程序重建任务，提供参考可执行程序和使用文档，让 Agent 在无法读取原始源码的条件下实现行为兼容的程序。构建环境隔离和测试筛选用来降低答案泄漏、无效断言与不确定测试的影响。本轮补读了相关方法，未复现实验或核验全部任务。

这比 issue 修复多考查一层能力：Agent 要自己发现输入输出契约，并建立实现结构，而非在现有架构中定位局部错误。它也给了可操作的环境反馈——运行参考程序可以观察行为。其适用价值更接近“通过实验理解未知系统并实现兼容”，不能直接等同无规格创业产品开发。

以下为本研究例子：参考命令接受一个空文件，返回特定退出码。Agent 需要判断这是输入校验、格式规则还是运行异常，再用自己的实现匹配。仅从说明书猜测默认行为可能失败；不断试探又会消耗时间。因此观察策略和预算与最终代码同样重要。

有限测试仍只覆盖行为的一部分。通过所有测试不能证明两个程序对所有输入等价，代码覆盖率也不直接证明规格完整。此类基准应与仓库维护、多轮需求变化、GUI 和真实用户收益分别报告，不能用一个总分涵盖所有 coding agent 能力。

## 13. SWE-Bench Pro Verified：2026-09 的新材料怎样改变评测解释

[2026-09-08 的预印本](https://arxiv.org/abs/2609.08149) 提出 SWE-Bench Pro Verified；它与早先的 SWE-bench Verified 不是同一个数据集。论文并行处理执行时答案泄漏与任务质量，后者包含描述冲突、测试过窄或过宽等问题。方法结合自动审查与人工最小修订，并比较保护环境和修订任务对结果的影响。[方法全文](https://arxiv.org/html/2609.08149v1)

这项研究的关键意义是：更“新”或更“难”的题目，也不保证评价有效。若任务描述允许两种实现，测试却只接受一种，失败可能来自测试过窄；若测试没有覆盖核心要求，成功又可能来自测试过宽。训练集污染和运行时获取参考答案则是不同问题，仅换一批新题不能同时解决。

本研究建议把分数变化拆开解释。采用隔离措施后下降，可能是关闭了答案泄漏路径，也可能是误限制了正常依赖；修订任务后提高，可能是消除歧义，而非模型能力升级。因此应分别保存环境变化、任务变化和 Agent 变化，不能将三个变量同时变动的结果归因给新模型。

该材料距检索日仅八天，属于作者研究与公开预印本，不能当成已经获得广泛独立复现的行业定论。本文没有将其局部发现概括为所有模型“作弊”，也没有替换此前基准；它补充的是判断基准可信度所需的分析维度。
