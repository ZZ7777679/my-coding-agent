# dsh-context：把上下文从一个数字变成可解释的数据流

> 核查日期：2026-09-23。`bowenliang123/dsh-context`，0.54.4，固定提交 `6064731c9f1c2fd77df40e3b951ed54df6c0f60a`，Apache-2.0。源码与兼容说明已读取，未运行其界面或测试。

## 1. 它解决的不是“显示 token 数”

一个长会话为什么越来越慢？是工具 schema 太多、重复注入项目规范，还是一次读取了很大的文件？压缩后总量下降了，但究竟删除了什么？只显示“上下文使用 70%”无法回答这些问题。

dsh-context 记录每个请求时的组成、随 step / turn 的变化、压缩事件、工具来源、文件活动和费用。它是诊断层，不是替代 DSH 的压缩器；图中看到的估算也不天然等于模型供应商的账单。

## 2. 仓库怎样将事实、算法和 UI 分开

| 路径 | 职责 | 为何要独立 |
| --- | --- | --- |
| `src/host/index.ts` | 挂载投影、详情通道和可选设置 | 不把算法混进启动代码 |
| `fold.ts`、`timeline.ts` | 将事件折叠成上下文历史 | 可以从持久日志重新计算 |
| `logShapes.ts` | 识别不同日志代际的字段 | 避免到处按版本号分支 |
| `headers.ts`、`attribution.ts` | 请求头和工具来源 | 总量与归属分开解释 |
| `detail.ts`、`backfill.ts` | 大数据按需读取、旧会话补算 | 不在启动或每次推送时读全库 |
| `src/shared` | 估算、图片、价格和文件操作类型 | Host / Client 共享纯计算规则 |

入口只把 `sessionProjections` 列为必需服务。侧栏、设置、详情通道和余额等功能通过可选接缝装配。缺少一种展示能力，不必让整个投影失效。[入口源码](https://github.com/bowenliang123/dsh-context/blob/6064731c9f1c2fd77df40e3b951ed54df6c0f60a/src/host/index.ts)

## 3. 请求发生后，怎样得到可信的时间线

插件不另写一份“真实会话”。它注册 projection definition，由宿主把已提交事件交给 fold，保存可序列化状态，再将 view 推给浏览器。状态含当前 surface、各类别累计量、请求记录、工具调用关联和待处理的压缩替换信息。

例如模型调用工具读文件：

1. tool call 建立调用身份和工具名的关联。
2. tool result 成为上下文 surface 的节点，进入工具类别。
3. 下一请求的 header / usage 与当时 surface 共同形成请求记录。
4. 浏览器显示占用及变化，用户再按需展开某次请求的组成。

这一方式允许实时和重启后的历史走同一套算法。副作用是投影实现必须准确跟随日志契约，不能依赖当前聊天 DOM 来反推模型看到了什么。

## 4. 压缩为什么不能简单“减去一段字符”

压缩事件声明被遮蔽的节点；后续替换消息本身又会占用 token。该插件用 `pendingShadowedSeqs` 暂存被替换的实际 seq，并在替换发生时移除对应 surface 节点，再加回摘要。事件展示的是净释放量，而不是原文的毛大小。

特别是剪枝产生的替换节点，其 seq 可能位于原区间末尾之外。如果仅按 start / end 删除，会遗留节点并重复计数。源码因此优先按实际 seq 集合更新，并对旧字段 `start/end` 与新字段 `startSeq/endSeq` 统一适配。这是上下文可观测性真正有技术含量的部分。[fold 实现](https://github.com/bowenliang123/dsh-context/blob/6064731c9f1c2fd77df40e3b951ed54df6c0f60a/src/host/fold.ts)

一个容易忽视的持久化细节是 plain JSON：未知字段应缺席，而不是留下值为 undefined 的属性。源码说明某个投影状态不可序列化可能影响整次缓存写入，甚至连带会话标题缓存。扩展自己的统计字段，也必须遵守宿主的缓存契约。

## 5. 大量历史如何避免拖慢每次会话

常驻推送只携带轻量视图，大型集合经详情通道按查看者拉取。新增投影或提高 stateVersion 后，旧会话缓存可能没有新字段；只等下一条事件，长期不活跃会话会一直显示不完整数据。

`backfill.ts` 因此在用户第一次打开 Dashboard 时触发一轮补算，跳过活跃会话，读 cold log，借宿主 `coldSnapshot` 的缓存路径复用已有部分、折叠余下事件并回写。它不是每次启动扫描全部历史，也不是往原始日志补造新事件。[按需补算](https://github.com/bowenliang123/dsh-context/blob/6064731c9f1c2fd77df40e3b951ed54df6c0f60a/src/host/backfill.ts)

## 6. 时效性检查揭示了哪些真实限制

作者 9 月 22 日的兼容表覆盖 DSH 0.1.2-rc.1 至 0.1.7-alpha.2，明确区分源码 seam matrix 与临时 profile 的人工安装 / 卸载：最新一行只有前者，不能写成完整端到端验收。

兼容说明还主动披露两项缺口：

- V4 图片卸载通过另一层消息投影改写，而插件读取原始持久事件；特定恢复路径上，图中图片占用可能暂时高估。
- 新版撤掉旧 settings host face / slot 后，偏好设置退回默认值；图表主要能力可工作，不意味着所有设置入口都已完成迁移。

因此最有参考价值的不只是图表，而是它把“支持版本”“测试到哪一层”“已知统计偏差”写成可审查的契约。[兼容记录](https://github.com/bowenliang123/dsh-context/blob/6064731c9f1c2fd77df40e3b951ed54df6c0f60a/docs/compatibility.md)

## 7. 本项目可以吸收什么

现有 Trace 已保存真实运行事实，请求材料和上下文服务也已存在。可在同一事实来源上增加“本次请求组成”：规则、Skill、记忆、对话、工具定义与工具结果各占多少；增加与上一请求的差异，以及压缩前后可回查关系。

实现顺序宜是来源归属 → 单次请求解释 → 变化趋势 → 历史按需聚合。先有可解释的数据，再决定画什么图。不要为统计再保存一套彼此独立的对话，也不要把额外诊断计算放进每次模型请求的必经慢路径。
