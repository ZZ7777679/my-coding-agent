# 非官方 DSH 二次开发对本项目的参考：围绕核心模块的吸收顺序

> 2026-09-23。以当前工作区和 M4 进度为基线。本文是研究总结，没有开始产品实现、增加依赖 / 模型 / 通用插件系统，也不改其他任务维护的规划与进度。上游机制的源码证据见本专题各篇。

## 1. 先给结论：最值得学的是扩展能力如何落在真实运行过程里

这些社区项目说明，coding agent 的改进不只有换模型或加提示词：上下文可以解释到来源、协作可以区分一次任务与一次尝试、工具可按需要披露、长期记忆可以纠正和遗忘、桌面应用可以在插件树损坏时仍保留恢复入口。

它们也展示代价：插件组合带来生命周期、版本、缓存和身份冲突；同一个名称可能对应不同生态；宣称“自进化”可能只是增加了提示和版本文件。我们应选择能解决当前具体痛点的机制，而不是整体搬运一个运行时。

## 2. 当前已经有的能力，不能重复当成待建项

| 模块 | 当前工作区事实 | 研究建议的增量边界 |
| --- | --- | --- |
| Runtime / 多轮会话 | Python 共用运行核心，桌面 / RPC 接入；有停止、续接和持久记录 | 核对跨生命周期关联和终态表达，非重建 agent loop |
| 上下文 | 手动 / 自动压缩、来源材料、归档回读与请求窗口已有实现 | 更直观解释一次请求实际纳入 / 排除什么 |
| 记忆 | 本地记忆、知识页、维护、纠正 / 遗忘已有实现 | 提高来源和冲突可见性，非默认接外部向量库 |
| 协作 | 正式会话分工、方向授权、持久消息 / 等待、可选内部 worker | 结果跨运行导航、尝试归属、持续团队需按需求评估 |
| Skill / MCP | 本地及在线导入、项目启用；stdio / HTTP MCP、资源和 OAuth 路径已接入 | 版本 / 来源 / 生效状态表达，非再次建议从零接 MCP |
| 工作流 | 模板、阶段、会话分配作为任务数据保存 | 仍不是通用可执行工作流引擎 |
| Trace / 修改记录 | 请求、工具和成果关联，before / after 差异已有实现 | 增加关联阅读价值；整目录回滚是另一项能力 |
| 执行 / 沙箱 | 所选项目默认本机执行，原目录协作；沙箱按实际可用能力显示 | 不能用 scope / worktree / 文件范围检查冒充 OS 隔离 |

## 3. 从用户打开任务开始：身份与生命周期

### 借鉴对象

Anywhere Desktop 的 startup generation、Open Design 的 request / session 握手、dsh-market 的 profileContext，以及 dsh-browser 的 tab affinity，处理的其实是同一类问题：**当前界面看到的对象，不一定是某个在途操作最初绑定的对象。**

我们已有 project_id / task_id / session_id / run_id，并要求迟到事件不覆盖新选择。可以进一步从用户视角让终端、预览、成果、协作回复都能回到其来源运行；重启后的后端实例与旧 UI 订阅也要准确区分。

需要核对的是具体迟到回调和实际资源拥有者，而非到处增加版本字段和重复校验。Open Design 的取消锁存可以提示我们检查“用户在启动接纳完成前按停止”这一窗口；Anywhere 的 generation 说明资源要由一代启动整体释放，而不是在各处猜测是否仍有效。

### 演化方向

社区从“能打开网页”走到“能升级、重启、恢复和多入口使用”，身份问题才集中暴露。我们后续加强桌面生命周期时，应优先延续现有服务所有权，保持 Python 对业务数据的单写者，不复制两套项目 / 会话状态。

## 4. 构建下一次请求：上下文的解释能力

[dsh-context](03-context-inspection.md) 最值得参考的是依据日志事件重建上下文投影，并处理 shadow、replacement 与冷历史回填。它不只画一个 token 进度条，而是解释“这部分为何仍在、那部分为何消失”。Modlens 又增加一层：历史保留原图，请求发出时可能替换成视觉证据。

我们的上下文模块已有来源材料、摘要和精确回读，因此可以围绕已有事实改善阅读：主请求材料与摘要取材分开显示，来源可跳转，估算与服务端 usage 分开，工具输出原文与模型看到的裁剪形式分开。不是再做一套平行的上下文计算器。

建议采用的原则是投影视图可以重建，原始事实不因 UI 分桶而被改写；后台回填不阻断活跃请求，复杂详情按需读取。dsh-context 在 V4 图像 offload 上仍有统计局限，也提醒我们不要把日志字节数简单宣称为真实模型 token。

实际价值是解释长任务为什么遗漏信息，并帮助判断压缩、工具输出和 Skill 加载是否浪费预算；单纯展示更多指标而不能回到来源，对用户价值较小。

## 5. 记忆与 Skill：先把变化说清，再讨论自进化

[memory-evolve](04-memory-evolve.md) 展示低成本本地记忆和回合内维护；[OpenViking / Mem9](05-memory-backends.md) 展示独立存储、召回和异步 capture；[Odai](08-ouroboros-and-odai.md) 展示 scope、来源、冲突与 Skill generation。

我们已有本地记忆维护，首要增量应是让用户知道一条记忆来自哪次输入、何时被修正、哪些项目会使用它。单纯把内容送到外部 memory server，不会自动解决错误记忆和授权范围；还会新增网络、身份、删除同步和失败处理。

Skill 可以参考 Odai 的候选与 active version 分开、上游更新时 rebase、保留 rollback 路径。我们已经有资源库 / 项目导入与来源文件，未来若允许 Agent 修改 Skill，应基于这些已有身份表达“本轮仍用旧版本、下一轮启用新版本”，避免运行中途语义改变。

RSI 的讨论应放在这一完整链条上：候选怎么产生、效果怎么观察、如何防退化、谁选择生效。仅修改 Skill 文件不证明能力增强。本项目未要求自动自改进，因此现在可借鉴版本与来源表达，不需要新建常驻评价 Agent 或为每次修改跑大型基准。

## 6. 工具、MCP 与插件：披露、权限和运行时是三层

[推理路由套件](15-reasoning-router.md) 的 tools_catalog / tools_help 对控制上下文有参考价值：先给短索引，真正使用时再取参数。它的阶段 restriction 是另一个功能，不能混成“减少 schema 就必须先过审批”。我们的 MCP 工具目录已经支持搜索和参数说明，后续只需评估模型请求侧是否仍有具体目录负担。

[Qwen carrier](09-multimodal-and-browser.md) 的演化提示适配层应随宿主能力增强而变薄：通用媒体、取消、认证交给负责该边界的组件。OpenViking 则说明若可选 MCP 握手挂起，不能连已有记忆 hooks 都无法装配；可选服务的生命周期应隔离。

通用 JavaScript 插件在宿主进程里运行，与 MCP 子进程、Skill 文档完全不同。DSH 的 scope 解决服务和注册可见性，不能限制插件任意文件读写。我们当前无需为了这些参考项目直接引入 Cordis；保持 Skill、MCP、内置工具各自明确职责，按真实替换需求再决定扩展接口。

## 7. 运行和协作：消息送达、成员空闲、任务完成要分别表示

[Agent Teams](06-agent-teams.md)、[task-coordinator](07-workflow-and-coordinator.md) 和 [Ouroboros](08-ouroboros-and-odai.md) 提供三种控制方式：持续成员池、正式会话协调、外部编排器向宿主派发执行。选择哪种，应先问用户需要长期团队，还是现有会话补充信息 / 一次性 worker。

我们的 `send_message()` 已经只投递不自动启动空闲接收方，`inbox()` 在请求边界交付，`acknowledge_messages()` 在完整模型回合后记录 delivered_run_id。这比泛泛要求“做邮箱”更具体，不能重复提案。[现有投递实现](../../../src/my_agent/collaboration/service.py)

值得继续检查的增量是任务尝试身份：旧 worker 的晚到结果能否被清楚标为旧运行的成果，而不是新尝试的完成事实；用户能否从结果跳回源运行、真实工具和修改。Nanmi 的 attempt_id 与 Ouroboros 的 stale_dispatch 提供参考，但我们已有 run_id / worker record，应先核对是否已足够，不自动再套一层新协议。

持续成员池会进一步需要 idle / stopped / task pending / parked 等区分；冷启动恢复与本进程观察到的 idle 也不能混用。若没有常驻团队需求，这套调度复杂度暂不值得引入。

多会话同目录还要牢记：调度锁只保护调度事实，不能阻止外部编辑器或 shell 改文件；attempt 失效也不自动撤回已经发出的副作用。现有文件工具的基线检查继续负责它自己的边界，不能把 worktree 变成普通并发的强制前提。

## 8. 工作流：描述性模板、程序编排与后台调度分开演化

[dsh_workflow](07-workflow-and-coordinator.md) 在 QuickJS 中运行显式工作流，通过宿主桥执行副作用并缓存 effect；[dsh-web Task Board](14-topic-products.md) 则用 Host ledger 管后台任务和 cron。它们分别解决重复编排与未来调度，不是同一个“多 Agent 功能”。

我们当前 `WorkflowStage` / `TaskWorkflow` 保存流程快照、阶段和会话分工；Skill 装配明确告诉模型它是 guidance，不授予执行权限，也不自动创建正式会话。可以继续保留这种轻量方式，直到出现值得固化的稳定流程。

如果未来引入程序工作流，需要明确 checkpoint 到底保存控制位置还是仅缓存工具结果；外部副作用发生后、结果尚未保存就中断时不能声称 exactly-once。若引入定时任务，需要明确错过时间是否补跑、关闭 UI 与退出 Host 的区别，以及请求 / 执行 / 会话身份关系。研究本身不授权创建当前任务的自动化。

## 9. 成果呈现、Trace 与恢复

[Sidebar / GenUI / ChangeLedger](10-workbench-and-rewind.md) 分别改善过程可见、成果交互和文件恢复。我们的 Trace 已按请求和工具调用身份关联，文件 before / after 也已有存储；可优先把用户关心的“改了什么、由哪个协作任务做、怎么继续”连接起来。

GenUI 可为比较表、方案选择和结构化报告提供有限组件，但 localStorage 的选择状态不是后端业务事实。需要模型接续的用户动作应该进入已有会话 / 运行链，而不是组件直接启动任意命令。

ChangeLedger 的 rescue point 和操作 journal 对未来撤销有价值。但恢复整目录与撤销本轮已记录修改不同，多会话共享原目录时尤其如此。实施前要确定具体恢复范围；不能因存在历史快照就承诺不会覆盖其他任务成果。

## 10. 社区演化路径带来的排序

| 观察到的演化 | 暴露的实际问题 | 本项目应先吸收什么 |
| --- | --- | --- |
| 小插件 → 完整工作台 | 多入口资源归属、卸载和重启 | 现有资源与运行身份关联、恢复入口 |
| prompt 拼接 → 上下文投影 | 日志不等于模型实际输入 | 来源解释和可回查的材料视图 |
| 单次 worker → 持续 Team | 改派、迟到结果、空闲与完成混淆 | 先检查现有 run / worker 结果关联 |
| 手动记忆 → 自动 capture / evolution | 错误放大、冲突、来源与版本 | 纠错和范围透明、候选 / 生效分开 |
| 一次安装 → 市场 / 配置管理 | 装错 profile、升级失败、宿主起不来 | 准确来源身份、生效状态、可恢复配置 |
| 自由文本流程 → 状态机 / 调度器 | 规则过强、额外调用、重复副作用 | 仅为已出现的稳定场景增加执行结构 |

较近的参考重点是上下文与成果来源、协作结果归属、Skill 生效版本和资源安装状态。中期按实际需求考虑恢复点、有限交互成果、持续成员或可执行工作流。多引擎切换、外部记忆数据库、运行时自注入和完整插件市场，当前没有足够需求依据直接引入。

## 11. 如何把研究变成下一次可实施任务

选定一个用户可感知的问题即可，例如“协作回复看不到源运行”“长会话不清楚哪些材料被压缩”“Skill 更新后不知道本轮是否生效”。先检查对应现有代码和近期改动，再为这个问题确定最小增量。

上游测试、作者实验和本次静态阅读都不是本项目的验证证据。后续验证只覆盖实际变更及其关键风险；不因为研究提到评测、RSI 或 gate 就自动新增一套常驻审查流程。当前默认原目录、本机执行、固定模型范围、真实故障停止、最小报告和按授权直接推进的约定继续适用。
