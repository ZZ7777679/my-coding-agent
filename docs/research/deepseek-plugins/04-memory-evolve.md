# dsh-memory-evolve：从持久记忆扩展到技能与会话协作

> 核查日期：2026-09-23。仓库 `csyangwen/dsh-memory-evolve`，固定提交 `c337dc1af7b5c8a5578e03150bf5c4d6133f66f9`，清单版本 0.1.0、MIT。主线功能明显多于这个包号能表达的范围，本文以提交为准；未安装或实测。

## 1. 先理解“evolve”究竟改变什么

该项目最初解决跨会话记忆，当前已经包含待办、技能管理、会话编排、广播、外部 Agent 派单、项目记忆同步及多种界面。它值得研究，因为展现了一个插件如何逐渐成为工作台；也值得警惕，因为“记忆插件”这个名字已不能准确反映其运行面。

这里的自进化主要是外部记忆与 Skill 内容的更新。它没有证明模型权重会改善，也没有仅凭名字就构成递归自我改进 RSI。判断 RSI 需要继续追问：是否修改改进器自身、是否有独立评价、是否选择并保留有效变体，而不是只看是否会写 SKILL.md。

## 2. 仓库的真实组织

Host 逻辑主要在 `lib/` 的 JavaScript，不应因目录名叫 lib 就完全跳过。`index.js` 装配服务和快照；`store.js` 处理记忆文件；`review.js` 管回合审查和候选；`skills.js` 管 Skill 写入；`session-orch.js`、`coi/` 管内部和外部协作；`sync/` 管跨设备同步。浏览器交互另外在 `src/client/`，脚本负责构建和同步 worker。

好处是每个扩展仍通过宿主服务装配，不需要改 AgentLoop。代价是 index 已经承担大量开关、注册与配置协调；必需 inject 包含 tools、systemPrompt、agents、sessionTitle、sessionPersistence、settings、llm，某个必需服务变化会影响比记忆更大的能力集合。[入口](https://github.com/csyangwen/dsh-memory-evolve/blob/c337dc1af7b5c8a5578e03150bf5c4d6133f66f9/lib/index.js)

## 3. 新会话怎样拿到记忆

插件不是每步把所有历史重新发送。它注册名为 `memory:snapshot` 的 systemPrompt context，渲染当前会话对应的记忆、项目 / 分支信息和工作提示。Host 把变化的 context 作为追加材料处理，稳定部分有机会保持前缀复用。

这里有两种不同的状态：

- **用户 / 策展后的记忆**：保存长期事实和偏好，是后续快照的来源。
- **学习候选**：放入 `SUGGESTIONS.jsonl`，附带目标、内容、理由及重复次数，等待接受或按配置处理。

候选不应因为进入队列就自动被视为用户确定的事实。项目当前有更多 daily / project 等分轨；“五轨”等命名用于组织数据，不代表五套独立学习模型。若同步模块基于仓库远端识别项目，也必须区分同仓库多个分支的工作状态与真正跨项目共享的个人偏好。

## 4. 一条记忆写入怎样避免覆盖其他修改

`store.js` 使用 `\n§\n` 分隔条目，为条目提供稳定身份，并以目录锁串行化同类写入。写入经临时文件与 rename；解析后若不能无损还原磁盘内容，drift guard 拒绝整个文件重写，防止把人工编辑或外部 append 丢掉。

这比“存 Markdown”更关键：纯文本方便检查，但解析器升级、同步合并和人工编辑会改变 round-trip 条件。锁只协调遵守相同协议的写者；外部编辑器并不会自动获取此锁。源码采用同步 I/O 和按时间判断陈旧锁，适用于小文件假设，不应把它描述成任意规模、多机并发的数据库保证。[存储实现](https://github.com/csyangwen/dsh-memory-evolve/blob/c337dc1af7b5c8a5578e03150bf5c4d6133f66f9/lib/store.js)

## 5. 回合结束后，审查是怎样触发的

源码的 `reviewTurnCounter()` 按会话记录已完成用户回合，使用实际的 `agent/turn-stopping` 接缝。注释保留了一个有价值的修正：早先监听 `agent/settled`，但宿主并不发送该事件，功能会表现为“配置开着却永远不工作”。

审查默认关闭；开启后主要由主模型按提示检查 `memory_review_status`，到达间隔再反思，而不是每次都额外唤起一个后台评审模型。suggest 模式写候选，同内容候选合并并增加 hits；auto 模式允许直接写入。另有未记录 daily / project 的回合计数器用于提醒。

因此应准确说它提供了“回合计数 + 提示驱动审查 + 工具写回”的机制。反思是否全面、是否重复写入、是否把偶然情况归纳成长期事实，仍取决于模型和配置，源码本身不能证明越用越好。[审查实现](https://github.com/csyangwen/dsh-memory-evolve/blob/c337dc1af7b5c8a5578e03150bf5c4d6133f66f9/lib/review.js)

## 6. 技能改写怎样进入循环

`skill_manage` 可以创建、读取和修改 Skill。创建要求合法名称与 frontmatter；patch 检查调用者自己的会话中存在对目标 Skill 的读取记录，再进行内容替换。技能禁用状态从共享 registry 读取，避免每个插件各自维护启用列表。

这是可落地的“经验程序化”：重复解决某问题后，把步骤存成以后可加载的 Skill。但“之前读过”不能证明“新版本更好”；它也不是我们项目文件工具应新增的通用先读硬门槛。本项目用户已经选择在写边界唯一匹配并检查变化，不能照搬这里的额外限制。

更完整的进化机制应保存候选版本、来源任务和结果，并通过少量代表任务比较后再决定是否提升；失败版本可回退。当前已读实现主要证明创建 / 修改与候选流程，没有给出独立评估驱动的长期收益曲线。[技能实现](https://github.com/csyangwen/dsh-memory-evolve/blob/c337dc1af7b5c8a5578e03150bf5c4d6133f66f9/lib/skills.js)

## 7. 从记忆到协作，哪些耦合开始出现

记忆可以做协作的资料层，却不应替代任务所有权。项目提供会话编排和广播，能让不同会话共享结论；但一条“已完成”的记忆不等于所属 Run 已完成，分支相关记录也不等于文件已经合并。

跨设备同步又引入新的身份问题：条目需要稳定 id，冲突需要保留双方版本，删除需要明确传播语义；不能仅同步一个最终 MEMORY.md 后按最后写入者覆盖。当前指南提供采用本机、远端或两者的冲突处理，这更接近可维护知识库，而不是模型自动达成一致。

## 8. 对本项目的参考

优先参考候选与已接受记忆分开、来源任务可回查、稳定条目标识、变化后再注入，以及记忆 / Skill 同步保留冲突。现有记忆纠错和 Skill 归档可以承接这些能力，不需要一次性引入它的待办、远程派单和全部 UI。

不建议直接采用每轮写记忆的压力提示、额外先读门槛、自动改写所有技能或自动调用外部模型。需要提升的是知识质量与可追溯性；记录条数、反思次数、Skill 数量均不能代替结果质量。
