# 上下文工程与代码检索：让 Agent 在正确的时刻看到正确证据

> 调研与访问截止：2026-09-16。覆盖输入组织、代码定位、结构索引、GraphRAG、检索子 agent、RLM、压缩与缓存。源码核查包括 Aider repo map 的关键路径，未安装或运行第三方系统。关联：[记忆](01-memory.md)、[推理模式](07-reasoning-modes.md)、[评测](09-evaluation-observability.md)。

## 1. 从“模型没看懂项目”拆出真正的问题

用户报告“取消导出后仍生成文件”。Agent 搜索 cancel，读到前端按钮，于是修改界面状态；实际上后台进程根本没收到取消。模型并非一定缺乏推理能力，它可能缺少关键文件，或者被大量无关片段引向了错误前提。

上下文工程研究的是：一次模型调用应看到哪些指令、任务事实、代码、历史、工具描述和执行结果；哪些内容留在外部，怎样按需取回，内容变化后如何失效。它覆盖整个运行过程，不只是把 system prompt 写得更长。Anthropic 2025-09 的工程文章将其描述为对有限上下文的持续组织，并讨论按需访问、压缩、笔记和子 agent。[原始材料](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

本文的取消缺陷是自拟例子。一个完整证据链可能跨越 UI、RPC、任务控制、进程和文件写入；找出包含关键词的一个文件只是起点。读者应始终追问：当前信息足以支持哪个判断，还不能支持哪个判断。

## 2. 几个经常混用的概念

| 概念 | 负责什么 | 典型结果 | 无法单独保证什么 |
| --- | --- | --- | --- |
| 长期记忆 | 跨任务保存事实和经验 | 记录、知识页、可复用策略 | 当前调用会看到或正确使用它 |
| 检索 | 从候选资料中找相关内容 | 文件、片段、来源引用 | 结论正确、资料最新 |
| 上下文组装 | 在预算内选择和组织输入 | 一次实际模型请求 | 模型必然遵循全部约束 |
| 压缩 | 用更短表示承接已有信息 | 摘要、任务状态、证据指针 | 无损保留全部细节 |
| Prompt cache | 复用部分输入计算 | 更低重复计算成本或时延 | 业务记忆、事实更新 |
| 代码结构索引 | 描述定义、引用、依赖 | 符号表、图、repo map | 完整理解动态行为 |

大上下文窗口扩大可容纳量，但不自动解决选择和冲突。检索率高也未必更好：加入太多相似却不适用的片段，会增加模型判断负担。需要同时考虑覆盖、精度、当前性和总成本。

## 3. 发展路线与当前重点

早期 RAG 将外部文档检索后放入生成上下文；代码助手进一步需要按函数、符号、依赖和版本组织内容。Aider 的 repo map 展示了结构摘要路线；GraphRAG 研究全库主题与关系综合；agentic search 通过多步工具探索追踪未知路径；2025–2026 的检索子 agent 和 RLM 则把部分信息处理移出主上下文。

| 材料 | 时间或版本依据 | 本轮关注点 |
| --- | --- | --- |
| [Lost in the Middle](https://arxiv.org/abs/2307.03172) | 2023 年论文 | 位置和输入组织会影响使用信息的能力；结果有模型与任务条件 |
| [Aider repo map](https://aider.chat/docs/repomap.html) | 访问日文档与源码 | 用符号和关系形成有预算的仓库视图 |
| [Microsoft GraphRAG](https://microsoft.github.io/graphrag/) | 访问日官方文档 | 将局部实体查询与全局主题综合分开 |
| [Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 2025-09-29 | 持续整理输入，按需加载和长任务接续 |
| [SWE-grep / Fast Context](https://cognition.com/blog/swe-grep) | 2025-10-16 | 为代码检索训练专用、并行的子 agent |
| [RLM](https://arxiv.org/abs/2512.24601) | 2025-12 首版、2026-05 修订 | 外部输入、程序访问与递归语义处理 |
| [Deep Agents 动态子 agent](https://www.langchain.com/blog/introducing-dynamic-subagents-in-deep-agents) | 2026-06-29 | 用程序确定覆盖范围，隔离子任务上下文 |
| [Fusion Desktop / CLI](https://cognition.com/blog/local-fusion) | 2026-09-11 | 持续的多主体上下文与交接成本，详见 coding agent 专题 |

新方法并未使 grep 或读取文件失去价值。它们主要改变如何选择查询、并行收集和综合证据。判断方案时应比较工作负载，而不是将“向量”“图”“递归”当作越来越高级的标签。

## 4. 一个可实施的上下文管线

```mermaid
flowchart LR
  T[当前目标与已确认约束] --> Q[形成信息需求]
  Q --> R[关键词 结构 语义或 Agent 检索]
  R --> F[范围 版本 权限过滤]
  F --> D[去重与证据关联]
  D --> B[预算内组装]
  B --> M[模型判断与行动]
  M --> O[新观察]
  O --> Q
  O --> S[任务事实与外部产物]
```

### 4.1 先定义信息需求

“搜一下取消”过于宽泛。更好的信息需求是：取消请求从 UI 发向哪里；后端怎样关联运行；执行器持有哪些子进程句柄；取消后怎样处理输出文件。它把查询与待证明的因果链关联起来。

第一轮不必知道所有路径。搜索命中可以生成下一轮查询：读到 cancel_run 后查其实现和调用方；读到 worker_id 后查映射和生命周期。检索因此是迭代过程，而不是一次 top-k 就结束。

### 4.2 内容单元与来源元数据

固定长度切块简单，但可能将函数声明和关键分支切开。语法单元切块更适合代码，却仍需处理超长函数、跨文件类型和动态注册。可以保留定义块、周围结构与按需扩展入口，而不是试图让每个块独立解释全部程序。

每个片段至少应带项目、路径、版本或内容 hash、行范围、读取时间和截断状态。模型生成的摘要要链接回原文。若后续编辑基于旧片段，需要重新读取当前基线，不能把检索缓存直接当可写文件内容。

### 4.3 排序与上下文预算

相关性可以来自字面命中、语义相似、符号关联、当前文件邻接和历史经验。不同分数未必同尺度，不能简单把 cosine similarity 与关键词分数直接相加。常见工程方法是分别召回，再做统一排序或秩融合，并保留各自来源。

预算应先给不可丢失的目标、限制和执行事实，再给最能减少当前不确定性的证据。无需每轮重复加载所有参考资料；大工具输出可以保存在产物中，提供摘要和访问指针。对未显示部分要明确标记，避免模型将截断当成不存在。

## 5. Aider Repo Map：结构化仓库摘要怎样产生

### 5.1 它不是把 README 缩短

Aider 的 repo map 提供文件和重要符号的紧凑视图，帮助模型知道未完整载入文件的大致接口，并在 token 预算中选择内容。[官方说明](https://aider.chat/docs/repomap.html)

源码中可以核实三段关键路径：get_tags_raw 使用语法解析提取定义和引用；get_ranked_tags 建立加权关系并运行 PageRank；后续将排名结果整理成有预算的地图，缓存与文件状态关联。[repomap.py](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/repomap.py)

它的输出不是完整代码理解结果，而是一张“值得进一步读取哪里”的地图。用户已提及的文件或标识符会影响排序，因此地图可以随当前对话变化，而不只是固定全仓摘要。

### 5.2 用取消链路解释收益

假设 UI 文件引用 CancelRequest，后端 handler 引用 TaskRunner，TaskRunner 使用 ProcessHandle。即使用户没有说出这些名称，定义和引用关系也能帮助把相关接口放到地图中。模型接着读取关键函数正文，确认取消怎样传播。

这比把所有文件目录列出来多提供结构，也比直接塞完整仓库便宜。但是关系排名容易偏向被广泛引用的中心模块，一个只在边界条件触发的稀有分支可能很重要却排名不高。因此地图应与问题导向搜索结合。

### 5.3 实现边界和成本

语法解析受语言支持和代码可解析性影响；字符串注册、反射和生成代码可能无法形成完整引用关系。源码中的符号关系不能视为编译器已经解析全部真实调用目标。名字相同的多个定义也会增加歧义。

维护成本来自首次扫描、增量更新、缓存失效与多分支工作区。每次构建都全量重扫会拖慢交互；过度缓存又会返回旧符号。采用前应测首次与热查询成本，并使用真正需要跨文件定位的任务评价地图价值。

## 6. GraphRAG：什么时候需要全局综合，什么时候只要局部检索

### 6.1 基本结构

GraphRAG 索引阶段从语料组织实体、关系及更高层的社区报告，查询阶段提供不同策略。Local Search 结合相关图信息和原文片段；Global Search 对社区报告做分阶段综合；DRIFT 将社区信息用于拓展局部查询；Basic Search 提供向量检索对照。[索引入口](https://microsoft.github.io/graphrag/index/overview/)、[查询策略](https://microsoft.github.io/graphrag/query/overview/)

“社区”在这里是图中关联较密集的一组对象，不是互联网用户社区。社区报告提供预先整理的主题级信息，适合回答整个资料库有哪些主要趋势。这与“某函数在哪个文件”有不同的信息需求。

### 6.2 用工程资料库比较两种问题

问题 A：“取消按钮调用哪个后端函数？”通常沿符号与局部代码即可解决，构建全库社区报告成本可能过高。

问题 B：“过去一年取消相关事故主要集中在哪些架构边界？”需要综合多个 issue、日志、设计文档和改动。关键词片段 top-k 可能只覆盖最相似几次事故，缺少全局分布；图关系与主题报告可以提供更广的候选视图，再回读原始材料验证。

问题 C：“某个客户案例中的超时，是否与平台取消机制有关？”可能先从客户和事故实体局部检索，再沿共同模块扩展。GraphRAG Local Search 文档展示的思路是将关联信息与源文本一起组织，而不是只返回没有证据的图三元组。[Local Search](https://microsoft.github.io/graphrag/query/local_search/)

### 6.3 为什么图不会自动变成事实

实体和关系往往由模型抽取，错误可能在索引阶段固化。将两个同名服务合并，会制造虚假的跨项目关联；社区摘要遗漏时间条件，会让历史事故看似仍普遍存在。图的每条重要结论仍应能追溯到原文和版本。

它与 Graphiti 的侧重点不同：本篇 GraphRAG 面向资料库检索和综合；记忆篇 Graphiti 强调持续事件、实体关系与时间有效性。两者都有图，但不能据名称相似互换数据模型或部署承诺。

适用判断要包含入库成本、更新频率、查询类型和复用次数。频繁变化的小型代码库不一定值得维护复杂图索引；跨大量稳定文档的重复综合更可能获得收益。

## 7. Agentic Search 与检索子 Agent：把探索留在子上下文

Agentic Search 通过搜索、读取和继续追踪来找证据，适应未知命名与路径。它的代价是多次串行请求，以及主模型看过大量最终无用的内容。专门检索子 agent 可以保留探索过程，只向主 agent 返回文件和证据范围。

Cognition 的 SWE-grep 工作以文件和行范围为结果，使用受限搜索工具、并行调用及专门训练优化检索；其公开材料将质量和端到端延迟一起评价，并说明演示不等同严格基准。[2025-10 工程与训练说明](https://cognition.com/blog/swe-grep)

值得借鉴的是接口选择：返回“这些文件的这些位置相关”，比返回一份不可核对的长总结更容易评估。主 agent 可以自己读取并解释原文，降低子模型错误概括的传播。它也让检索任务有较客观的标签，例如是否找到真实相关位置。

不过只追求精度可能遗漏跨文件隐含关系，只追求召回则可能塞入大量噪声。实际应观察下游修复质量，而不只看检索分数。检索器若只根据标准答案附近行训练，也可能对真实开放问题泛化不足。

针对取消例子，检索子 agent 应返回 UI 发起点、RPC 接收点、任务关联和进程执行处，并明确尚未找到文件清理逻辑。把缺口列出来，比编造一条完整调用链更有用。

## 8. RLM：把大输入变成可操作环境

### 8.1 与“切块后分别总结”的区别

Recursive Language Models 将长输入放在外部环境，根模型通过程序查看结构、过滤、切片，必要时调用模型处理局部内容，再汇合结果。输入不必一次进入根提示。原论文与公开实现研究了这种递归访问方式。[论文](https://arxiv.org/abs/2512.24601)、[官方实现](https://github.com/alexzhang13/rlm)

固定切块总结通常预先决定每块都要处理；RLM 式访问可以根据中间结果决定下一步看什么。处理百万行日志时，先程序筛选运行 ID 和时间窗，再对异常片段做语义判断，可能比对所有块都调用模型更经济。

### 8.2 一次教学运行

根调用先检查日志字段和时间范围，发现同一 run ID 出现两个输出路径；程序提取这两个路径相关记录；子调用分别分析取消前后进程状态；根调用比较时间线，发现取消仅结束前台等待。随后回到代码检索，定位执行器。

在这个过程中，程序适合精确计数和筛选，子模型适合解释局部日志，根模型负责跨片段因果判断。任何一层都可能出错：筛选条件漏掉别名，子模型误读时间，根模型把相关性当因果。因此中间结果必须带原文定位和不确定性。

### 8.3 运行时才是落地难点

当前 RLM 仓库同时提供本地及隔离环境，默认 LocalREPL 在宿主进程执行；Docker 等后端另有模型调用桥接、递归调用和会话状态支持。不能因为名称含 REPL 就宣称执行已隔离。[实现说明](https://github.com/alexzhang13/rlm#repl-environments)

实际应用需要限制递归深度、累计子调用、总费用、输出体积和并发；还要决定中断后哪些变量可恢复、哪些外部动作已经发生。父调用超时不能只抛弃孩子的句柄，让它们继续收费或写文件。

这条路线适合输入很大且可程序化访问的分析任务，不保证对每个小问题更快。它的递归是求解和上下文访问，并不自动构成[RSI](03-self-evolution.md)。

## 9. 压缩与交接：保留继续工作的依据

### 9.1 摘要为何容易丢失关键内容

普通摘要偏向已经发生的主线，可能删去一个看似次要但仍约束实现的用户要求。对长期开发，“不要覆盖旧文件”“不改变 provider”“某检查尚未运行”可能比过程叙述更重要。

因此任务交接应有明确字段：当前目标、已确认约束、已完成及证据、未完成、已排除假设、环境事实、产物指针和下一步。已排除假设要保留适用条件，避免新会话重新做相同排查，也避免将旧排除结论无限延用。

### 9.2 分层压缩比一次性总结更可控

最近工具结果可以保留原文；较旧过程压缩为事实与指针；稳定项目知识进入可审查记忆；任务状态单独维护。需要细节时回读证据。这样既不让全部历史占满输入，也不要求摘要承担所有真实性。

压缩应记录使用了哪些输入版本、何时产生和哪些部分未覆盖。多个来源冲突时保留冲突，不为了形成顺畅故事擅自选边。压缩后的内容仍然是派生表示，不能获得高于原始用户要求的权威。

### 9.3 子 Agent 交接的最小包

给实现子 agent 的输入应有目标、必要接口、约束、工作区身份和完成判据；返回应有产物、验证、未解决事项和关键发现。历史应按角色选择：独立研究与审查通常适合较小、独立的输入；接续已经完成的诊断可以继承父上下文。不能把“只传简短任务”和“复制全部历史”中的任何一种写成所有角色的统一最优解。

主 agent 必须处理孩子的新发现。例如子任务发现公共接口缺陷可能影响其他任务，不能只将它写在最终长总结里。通信应允许关键发现及时上报并更新共享目标事实。

### 9.4 2026-09 的具体变化：Fork 与 Isolated 应当按职责选

LangChain 在 2026-09-08 介绍 Deep Agents 的两种子上下文模式：`isolated` 从分派任务开始，`fork` 继承父会话再追加子任务，最终把子 Agent 结果收回为工具结果。当前 Python 文档注明 fork 需要 `deepagents>=0.7.13`，仍属 beta；不能将文章里的跨语言示例直接当作任意已安装版本都支持的接口。[工程说明](https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness)、[当前接口与限制](https://docs.langchain.com/oss/python/deepagents/subagents)

**自拟例子**：父 Agent 已经读过五个模块，确定一个缺陷来自事件归属错误。如果实施者只收到“修复迟到响应”，它要重复定位，而且可能漏掉已确认的兼容约束；继承现有诊断更有价值。相反，让审查者继承“原因已经确定、方案没有风险”的整段诊断，可能把待验证假设变成心理锚点。审查输入更适合包含需求、基线、补丁和验证记录，让它自行建立判断。

由此可以把上下文分成三层：**双方必须共享的事实、工作者可以继承的探索历史、审查者应独立验证的假设**。上下文隔离并不意味着不能共享需求；完整继承也不意味着父 Agent 的每项判断自动升级为事实。若缺少这一区分，多 Agent 可能只是增加相同偏差的副本。

Fork 还不能被解释为工作区快照。父子看到的历史可以相同，磁盘却可能被另一个任务更新；继承的“刚读过文件”需要关联文件版本。缓存收益同样有条件：系统提示、工具定义与 provider 缓存支持都会影响实际复用，不能仅凭 `fork` 标签承诺更便宜。当前能力在 [Harness 专题](06-harness.md) 中与 backend 和持久化一起分析。

## 10. 缓存、延迟与成本：不是只减少 token

上下文组织还影响前缀缓存。稳定规则和工具描述可形成较稳定前缀，频繁变化的日志放在后部通常更利于复用；具体缓存行为依 provider 实现，不能据通用经验承诺命中或费用。业务正确性优先：过期约束不能为了缓存而保留。

总延迟包含检索、网络往返、模型预处理、生成、工具执行和汇合。减少输入可能同时增加检索调用；并行降低等待却增加总消耗；预建索引加速查询但增加首次和维护成本。应分别记录冷启动、热查询与完整任务时间。

一个有解释力的对照是同一缺陷集使用：直接 grep / read、repo map 加搜索、混合检索、检索子 agent。固定模型和预算，观察定位正确性、无效阅读量、首次有效动作时间、总成本和最终修复质量。只有检索变快而任务没有改善，也是一项需要解释的结果。

## 11. 社区争论、证据限制与采用判断

“不用向量检索也能做 coding agent”和“只靠 grep 不能覆盖大型知识库”可以同时成立：前者针对可交互探索的代码环境，后者针对跨大量资料的语义综合。检索方法应由问题决定。

“上下文越短越聪明”也过于绝对。丢掉必要证据会直接降低正确性；目标是保留高价值信息、减少无关与冲突内容。旧长上下文实验的结果不能不加条件地推广到所有新模型。[Lost in the Middle](https://arxiv.org/abs/2307.03172)

本轮补查已经读取 Manus 原文，相关分析见下节，替代此前“正文访问失败”的限制。Aider 检查到关键源码路径，GraphRAG 和 RLM 主要核对官方结构及接口，没有声称完成全仓源码审计。这些证据深度差异应在选型时保留。

本项目可先从现有 list_files、search、read_file 改善证据定位、截断提示和版本关联；任务层保存稳定目标与约束；真实跨文件定位困难出现后再比较结构索引或检索子 agent。研究并不授权立即增加向量库、图数据库、递归运行时或新模型。

## 12. Manus：缓存、可回读资料和错误证据怎样共同影响运行

2025-07-18 的 Manus 工程文章提出稳定前缀、文件外置上下文、保留失败证据和周期性重述任务目标等经验；工具可用性还通过状态约束控制。这里分析其机制，不引用旧模型价格作为当前价格，也不把该文描述成 2026 年新增功能。[官方原文](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

这些经验对应三种不同成本。模型每一步需要处理已有输入，所以稳定输入有利于缓存；长观察占据工作窗口，所以外置文件有利于后续按需读取；错误被抹除会诱发重复尝试，所以压缩不能只保留顺畅的成功叙事。它们共同作用于“下一步能够依据什么作决定”，不能分别退化为“少发 token”“多写文件”“多写总结”。

**教学推演**：Agent 读取一份很长的 API 文档，可以先保存原始版本，给当前上下文留下适用版本、关键约束和定位指针。后面遇到字段歧义时回读原文。如果只留下可变化的网页 URL，就没有保证还能读到同一版本；如果文件随临时环境销毁，所谓外置记忆也已经消失。因此工程落地需要来源快照、生命周期和访问权限，不能只增加一个文件工具。

对失败也应做结构化保留。例如一次构建失败与一次授权拒绝会导致不同下一步：前者可以产生最小修复，后者不能通过换工具重做同一动作。适合压缩的是冗余日志，必须保留的是错误类别、触发条件、已尝试动作和观察结果。这能让错误成为控制信号，避免完整堆栈长期挤占窗口。

原文的工具约束经验还需要放回当时的接口条件理解。今天的延迟发现、程序化调用与模型原生工具机制并不相同。实际选择应测量工具发现召回率、缓存命中、schema 错误和完整任务成本；不能从一家厂商的局部最优，推出所有宿主都应永久禁止动态工具加载。能力组织的比较见 [02](02-skills-tools-mcp.md)。

## 13. OpenWiki：把代码知识的陈旧问题放进更新流程

2026-09-10 的 Credit Genie 案例补充了 LLM Wiki 之外的产品实践：团队使用 LangChain OpenWiki，按代码变更更新仓库内的 `openwiki/` 文档，并聚合为面向人的查询入口；Coding Agent 也读取同一份仓库知识。案例描述了定时检查、生成更新 PR 和自动维护流程，跨仓库关系增强则仍是下一步方向。它是厂商发布的客户案例，没有随机对照的生产率证据。[案例原文](https://www.langchain.com/blog/how-credit-genie-uses-openwiki-to-keep-codebase-knowledge-fresh-searchable-and-automated)

**架构分析**：代码是原始事实，Wiki 是可重建的派生视图，门户是检索与阅读入口。三者需要不同版本：源码 commit、文档生成版本、门户索引版本。只记录“昨晚任务成功”并不能证明当前页面与最新代码一致，因为生成、合并和重新索引可能分别失败。

例如一次函数重命名同时影响 API 文档和两篇教程。可靠更新至少应知道哪些页面引用旧符号、哪些页面本轮已检查、哪些例子仍未验证。若只重新生成主 README，搜索排名很高的旧教程仍会误导人和 Agent；若全部重生成，又可能扩大无关差异并抹掉人工解释。这使增量依赖、来源定位和人工内容的保留策略成为核心实现问题。

它与 [LLM Wiki](01-memory.md) 的共同点是知识需要维护，不是一次索引即可完成；区别在于这里的主要触发源是仓库变更，交付通道是工程工作流。这个模式适合跨团队理解代码和入职学习，但不应把客户的自动合并策略当作所有仓库默认：是否采用自动合并，取决于产物范围和现有审查约定。

## 14. OpenViking：从返回命中文档到组装可用上下文

### 14.1 为什么要在向量库之上增加文件系统语义

[OpenViking 架构](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/01-architecture.md) 将资源、记忆与技能放在统一上下文空间，以目录和 URI 组织访问。L0 摘要、L1 概览、L2 原文支持从粗到细读取；目录的 `.abstract.md`、`.overview.md` 是派生视图，不能理解为所有文件都强制同时具备三份内容。统一寻址减少不同 Agent 各自组织上下文的重复工作，但没有抹平三类对象的更新与授权差异。

例如研究一个支付模块，Agent 可以先读模块概览，定位重试与退款两个子目录，再读取相关实现。相比把整个仓库平铺成片段，这种组织保留了“片段属于哪个模块”的信息。代价是目录概览也会陈旧，需要知道它由哪批内容生成；目录结构差、摘要漏掉关键责任时，分层检索仍会沿错误路径深入。

### 14.2 当前 API 已把上下文预算放到服务端

[访问日的检索文档](https://github.com/volcengine/OpenViking/blob/main/docs/en/api/06-retrieval.md) 区分 `find` 与带意图分析的 `search`，并提供 `search(mode="context")` 的服务端组装流程：受限的查询扩展、按类别召回、预算内逐级填充、可选摘要与引用。超大的详细层可以退回较粗层，而非机械截断文本。当前 context 模式不支持 `target_uri`，不能把 list 模式的参数能力不加核对地复制过去。

以下是本研究对价值的推演。假设可用预算只能容纳 5,000 token，同时召回了一份详细设计、两条个人偏好和一个部署 skill。单纯按分数排序可能让详细设计占满预算，使关键限制完全消失。按类别先提供必要信息、再用剩余预算深化，有机会兼顾广度与精度；但类别配额也可能浪费预算，因此必须观察任务分布，而不是永久写死所有类别同样重要。

服务端统一组装还能让多个 harness 使用一致的降级策略。与此同时，返回结果应解释用了哪些来源、哪个详细层、哪些内容被排除；否则客户端只能看到一段“整理后的上下文”，无法判断遗漏是检索、预算还是摘要导致。

### 14.3 URI 不是版本，也不是可靠性的证明

[Viking URI 文档](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/04-viking-uri.md) 定义上下文地址与命名空间。地址解决“对象在哪里”，不自动回答“当时读的是哪个内容版本”。同一路径下文档被改写后，历史回答只有 URI 仍可能无法重现；地址派生的标识也不能当成内容校验值。

本研究建议同时记录来源地址、内容版本或摘要、提取时间和派生层版本。若摘要声称函数仍接受旧参数，而 L2 已修改，系统应优先呈现这种不一致。将内容挂入统一空间的落地价值是可管理、可遍历与可组合，最终事实仍需要回到适当版本的原始材料。

本轮阅读的是当前官方概念与 API 文档，记录了仓库 HEAD，未完成固定提交的检索源码审计或性能验证。具体延迟、检索收益与部署成本仍不能由结构设计直接推出。
