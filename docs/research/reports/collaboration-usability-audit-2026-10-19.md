# 协作空间、任务工作图的可落地性与运行约束审查

> 后续状态：R1–R6 与经核实的 DS 缺口已完成本轮修复，详见 [方案与用法](../../plan/collaboration-usability-fixes.md)、[M5 最终证据与剩余观察](../../progress/m5.md)。下文保留修复前的审查事实和行号，不代表当前行为。

日期：2026-10-19。基线：当前 `dev` 工作区，包含尚未提交的 M5 / 工作图实现及其复用的协作、Goal、文件工具。承接 [DS 评价源码核对](collaboration-ds-review-2026-10-19.md)，本轮进一步检查真实调用与编辑链路。

本轮是审查，未修改产品代码、协议、个人数据或系统配置，未提交 / 推送。新增一个隔离观察脚本，保存复现与桌面验证证据。用户追加的“生成后图是否还能编辑”已纳入范围。

## 1. 总体判断

底层已经能够执行真实的成员委派与结果回收。任务、成员、会话、工作定义、运行和报告分离的方向可以保留，当前没有必要推倒重建或另写图运行时。

**但还不足以作为顺畅、长期使用的合作空间交付。** 本轮确认了可修正协作错误导致整轮失败、只读 Review 接续模式变化、生成节点删除无效、图编辑能力不完整、长输入与累计存储容量阻塞等问题。此前的简短闭环证明了接线可用，没有覆盖这些日常操作和长期使用边界；“已有实现”不能替代“用户能够顺畅使用”。

DS 对接入不清、来源难查和生命周期体验的担忧有依据；其“没有 spawn、没有取消、没有冲突检查、必须粘贴 UUID、协作完全未落地”等判断仍不符合当前实现。细分事实见前一份核对，不因此补建重复系统。

## 2. 已确认问题，按修复优先级排列

### R1 · P1：尚未执行的协作调用错误，会终止整个 Run / Goal

- 触发：同任务两个会话已存在，但尚无协作约定；模型尝试 `request_collaboration`。
- 复现：工具返回 `COLLABORATION_NOT_LINKED`，只请求模型 **1 次**，普通 Run 直接变成 `failed / TOOL_FAILED`；Goal 场景中 Goal 同样变成 `failed`，没有机会把反馈交回模型解释或选择下一步。没有向接收方启动工作。
- 根因：[协作工具](../../../src/my_agent/collaboration/tools.py) 445 行把业务码原样作为工具错误返回；[运行循环](../../../src/my_agent/runtime/loop.py) 204、218 行通过固定可恢复错误名单决定是否停止，协作未安排 / 目标不属于当前范围 / 请求不存在等接纳前错误未列入。团队 `manage_space_work` 已把类似错误转为可修正反馈，两个入口行为不一致。
- 影响：探测能力或选错对象就会中断原任务，属于真实的过强停止约束。代码静态上其他同类错误也走此分支，本轮动态只复现“未建立约定”。
- 最小修正：让接纳前的可修正错误回到模型，同时保留“本次没有投递”的事实；实际模型、执行和保存故障继续按已有规则停止。复用现有失败分类，不自动代建约定、不自动重放请求、不新增审批。

### R2 · P1：工作图的只读 Review，在持续执行第二轮变为 Normal

- 触发：选择方法为 `review` 的工作节点并持续执行；首轮正常报告同一个审查工作仍需继续。
- 复现：真实 `RunAccepted.mode` 先后为 **`plan → normal`**。使用模型替身提交报告，没有执行文件修改。
- 根因：[工作图启动](../../../src/my_agent/spaces/work_graph.py) 221、253 行将 discuss / plan / review 都视为只读，并以 `method="plan"` 创建 Goal；[Goal 接续](../../../src/my_agent/goals/service.py) 548 行在选出工作项后，只判断 `work.method == "plan"`，`review` 因而落入 Normal。
- 影响：同一用户操作在不同轮次具备不同的工具执行能力；会影响用户对审查、讨论和实现的理解。尚未证明发生过实际越界写入，已证明接纳模式发生变化。
- 最小修正：统一方法与执行能力的映射，并保留用户启动该轮时的模式；节点切换不自行扩大执行范围。修正已有契约即可，无需再增加一层安全工作流。

### R3 · P2：生成的工作节点没有可靠的删除语义

- 界面：工作视角有“添加工作”，没有删除节点的入口。
- 后端复现：空间含一个 `initial_work_items` 生成节点。通过正式 `spaces.work_graph_save` 保存空 `items` 后，`planned_items` 确实为空，但返回的工作图仍含该节点。
- 根因：[work_items](../../../src/my_agent/spaces/work_graph.py) 28–31 行每次重新合并生成草稿、用户定义与报告；缺失于用户定义不表示删除。报告中存在的节点同样具有重新出现的代码路径，本轮动态验证的是生成节点。
- 影响：用户不能把生成结果收敛为自己想要的实际流程；“保存成功”与“图按编辑结果变化”不一致。
- 最小修正：生成草稿采用时进入任务工作定义，此后由任务定义负责当前节点集合；移除节点仍可保留报告和运行历史，但历史不能自动恢复为当前节点。兼容旧记录需明确一次性的采用方式，避免为此再建第二套图状态。

### R4 · P2：两种图的编辑体验割裂，普通修改会禁用相邻操作

| 操作 | 团队关系图 | 工作图 |
| --- | --- | --- |
| 移动节点 / 保存位置 | 支持，桌面复查已走通 | 明确禁用拖动，位置由每次排列计算 |
| 拖动创建连线 | 有 `onConnect` 接线 | 明确禁用连线；依赖 / 反馈在节点下方勾选 |
| 改成员或节点属性 | 点击后进入图下方表单 | 点击后进入图下方表单 |
| 移除关系 / 成员 | 支持，成员历史会话保留 | 关系通过勾选修改；没有删除工作节点入口 |
| 一次编辑标题、范围、负责人 | 团队草稿可统一保存 | 标题 / 范围变动产生草稿后，负责人下拉框被禁用，需先保存再分配 |

- [WorkGraphPanel](../../../apps/desktop/src/renderer/src/WorkGraphPanel.tsx) 418–419 行设置 `nodesDraggable={false}`、`nodesConnectable={false}`，512、565、580 行在有草稿时禁用负责人 / 状态保存。工作视角本质上是图形展示加表单编辑，尚不是直接图编辑器。
- [SpaceTemplates](../../../apps/desktop/src/renderer/src/SpaceTemplates.tsx) 184 行要求先“采用草稿到团队编辑区”；[SpacePanel](../../../apps/desktop/src/renderer/src/SpacePanel.tsx) 将群聊、图和下方属性表单串在长页面里。采用后没有明确选中生成节点并聚焦属性编辑器。已有真实截图中，工作图占一屏的大部分，属性与执行入口位于下方。
- 用户的感觉有依据：工作图确实不能直接拖动或连线；团队图并非生成后永久锁定，但生成 → 采用 → 编辑 → 保存 → 组建的状态与入口不够直观。
- 最小修正：统一选中节点后的就近属性编辑，增加明确的移动 / 连线 / 删除操作及未保存提示；负责人进入同一草稿，保存时一起提交。已绑定成员无需每次重新组建；新增成员仍由用户明确创建 / 绑定会话。工作历史不因删图而删除。

### R5 · P2：合法进入启动接口的长输入，在内部包装后被固定长度限制拒绝

- [StartWorkGraphParams](../../../src/my_agent/spaces/work_types.py) 的 `instruction` 是无长度限制的字符串；内部拼装提示词后传入 [SpaceChatParams / StartSpaceRoundParams](../../../src/my_agent/spaces/team_types.py) 的 `Description`，后者上限 16,000 字符。
- 复现：16,000 字符补充说明被外层接收，包装后在 `SpaceChatParams.content` 抛出 `ValidationError`，模型请求为零。失败前已执行 `stage()`：成员阶段从未绑定变为 `review`。因此启动失败却已改变后续上下文选择。
- 这是接口预算不一致和副作用顺序问题，不是模型上下文真的容纳不下。
- 最小修正：分清用户说明与内部执行材料，统一必要的输入预算，并在变更阶段前完成接纳条件检查。不要简单给外层再叠一个更短硬编码，也不静默截断用户说明。

### R6 · P2：增长中的群聊历史套用了固定 4 MiB 文档容量

- [SpaceTeamStore](../../../src/my_agent/spaces/team_store.py) 将所有群聊消息、轮次和生成记录保存到单个 `.chat.json`，借用 [storage.py](../../../src/my_agent/storage.py) 51 行的 `MAX_DOCUMENT_BYTES = 4 * 1024 * 1024`，超出后返回 `SPACE_CAPACITY`。尚无历史分页落盘或归档后继续追加的路径。
- 隔离复现：构造 100 条各 15,000 个中文字符的合法消息，累积保存被拒，旧文件保留。**这不是“100 条就固定失败”**，触发因素是累计编码大小；短消息需要更多条，轮次和生成记录也占容量。
- 影响：长任务最终可能无法再发群聊、创建轮次或保存相关状态，即使单条消息都正常。这一上限目前成了整个合作空间历史的容量上限。
- 最小修正：沿已有日志组织方式把增长历史拆为增量记录 / 分页，配置快照保持小；历史只读加载按需进行。无需换数据库，也不应仅把 4 MiB 改成更大的固定数掩盖问题。

## 3. 仍影响落地的体验缺口

这些有源码依据，但本轮没有把所有组合都做成新的回归测试。

1. **能力状态和接入入口不连贯。** `list_collaborators` 只返回已启用出向约定，空列表不说明当前任务 / 成员绑定情况。模型侧工具仍可见，但调用后才发现当前不可用。补统一的真实状态、成员名称 / 角色及下一步即可；UI 已可选会话，空间上下文也有成员身份，不需要新建另一套发现系统或允许模型偷偷创建正式会话。
2. **等待可用，但缺用户和模型都能理解的退出契约。** `wait=true` 有停止、插话、互等和目标受阻处理；活跃 Run 预算扣除被动等待，接口没有独立等待时长。目标忙时可能一直等待，模型也没有精确取消自己请求的工具。可增加可选等待时长，到期返回 pending，不宣告失败或取消对方工作；取消实际请求复用已有 UI / RPC 服务。
3. **多个长期 Goal 不等于可随时互相承接新工作。** 协作接收端正在运行或存在未结束 Goal 时，`_blocker` 保留原工作，新的独立委派排队；暂停、失败 Goal 不被协作恢复。不能把“给每个成员都开持续执行”描述成自由互相委派。当前更易落地的是协调成员持续推进，其他成员承接有限请求；普通补充可用 `send_peer_message`。未来若支持更多模式，应区分补充消息与新工作，不取消用户暂停、不自动越过真实失败。
4. **跨会话文件来源仍难查看。** 文件工具已保存来源且共享写入协调，`list_changes` 默认只展示本会话；缺按文件聚合任务内变更的入口。可直接投影已有记录，shell / 外部编辑造成的未知来源明确标记，不猜作者，也不加长期独占文件锁。
5. **长期历史读取可能变慢，尚未量测。** `chat_view` 为每条历史执行引用重复读取会话并遍历事实；`WorkGraphPanel` 与群聊事件刷新会再次取完整投影。建议先按同一会话去重读取、分页获取旧输出，随 R6 一起做最小处理。本轮没有性能测量，不给出虚构延迟或成员规模阈值。

## 4. 硬编码和过强约束的取舍

| 条件 | 审查结论 |
| --- | --- |
| 可恢复错误码名单遗漏协作接纳错误 | 确认会中断正常任务，优先修正分类；不是取消全部工具错误处理 |
| 图内用户输入叠加提示词后再受 16,000 字符上限限制 | 确认不一致，应对齐接口与材料组装，接纳失败前不改阶段 |
| 全部群聊历史共用固定 4 MiB 容量 | 确认不适合增长历史；拆分记录，不再以整个历史大小封死继续使用 |
| 工作图拖动 / 连线禁用，有草稿就禁用负责人 | 不影响底层代码执行，但阻断正常编辑步骤；应改善交互和草稿保存 |
| 双方同任务同项目、已有成员绑定 | 与既定任务归属和不自动创建正式会话一致，保留；让状态与显式接入更容易使用 |
| 同一会话已有 Run 时不另起第二个 Run | 保留单会话执行语义；使用可解释的排队 / 补充消息，而不是重复启动 |
| 实际失败后停止、暂停 Goal 不被自动恢复 | 用户已明确的产品规则，保留；接纳前反馈不应被误归类为实际执行失败 |
| 文件唯一匹配、写入前内容冲突、稳定身份 / 保存冲突 | 保留其实际用途，不恢复模型 hash 回传、反复读取或逐工具审批 |
| worker 开关、并发配置、现有请求 / 工具预算 | 不是“功能未实现”；并发可调，Goal 累计预算可空。说明状态，不新增固定深度 |
| 分页长度、布局间距、节点展示列数 | 不等于业务门槛，不机械删除；布局应允许用户编辑而不是影响运行 |
| 反馈成环、依赖未完、没有报告、证据字段不完整 | 当前图不以这些条件强制禁止普通执行；不建议添加无环、强制报告 / 结果 schema、评分或文件占用门槛 |

没有在本批协作 / 工作图主链路发现个人仓库绝对路径、强制远端 Git、必须 worktree 或新增模型 hash 门槛。这里只覆盖相关模块，不声明全仓不存在这些问题。

## 6. 建议的最小修复顺序

1. 先修 R1、R2：避免接纳前小错误杀死原任务，保持同一工作轮次模式一致。
2. 以“生成 → 修改 → 删除 → 保存 → 再次修改 → 执行”为主体验，统一工作图编辑并修 R3 / R4；保留团队图现有能力和历史记录。
3. 修 R5 / R6：对齐输入与内部材料的预算，把增长历史从小配置文档分开。
4. 补真实能力状态、等待 / 取消和按文件来源汇总；复用现有 task、report、handoff、Run、Goal 和投递服务。
5. 定向复核上述触发条件，更新失效的桌面定位，再用一个两成员小任务检查实际闭环；不以全量回归或新的审批系统作为实现前置条件。

以上是审查建议，本轮未开始修复产品；当前实现的既有验收历史保留，但不能据此忽略这份审查列出的缺陷。
