## R1 · P1：普通规模正则搜索会触发全局后端超时

**位置**：[read_only.py](../../../src/my_agent/tools/read_only.py#L293) 的逐文件 `_regex_lines`；[m5.ts](../../../apps/desktop/src/main/m5.ts#L127) 的默认 RPC 调用；[backend.ts](../../../apps/desktop/src/main/backend.ts#L300) 的超时处理。

正则先用 rg 批量筛选文件，随后每个候选又单独启动一次 rg 获取行号。默认返回 100 条时仍可能启动约 100 个额外进程。`documents.search` 沿用 8 秒普通请求时限；超时调用 `fail()`，结束所有 pending 请求并终止整个 Python 后端，而非只结束这次搜索。

**实证**：201 个仅两行的 Python 文件，查询 `^def\s+`、`regex=true`、`limit=100`。直接后端搜索耗时 **11.507 秒**，返回 100 条并正确标记截断。通过现有真实 Electron 构建的 preload → IPC → RPC 调用同一查询，**8.032 秒返回 `BACKEND_TIMEOUT`**；紧接着 `listProjects()` 也返回同一错误，必须重新打开应用。

**建议**：由一轮或少量批量 rg 同时返回文件、行号和匹配信息，避免每候选启动进程；搜索应有独立的运行 / 取消边界，并避免单次搜索耗时使整个后端失效。只放大 8 秒数字无法处理普通队列被长搜索占用的情况。

证据：`.artifacts/tests/search-git-review-_yjht4la/report.json`；`.artifacts/tests/search-argument-review-6natgh2v/desktop-search-report.json`、`desktop-search.png`。桌面实验使用真实现有构建与 201 个隔离文件，没有注入慢搜索。

## R2 · P1：Git 移动仍可间接堵塞普通 RPC，导致无关请求超时

**位置**：[LocalGitService.status](../../../src/my_agent/local_git/service.py#L303)、[transport.py](../../../src/my_agent/rpc/transport.py#L177)、[LocalGitPanel.tsx](../../../apps/desktop/src/renderer/src/LocalGitPanel.tsx#L57)。

`git.configure` 虽放入辅助任务且取消了自己的短超时，但移动期间持有项目锁。`git.status` 等待同一个锁，并仍在串行普通控制队列中执行。移动过程中折叠再展开 Git 面板、切走再回来，都会再次读取状态；它后面的 `git.settings`、项目列表等请求被连带阻塞。其中仍有 8 秒超时的请求，最终会触发全局后端失败，甚至打断尚未完成的移动。

**实证**：以真实 `run_transport`、项目锁和 Git 设置服务执行隔离观察，仅将元数据移动接纳后的处理人为延后 8.2 秒。在此期间依次发送 `git.status`、`projects.list`，两者均无响应；解除延迟后分别在 **8.260 / 8.262 秒**返回。证明“移动不占普通队列”只对 configure 自身成立。桌面全局超时后失效的行为另由 R1 的真实实验确认。

**建议**：等待项目 Git 锁的请求也不能占用全应用控制队列；可独立调度并保持原项目串行，或者在移动时立即返回明确的进行中状态。保留该项目移动与 Git 操作的协调，不通过移除锁来允许读写正在移动的元数据。

证据：`.artifacts/tests/git-queue-review-mlknc632/report.json`。这是受控慢操作复现，未声称实际大仓库跨盘移动耗时已经测量。

## R3 · P2：正常退出仍会强制中断慢元数据移动

**位置**：[LocalGitService.configure](../../../src/my_agent/local_git/service.py#L91)、[GitSettingsStore._move](../../../src/my_agent/local_git/settings.py#L84)、[Backend.stop](../../../apps/desktop/src/main/backend.ts#L395)。

Python 的 `shield()` 与 EOF drain 会等待移动线程，但 Electron 正常退出在默认 **15 秒**清理宽限后仍终止整个后端进程树，未识别在途 `git.configure`。项目和数据根跨盘、元数据复制较慢时，普通关闭应用也会中断 `shutil.move`，无需用户执行强制退出。

复制阶段中断可能留下完整源目录和不完整目标；删除源阶段中断可能留下完整目标与残留源。再次开启发现两处同时存在会报冲突，需要人工整理；不能再承诺正常退出总能等到可恢复移动完成。这里没有证据表明两个副本都会丢失，不能把“可能中断”夸大为已发生数据丢失。

**建议**：让退出流程识别并等待已接纳的元数据迁移，正常退出不按子进程清理时限强杀它；同时把移动中和恢复状态表达清楚。无需增加用户逐次审批或扩大所有命令超时。若未来支持可中断复制，则再定义独立的完成状态和接续方式。

证据级别：静态调用链确认；未通过故意终止跨盘大仓库制造残留。应用 `before-quit` 确实调用 `Backend.stop()`，不存在另一个等待元数据完成的退出入口。上一轮“退出仍等待已接纳移动”的记录在 Electron 整体退出层面被本项纠正。

## R4 · P2：路径筛选模式错误被升级为 Run 内部故障

**位置**：[read_only.py](../../../src/my_agent/tools/read_only.py#L274)。

`include_globs` / `exclude_globs` 传入 pathspec 编译时没有将模式语法错误转换成可修正工具反馈。`!`、尾部反斜杠等会抛出 `GitIgnorePatternError`；`[z-a]` 会抛出正则编译 `PatternError`。它们越过工具边界，最终变成 `RUN_INTERNAL_ERROR`，模型没有机会修正参数。这与无效查询正则已返回 `INVALID_TOOL_ARGUMENTS` 的处理不一致。

**实证**：本地模型替身先调用 `search(query="needle", exclude_globs=["!"])`，下一步已准备普通回答。实际生产装配只执行 **1 次模型请求**，Run 状态 `failed`、代码 `RUN_INTERNAL_ERROR`，下一步未被调用。单独测试合法模式正常，说明不是 rg 不可用或实际文件故障。

**建议**：在路径模式编译这一处捕获已知语法异常并返回 `INVALID_TOOL_ARGUMENTS`，说明出错字段 / 模式，让模型修正；桌面也展示同一个明确错误。不要增加重复检查、自动重试或把错误吞成空搜索结果。

证据：`.artifacts/tests/search-git-review-_yjht4la/report.json`（模式对照）；`.artifacts/tests/search-argument-review-6natgh2v/report.json`（真实 Run 控制器，只有模型为本地替身）。
