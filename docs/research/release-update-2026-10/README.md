# Coding Agent 发布增量与本项目影响：2026 年 10 月

> 调研日：2026-10-19。对照 2026-09-21 的 Agent 快照及 09-23 的生态调研，重点覆盖此后发布；同时补读与当前开发直接有关的官方文档。本文是研究结论，不是已批准的实施方案。没有修改产品、升级依赖或调用模型。

配套阅读：[落到当前代码的建议](project-implications.md) · [来源、版本与证据边界](evidence.md) · [当前进度](../../progress/project-status-and-roadmap-2026-10-19.md)。

## 1. 结论与路线变化

本项目不需要推倒 M3–M5。现有独立成员、任务级合作空间、渐进加载、事件记录和请求材料清单，仍然适合继续发展。新资料更支持三个方向：**先核实模型服务契约，再提升协作执行的可接续性，最后优化每次请求携带的材料及压缩等待**。

| 方向 | 这次研究改变了什么 | 对当前开发的建议 |
| --- | --- | --- |
| 模型服务 | Go 官方文档的推荐地址已经变化；DeepSeek 发布模型更新和独立搜索接口 | 把服务兼容核对排在新功能前面；不直接断言旧地址失效 |
| 合作空间 | 新版本越来越关注消息到达、等待、取消和结果恢复，而不只是生成团队 | 下一批先做现有合作空间的工作闭环，不扩充组织形式数量 |
| 上下文 | 工具按需加载扩展到内置工具；稳定请求前缀、后台压缩成为具体实现方向 | 保留 800K 配置，优先减少重复材料，再考虑真正非阻塞的压缩 |
| 工作流 | 完整 Agent 可以成为可重跑脚本的节点 | 将组织图、工作依赖和实际运行分清；按真实复用需求逐步增加可执行流程 |
| Skill / MCP / 插件 | 扩展能力从提示词和工具连接进一步进入宿主事件与界面 | 先用现有资源组成可分享工作方式，暂不复制通用插件运行时 |
| 记忆 | 新进展包含接口和部署边界的整理，不能等同于记忆算法突破 | 补好任务共享事实、个人偏好、成员工作状态的使用分工，不重建数据库 |

## 3. 首先影响现有产品的是服务契约

### OpenCode Go

官方当前为 `glm-5.3-flash` 和 `deepseek-v4.1-flash` 列出的 Chat Completions 地址为：

```text
https://opencode.ai/inference/go/openai/v1/chat/completions
```

模型目录为 `https://opencode.ai/inference/go/v1/models`。文档仍要求客户端使用自己的 User-Agent 和每会话稳定的 `x-opencode-session`。[Go 官方文档](https://opencode.ai/v2/docs/console/go/)

本项目集中默认值仍是 `https://opencode.ai/zen/go/v1`。**已确认的是文档与本地配置存在差异，未确认的是旧地址是否停止兼容。** 下一步应做一个小范围的服务兼容核对，分别处理主对话和现有原生搜索辅助请求；不能简单字符串替换整个基地址，因为两个接口使用不同协议。

我们使用的是 Go 服务，不依赖 OpenCode CLI 来驱动 Agent。上游 CLI 的大版本升级不意味着本项目也要更换运行核心。OpenCode 当前托管 Web Search 文档描述的是其连接用户和工作区设置，并未证明仅持有 Go key 的任意第三方客户端可以直接调用一个通用搜索端点。[托管搜索说明](https://opencode.ai/v2/docs/console/websearch/)

### DeepSeek 的模型更新与独立搜索

DeepSeek 在 10-17 发布 V4.1-Flash-1017，同时开放 Search / Fetch API。模型效果和速度提升是厂商发布结论，本轮未测得本项目收益，也未确认 Go 当前路由到的具体模型修订。[发布公告](https://api-docs.deepseek.com/news/news261017/)

独立接口是 `POST /v1/tools/search` 与 `POST /v1/tools/fetch`，使用 **DeepSeek 官方 API key**，分别返回搜索结果与抓取内容。它们可以作为工具直接调用，无需先通过一次模型生成来触发搜索。Go key 与官方 key 不可混用；临时优惠也不能作为永久免费的设计依据。[官方搜索指南](https://api-docs.deepseek.com/guides/search/)

对我们而言，这是一个值得小范围比较的可选搜索后端：主对话仍走 Go，只在用户选择时使用已有官方 key 搜索。预期好处是调用链更短、结果更明确；准确率、首结果延迟和费用仍需同一小样本比较，不应先承诺一定更快。

## 4. 多 Agent：新重点是执行生命周期

DSH `0.2.1-rc.1` 将团队消息直接投递目标 Inbox，移除独立 outbox 及其自动重发链路；子 Agent 支持返回身份后等待结果，并修正等待子 Agent 消耗 Goal 轮次的问题。它也移除了 runtime invariant 插件，修复多处轨迹状态问题。[DSH 发布说明](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-rc.1)

Codex `0.163.0` 的已发布说明包括只读工具并行、CodeMode 取消传播、异步回复正确回到发起线程及子进程输出结束处理。该条目还列出后台压缩的配置 / 基础设施 PR；这些开发变更不等于所有用户已默认启用后台压缩。[Codex 官方 changelog](https://learn.chatgpt.com/docs/changelog)

本项目的启发是：一个成员“已接收消息”“正在处理”“等待另一个成员”“本次发言已结束”“负责的工作已完成”，应当能区分。组织图已经有了，继续增加图样式不如让用户看懂谁在等谁、结果在哪、停止会影响哪些工作。

DSH 的简化也不能机械翻译成删除所有数据边界。应优先删除没有业务作用的重复链路和语义门槛；真实写入冲突、取消清理、结果关联仍解决具体问题。我们不需要再建 outbox、第二套状态机或报告合格评分来实现这些体验。

## 5. 上下文：减少输入与降低等待是两件事

### 请求装配比继续降低压缩点更值得先看

Cursor 09-23 的官方文章介绍了精简系统提示、将低频内置工具按需加载、将易变材料移出稳定前缀，以及减少强制使用子 Agent 的引导。文章报告了生产 A/B 收益，但这些数字依赖其模型和流量，不能移用到 Go。[Cursor 技术文章](https://cursor.com/blog/improved-token-efficiency)

这支持我们继续复用 M4 的工具发现，而不是把所有新能力的 schema 永久塞入每次请求。核心读写、执行和当前模式所必需的工具应容易使用；低频管理能力才适合渐进加载。项目规则不能因为“省 token”被静默移除。

本地还有具体落点：任务和团队材料当前参与 system 内容拼接。可以先用已有请求材料清单观察哪些内容每轮变化，再分离稳定规则与动态工作状态。这里只能推断可能提高缓存复用，不能推断 Go 支持其他厂商的显式 cache breakpoint。

### 真正的后台压缩

Claude API 当前 beta 文档给出明确方式：对固定历史快照请求摘要，同时允许原对话继续；结果到达后仅替换该前缀，保留新增尾部，在下一请求采用。失败时保留历史；同时有两条请求，占用额度与并发。[后台压缩文档](https://platform.claude.com/docs/en/build-with-claude/compaction-background)

这是一份本轮补读的当前文档；`compact-2026-09-04` 的 beta 标识早于本次增量区间。它是 Claude API 的契约，不能直接给 Go 请求加同样参数。

Claude Code `2.1.299` 另有**空闲压缩**：较长会话闲置接近其缓存有效期时整理。这与边执行边压缩不是同一机制。[2.1.299 发布页](https://github.com/anthropics/claude-code/releases/tag/v2.1.299)

对本项目建议保留用户选择的 800K 自动点，不引入固定 54 分钟等上游专属阈值。若增加后台模式，应利用现有切点、摘要和材料清单；在窗口还有余量时预备，在请求边界采用，接近实际容量时再等待。它优化的是等待体验，不自动保证摘要更准或 token 更省。

### 模型切换也是上下文问题

Pi `1.3.0` 不再把另一模型的思考转成普通文本交给新模型，并恢复会话先前激活的工具；同版还修正流式思考 / 正文顺序和部分 Go 协议适配。[Pi 1.3.0](https://github.com/earendil-works/pi/releases/tag/v1.3.0)

本项目允许在输入框切换 GLM / DeepSeek，应该检查请求投影是否正确处理旧模型原生续接数据。历史展示可以保留，发送给另一模型的内容则应按实际兼容能力构造。当前读取发现原生消息复用路径，尚未实测出错误，不能当作已确认的线上 bug。

## 6. 工作流与插件：可复用方式比更多配置更重要

Claude 当前动态工作流文档描述由脚本组织完整 Agent，使用分支、循环和并行，保存结果以支持重跑；恢复具有特定顺序语义，不能保证只重跑失败节点。文档亦包含自动重试行为，不能直接套用本项目的失败停止约定。[动态工作流](https://code.claude.com/docs/en/workflows)

它与用户之前希望的 graph / loop engineering 更接近：节点仍是完整 Agent，代码或配置决定何时派发、汇合与返回。我们现有图描述成员关系，工作项描述进度，模板描述阶段；三者不应混成一个强制执行 DAG。

建议先让一个现有团队配置能重复执行“实现 → 独立 Review → 汇总”，保留用户明确授权的修复边界。实际证明经常复用后，再增加少量显式执行关系，不先开发任意脚本宿主和复杂图编辑语言。

Claude 10-01 发布 Mods：TypeScript 扩展可介入事件、修改行为或界面，并通过插件分发。[Mods 公告](https://claude.com/resources/articles/claude-code-mods)

这证明 Skill、MCP 与宿主扩展解决不同问题。我们若要分享个人工作习惯，第一步可以只是已有 Skill、工作流模板、团队角色和 MCP 引用的资源包。只有这些无法表达的真实需求出现时，再开放有限事件接口；不必为了兼容某个生态立即加载任意扩展代码。

## 7. 记忆与工具执行的新信号

Hermes `0.22.0` 将多种第三方记忆集成移出核心、通过插件目录安装，同时改善子任务可观察性和压缩失败保留历史的处理。它没有提供足以证明某个新记忆算法优于我们现有实现的比较。[Hermes 0.22.0](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.0)

对本项目，更有价值的后续工作是把三类信息用对：个人 / 项目长期偏好、任务已确认结论、成员本轮临时状态。成员可以共享任务成果，但不应因一次协作而复制其他人的完整对话，也不应把每条临时执行记录自动提炼为永久记忆。来源、纠错和撤回继续复用现有记忆服务。

Pi 09-29 起的版本加入 CodeMode 与工具搜索：用代码组合工具，按需取得工具能力；后续版本继续缩短相关提示。[Pi 固定版本 changelog](https://github.com/earendil-works/pi/blob/71023aec1546d6d677a65669c5665c0927ce0dd0/packages/coding-agent/CHANGELOG.md)

这适合“多次检索、过滤、汇总”的往返优化，却增加另一种代码执行、取消与调试路径。我们先扩展现有工具发现和少量只读批处理更合算；CodeMode 可以作为有独立收益样本的后续实验，不能把一般文件编辑改成必须先写一段工具编排代码。

## 8. 建议的接续顺序

1. **小批兼容与缺陷收尾**：Go 契约核对、既有 `report_work` 错误提示，以及双模型切换材料的定向核实。
2. **合作空间可接续体验**：请求 / 结果 / 等待关系可见，局部停止，接续不误重放，沿用现有事件和成员身份。
3. **请求装配效率**：测量实际材料，再处理重复规则、低频工具和动态前缀；维持 800K 的既有选择。
4. **可选后台压缩**：使用固定切点和增量尾部，明确占用、采用时刻及容量不足时的行为。
5. **复用个人工作方式**：小范围任务流程与资源包；独立搜索后端按需求比较，通用插件 / CodeMode 后置。

安装包与原有交付计划仍然保留，不因研究新发布而无限后移。具体代码映射、收益与代价见[实施影响分析](project-implications.md)；以上均为待讨论建议，未创建 M6 或改写已确定阶段范围。
