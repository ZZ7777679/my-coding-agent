# Coding Agent：从最小循环到产品运行系统

> 调研截止与访问日期：2026-09-16。比较公开实现与闭源产品的可核实机制，不做未经同条件测试的排名。本文没有安装、运行或计费调用任何第三方 agent。关联：[工作流](04-workflows.md)、[Harness](06-harness.md)、[代码上下文](08-context-engineering.md)。

## 阅读起点：代码助手怎样变成能完成任务的 Agent

普通代码问答把需求转换成一段回答；coding agent 还要把回答转成真实动作，观察结果，再决定下一步。例如修复一个导出错误，它需要读到正确版本的代码，形成假设，修改文件，执行适合的检查，理解失败，最后交付可审阅产物。模型生成的补丁只是其中一个环节。

这里至少有三种“完成”：模型结束输出、运行器结束一轮、用户目标得到满足。三者可能不同。模型可能因为上下文不足而停止；运行器可能因为预算用尽而结束；文件已修改但关键行为未验证，目标仍未完成。成熟产品需要把这些情况分别表达。

本篇从最小可读实现讲到完整产品和企业案例。代码开源、客户端开源、模型权重开放、托管平台公开是不同维度；不能因为某产品有 GitHub 仓库，就假定其全部运行逻辑和模型可自行部署。

## 1. Coding Agent 的工程对象

能生成代码的模型不自动构成 coding agent。完整系统需要获得任务和代码状态，选择操作，执行读取 / 修改 / 检查，依据结果调整，再交付可审阅成果。工作对象也不限于源文件：需求、构建环境、日志、浏览器、版本控制和人的反馈都会改变下一步。

可以把架构分为五个面：模型适配负责请求与响应；运行循环负责何时继续和停止；执行环境负责进程与文件；状态系统负责会话、事件和恢复；产品界面负责让人理解、纠正和接管。这种分法解释了为什么几十行循环可以在 benchmark 上有效，却不能独自覆盖成熟桌面产品。

2024 年 SWE-agent 强调为模型设计操作界面；mini-swe-agent 随后探索更简单的 shell 循环。到 2025–2026，SDK、前后端分离、远程工作区和长期任务逐渐成为独立组件。这里不是一条“复杂架构必然优于简单架构”的演进线：研究基线、个人 CLI 和企业工作平台追求不同目标。[mini 项目对原始 SWE-agent 的说明](https://github.com/SWE-agent/mini-swe-agent)、[OpenHands SDK 论文](https://arxiv.org/abs/2511.03690)

## 3. mini-swe-agent：源码小，但语义并不只有 while 循环

### 3.1 沿实际实现走一轮

访问日 `DefaultAgent` 的 `run()` 初始化消息并循环 `step()`；`step()` 查询模型再执行 action；查询前核对调用、成本和墙钟限制，查询后累计费用；格式错误有独立累计与退出路径；每轮结束保存轨迹。终止通过带退出信息的消息表达。[当前实现](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/agents/default.py)

这里有一个值得学习的细节：模型输出解析失败不表示模型请求免费。源码专门处理已计费的格式错误，避免只统计成功解析的轮次。**本项目推论**：预算账本应由请求事实驱动，解析、策略拒绝和用户中断不能使已发生费用消失。

项目主张工具面以 bash 为中心，动作使用独立进程执行，历史保持线性，方便调试与训练数据复用；当前主线已是 v2。[README 与版本提示](https://github.com/SWE-agent/mini-swe-agent)

### 3.2 独立 shell 动作的收益和代价

**架构分析**：无长期 shell 状态，意味着每次动作必须明确工作目录和依赖环境。上一条命令的 `cd` 或临时变量不会自然成为下一条命令的隐式状态。这减少了“到底在哪个目录运行”的不确定性，也方便将本地命令执行替换为容器内执行。

代价是长运行开发服务、交互进程和终端会话需要另外建模；不能把它们当作普通短命令。只有 bash 也不自动跨平台：Windows 的路径、编码、进程树取消与命令可用性都不同。模型能写出 PowerShell 不代表采用 bash 假设的环境已经支持它。

### 3.3 为什么适合基线，不等于适合直接当桌面后端

极简历史适合检查模型实际看到什么，但长期任务会积累大量输出；简单轨迹落盘可以帮助研究复现，却不等于多会话单写者存储、原子持久化或崩溃恢复。产品还需要严格 DTO、隐私处理、UI 事件归属、授权和持久预算。这些属于不同需求，不应以核心行数少就推断整个产品容易复制。

选择 mini 作为对照时，应保留相同模型与任务，看新增复杂机制是否产生可解释收益。例如增加语义检索后减少多少无效读取；增加 planner 后是否只是耗费更多 token。它的价值之一是迫使复杂架构证明自己。

### 3.4 沿一个失败回合理解最小循环的边界

用一个自拟例子：模型发出读取文件的命令，执行结果提示路径不存在。Agent 应把真实错误作为观察进入下一轮，让模型检查目录或修正路径；不能捕获错误后返回空正文，使模型误以为文件存在但没有内容。

mini 的当前 default agent 将查询、动作执行、结果处理和轨迹保存分成可读方法，并在预算与错误路径上保留逻辑。源码中模型输出格式失败仍可能产生已计费消耗，保存逻辑也不应只在成功时执行。[实际实现](https://raw.githubusercontent.com/SWE-agent/mini-swe-agent/main/src/minisweagent/agents/default.py)

它说明一个重要工程原则：失败回合也是运行事实。格式错误不等于模型没有收费，工具失败不等于用户目标不再存在，程序退出不等于结果可交付。最小循环已经需要处理这些语义，只是产品会在它们周围增加更强持久化和交互。

### 3.5 适合作为什么样的对照基线

如果一个新架构增加 planner、检索器和三个 reviewer 后表现更好，需要排除它只是用了更多预算。可以先固定模型、工具环境和费用，以 mini 风格的简单循环作对照，再逐项增加机制。目标不是证明极简永远最好，而是知道复杂性究竟解决了什么问题。

这类研究基线也提醒开发者不要以代码行数比较完整产品成本。研究执行器不必同时支持用户任意目录、多个会话、原生 UI、更新迁移和权限解释；个人桌面产品却必须面对这些需求。

## 4. Pi：通过扩展保持核心可理解

Pi 当前将自己定位为最小终端 coding harness，提供读、写、编辑和 bash 基础工具，并通过 extensions、skills、prompt templates、packages 扩展；支持交互、单次输出 / JSON、RPC 和嵌入式 SDK。默认不内置完整 plan mode 或子 agent 编排。[实际包入口](https://github.com/earendil-works/pi/tree/main/packages/coding-agent)

**架构分析**：模型 API、agent loop、终端 UI 与 coding-agent 产品可以分层。基础 loop 只需要理解模型消息和工具回合，产品层再处理会话、配置、上下文文件与扩展。用户若想定制工作方式，不必每次 fork 底层循环。

这类架构最容易被误学成“什么都做插件”。真正需要设计的是稳定扩展点：何时允许加上下文，何时可拦截工具，何时能停止运行，扩展异常由谁承担，以及卸载时怎样释放监听器和资源。扩展越接近运行循环，版本兼容和错误隔离越重要。

**一个插件冲突的具体例子**：扩展 A 在工具执行前增加用户确认，扩展 B 自动重试失败操作。如果 B 绕过原工具入口重试，A 的确认便不再覆盖重试；如果两者都修改同一消息，处理顺序会改变模型输入。解决方案需要宿主统一执行管线与显式顺序，不能只让插件作者约定“请小心”。

**落地判断**：Pi 适合研究小核心如何支持多种入口与个性化扩展。当前仓库和 npm 组织已有变化，应以当前来源核实，不直接照搬旧 `pi-mono` 教程中的路径。对本项目可以吸收职责分离；已有 Python 核心与受控 provider 边界无需为使用其插件生态而替换。

## 5. OpenHands SDK：Agent、Conversation、Workspace 为何要分开

### 5.1 三个对象承担不同生命周期

OpenHands SDK 的公开架构把 agent 的推理行动逻辑、conversation 的状态 / 生命周期、workspace 的执行位置分开；工具具有 action、observation、executor 类型，另有事件、condenser 和执行前安全机制。SDK、tools、workspace、agent-server 也分成不同包。[架构文档](https://docs.openhands.dev/sdk/arch/overview)

**这种分离解决的问题**：agent 配置可以复用，但每个 conversation 不能共用可变历史；同一任务逻辑可以运行在本机或远程环境，但路径和进程实际属于 workspace。若三者混为一个大对象，UI 重连、迁移环境或并发会话时容易意外复用状态。

一次运行可拆成：客户端发送消息 → conversation 接纳输入 → agent 构建模型请求 → 产生 action → workspace 内 executor 执行 → observation 进入事件流 → 下一轮或终止。这里每个边界都能独立提供类型校验和观测。

### 5.2 远程工作区不只是给 shell 加一个 Docker 前缀

本地模式可以单进程执行，远程模式通过 Agent Server 和 workspace 实现运行环境切换。当前仓库明确把 SDK / Server、TypeScript client、Agent Canvas 和 automation 的职责分开：调度、webhook 和 run history 不全部塞进 SDK。[仓库边界](https://github.com/OpenHands/software-agent-sdk)

**远程化推演**：上传文件、流式输出、断线重连和服务生命周期都会成为协议问题。一个 UI 请求断开时，后台任务可以继续也可以取消，但必须有约定；不能由 HTTP 连接偶然断开决定业务状态。UI 重新连接应读取权威快照，再从已知游标追赶事件，而非凭本地 spinner 猜测。

**成本与风险**：远程环境提供可丢弃运行位置，但镜像构建、依赖预热、网络权限、secret 注入和产物回收都需要运维。把 workspace 设为本地目录则没有自动容器隔离。是否采用取决于真实执行需求，不能由 SDK 示例中的一个参数推断安全保障。

### 5.3 对本项目最有用的参考

现有 Python 后端、独立 Electron 前端和 Pydantic DTO，与这种职责拆分有相通之处。下一步可以研究“执行事实怎样形成事件、UI 怎样恢复”，而不是先引入另一整套运行时。若将来使用其某个组件，应评估 SDK 自带重试、默认日志和凭据转发是否与本项目统一预算和脱敏规则兼容。

### 5.4 把一个任务移到远程环境，具体多出什么

假设用户在桌面发起任务，实际代码放在远程容器。客户端需要传递目标和工作区身份；运行端拥有模型循环与执行器；文件、进程和依赖必须处于同一工作世界；结果通过事件流和产物引用回到客户端。OpenHands 的 Agent / Conversation / Workspace 分层为分析这些职责提供了公开入口。[架构说明](https://docs.openhands.dev/sdk/arch/overview)

断网时有两个独立问题：后台是否继续执行，前台如何补回错过的事实。可靠 UI 通常先恢复权威快照，再从游标追赶事件，并按运行身份拒绝迟到事件污染新任务。本文描述的是通用设计要求，不能仅因某 SDK 支持远程连接就宣称这些场景全部验证通过。

远程执行收益是环境可预配置、可丢弃、可与用户桌面分离；代价是启动、同步、网络、凭据注入和产物回收。若用户频繁依赖本机原生应用或未同步文件，远程路径反而增加摩擦。选型应以任务环境为起点。

## 6. Codex、Claude Code、OpenCode：产品 API 暴露了哪些核心语义

### 6.1 Codex 的 thread / turn / item

Codex app-server 面向富客户端，区分会话 thread、一次用户请求及后续工作 turn、消息 / 命令 / 文件修改等 item，支持流式事件、steer 与 interrupt。其实现可在开源仓库查看；特定 transport 和 API 仍有实验性标识，不能统称全部稳定。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

**设计分析**：三层身份使用户一句输入后产生多个工具动作仍属于同次工作，也让 UI 区分正文增量、工具进度和执行终态。`steer` 与 `interrupt` 分开尤为重要：纠正任务可以进入活动工作，取消则要求结束执行。把两者都实现成“发一条新聊天消息”，会让模型和进程状态失去对应。

对本项目而言，未来任务 Task 可以位于会话之上，不必直接等同于上游 thread。任务目标、会话历史、运行尝试和工具调用分别编号，才能处理多会话续接以及迟到事件。参考上游概念不意味着照搬其全部 DTO 或私有续接状态。

### 6.2 Claude Code 的回路与可接管性

Claude Code 官方说明了收集上下文、执行和验证的循环，以及会话压缩、文件 checkpoint、权限与运行中纠正。其 checkpoint 不覆盖远程数据库、API 或部署等副作用。[产品运行说明](https://code.claude.com/docs/en/how-claude-code-works)

**机制分析**：可撤销文件和可取消工作是两个独立维度。停止生成只能保证不继续请求，未必撤销已经写入的文件；恢复文件也不能撤销已经调用的外部服务。产品必须分别呈现“执行已停止”“本地改动仍在”“外部动作已发生”。这比给用户一个笼统的撤销按钮更准确。

压缩也不是完成信号。长会话中，用户的目标需要在压缩后保留；任务未完成但模型输出了总结时，外层控制器还应检查完成条件。用户看到的“会话结束”与“目标完成”应是两个事实。

### 6.3 OpenCode 的服务边界与 Go 网关

OpenCode 服务提供会话、消息、异步提示、终止、diff、权限和事件等接口，并公开 API schema。它展示了多个客户端共享运行后端的方式。[Server 文档](https://opencode.ai/docs/server/)

**对本项目必须保持的区分**：OpenCode Go 是当前使用的模型服务入口，OpenCode agent / server 是另一个运行产品。调用 Go 不等于依赖其 CLI 的工具执行循环；本项目已经有自己的运行核心。若复用它的客户端 / 服务端经验，可以研究事件流、schema 和 session 管理，而不将已有 Python 后端替换成进程包装器。

**接口设计推论**：异步发送只说明请求被接受，不能将 HTTP 204 当作任务完成；abort 接口返回也需要终态事件来确认清理结束；diff 应绑定具体基线和会话，避免展示其他任务的未提交修改。类似细节决定客户端是否可靠。

### 6.4 Aider：将方案形成与补丁表达分开

Aider 的 code、ask、architect 等模式区分讨论和修改；architect 模式先产生解决方案，再由 editor model 转为具体编辑，可以使用同一个或不同模型。官方也明确两次调用会增加成本和时间。[模式说明](https://aider.chat/docs/usage/modes.html)

这种分工解决的是两种能力可能不一致：模型擅长理解问题，不一定擅长稳定生成可应用差异。将编辑格式单独处理，可以针对 whole-file、search/replace 等表示做适配；但方案中的歧义仍会传播给 editor，不应把第二次调用视为独立验证。

对一个跨文件改动，架构阶段应说明接口和约束，编辑阶段读取当前文件后形成具体差异。若中间基线变了，需要重新核对；不能把 architect 的旧行号强行套到新文件。Aider 的 repo map 另见[上下文专题](08-context-engineering.md)，它与编辑器分工共同说明代码理解和代码写入是不同子问题。

旧文档中针对当时模型的推荐组合具有历史条件；本文只提取分工机制，不将旧模型建议当作 2026 年选型结论。

### 6.5 Cline 与 Roo Code：编辑器集成和可恢复交互

Cline 的 checkpoint 文档描述独立 shadow Git 仓库，并区分恢复文件、恢复任务消息、同时恢复两者。这把代码状态与对话状态拆成可单独操作的对象。[官方说明](https://docs.cline.bot/core-workflows/checkpoints)

它的实用价值是允许用户保留已有讨论、撤回某条错误实现，再尝试另一方案。代价包括仓库扫描和快照存储，以及恢复前识别用户后续修改。文档中关于降低错误成本的产品表述，不应扩展成远端副作用也能撤销；运行命令可能已经改过数据库或发出网络请求。

Roo Code 是这一类编辑器 agent 的重要历史项目，但主仓库在 **2026-05-15 已归档**。它可用于研究源码和模式设计，不能按旧教程将其写作仍持续更新的主线产品。[仓库状态](https://github.com/RooCodeInc/Roo-Code) 本轮没有将任何社区 fork 与原产品视为同一维护承诺。

### 6.6 Gemini CLI：将终端入口与运行核心分包

Gemini CLI 的公开架构区分 packages/cli 的输入显示与 packages/core 的模型、工具和请求处理；当前 core 包清单仍能核实这一边界及 Apache-2.0 声明。[架构文档](https://google-gemini.github.io/gemini-cli/docs/architecture.html)、[当前包清单](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/package.json)

这类分离使其他入口有机会复用运行核心，但“独立包”不等于其全部业务假设都通用。例如模型协议、认证、工作目录和工具策略仍可能与产品耦合。准备复用时应检查依赖方向和核心对象，而不是只看导出了哪些函数。

旧架构页中的权限默认和模型细节不在本文当作当前行为保证；本轮核查侧重职责边界，未做运行验证。

### 6.7 Devin / Fusion：近期闭源产品里的双 Agent 分工

Cognition 于 2026-06-29 介绍 Fusion，并在 2026-09-11 宣布进入 Desktop 与 CLI。其公开机制是 lead 负责规划、歧义判断与审查，sidekick 承接执行；双方拥有持续上下文，通过任务简报、结果和反馈交流。[6 月架构说明](https://cognition.com/blog/devin-fusion)、[9 月更新](https://cognition.com/blog/local-fusion)

关键设计问题是交接质量。若 lead 只说“修复导出”，sidekick 可能漏掉不覆盖旧文件的约束；若复制全部历史，又失去上下文分离的价值。一个有用简报应包含目标、必要事实、禁止破坏的约束、产物和完成判据，执行者发现矛盾时能反馈，而不是机械服从错误计划。

该路线与“最初按提示难度选一个模型”不同：任务难度往往要探索代码后才知道，因此能力分配发生在工作过程中。代价是协调和审查同样收费，弱执行者反复返工可能抵消其较低 token 单价。应评价完成任务的总成本与质量，不能单看价格表。

厂商材料披露了有收益也有质量下降的任务，且不同发布日期的实验组合与成本口径变化。本文不采用一个百分比概括全部任务，也未获得闭源实现或独立复现结果。本项目既定双模型范围不因此自动改变。

## 7. Cursor 的多 agent 实验：规模增加后瓶颈会迁移

Cursor 2026-01 的工程记录披露：早期平等 agent 通过共享文件和锁协作，出现等待、持锁故障和无人负责困难问题；随后分离 planner、worker 和阶段判断，并定期刷新上下文。文章同时明确部分大规模迁移仍需仔细 review。[原始实验记录](https://cursor.com/blog/scaling-agents)

**架构解释**：并发只缩短可以独立完成的部分。共享规划、集成、验证和 review 会成为串行路径；更多 worker 还会增加合并冲突与沟通开销。planner 的作用是发现依赖和定义接口，不是给每次工具调用排班；worker 输出应包含可核对产物和环境事实。

**一个具体分工例子**：API schema 与客户端生成依赖强，不宜让两个 worker 各自发明 DTO；独立文档调研或互不重叠的模块修改更容易并行。即使通过 worktree 隔离文件，也必须指定谁拥有共享规范和最终集成。当前用户提醒的 docs 并发正属于这种问题。

**证据边界**：厂商试验中的代码行数、提交数和长时间运行展示了活动规模，不直接证明维护性、用户价值或人均生产率。应测有多少任务无需返工完成、review 花多久、失败是否可恢复。2026-01 的模型比较也只属于当时配置，不能作为 2026-09 的模型推荐。

### 7.1 与 Cognition 近期经验放在一起看

Cognition 2026-04 的工程文章强调一种较窄的可用组合：多个 agent 提供分析和审查，写入责任保持清晰；它也讨论干净上下文 reviewer、专家咨询和更高层委派的通信问题。[原始文章](https://cognition.com/blog/multi-agents-working)

与 Cursor 的实验合看，真正的设计轴不是“一个还是一百个 agent”，而是哪些决策必须一致、哪些证据可独立收集、谁集成产物。只读研究通常较容易并行；多个写者需要隔离和合并；涉及同一接口的工作则应先明确共享约束。

这不能推导所有项目必须全局串行。不同会话的独立工作可以并发，真正冲突的文件或资源局部协调。把某厂商一种工作模式写成普遍定律，和盲目追求全并行同样缺少依据。

### 7.2 企业实际落地：HIL / SIL 分诊与测试生成

Cognition 2026-05 的客户材料描述在 RV Tech、Mercedes 等场景使用 Devin：收集故障日志、诊断、生成结构化分诊报告；将需求分析与测试实现分开，并用可复用 playbook 传递领域知识。文章也承认专有工具集成与宽泛要求映射仍有难度。[企业案例](https://cognition.com/blog/how-to-automate-failure-triages-and-10x-test-generation-what-weve-learned-deploying-ai-across-hilsil-workflows)

HIL 指把真实硬件纳入测试，SIL 则在软件环境模拟相关行为。硬件台架稀缺、运行慢，因此价值可能先来自提前分诊、减少无效等待和复用测试知识，而不是直接替代全部硬件验证。该材料是供应商发布的客户案例，不是独立随机实验；自动生成更多测试也不自动等于更高缺陷发现率。

这个案例对通用开发的启示是选择可闭合的工作单元：输入有日志和需求，输出有可审查报告或测试，工程师保留最终判断。先把 agent 接到已有工具、环境和结果链路，比单独增加一个聊天窗口更接近实际收益。

## 8. 横向分析：真正影响能力的四组耦合

### 模型与工具界面

同样模型，获得语义明确的文件编辑工具与获得裸 shell，成功方式不同。前者可以统一校验路径和基线，后者灵活但需要解释命令副作用。不能用一个工具配置下的分数决定模型在全部产品中的表现。强模型也可能适合更小的工具面，复杂 parser 反而制造失败点。

### 上下文与执行环境

模型看到的仓库摘要必须对应实际工作副本。索引来自主分支、执行发生在另一个 worktree 时，会产生似乎合理但定位错误的修改。环境标识、版本、缓存失效和检索证据应一起设计。详见[上下文专题](08-context-engineering.md)。

### 单次成功与长期可靠性

能修复一个 benchmark issue，不代表能正确处理用户中途变更、Windows 文件锁、部分写入或跨会话接续。产品验收应覆盖自己的关键路径；公共榜单用来理解能力类型，不能代替产品契约。

### 自主性与可接管性

更长时间连续工作，需要更清晰的状态，而非更少的信息。用户应能看到目标、当前活动、已产生副作用和阻塞原因。可靠的自主推进不是永远不停止：证据不足时应明确等待具体输入，但普通查询和进度插话不应丢弃原目标。

## 9. 本项目的研究结论与采用顺序

优先吸收 mini 的可理解循环与真实预算、OpenHands 的状态 / 环境分离、Codex 的运行身份与事件、Claude Code 的接管语义、Pi 的有限扩展点。DeepSeek Harness 的插件生命周期在[Harness 篇](06-harness.md)细拆。没有必要先选择一个“全能框架”再把产品需求塞进去。

当前 M1 只有只读工具闭环。近期设计应先定义 Task 与 Session 的关系、目标状态、产物和交接，再在进入实施阶段时增加有边界的编辑 / 执行能力。多 agent、远程容器、自动 PR 和自进化不是此调研隐含批准的实现项。

后续若做可运行对照，选择固定少量真实任务，冻结模型、预算、初始代码和环境，比较定位正确率、补丁正确性、用户纠正、恢复成本与总费用。不要把来自不同日期、不同模型和不同 benchmark 的数字拼成统一排行榜。

## 10. 补齐 SWE-agent 的 ACI：工具界面本身就是算法的一部分

此前介绍 mini-swe-agent，却没有充分交代其前身路线，是一个概念沿革缺口。[SWE-agent 的 ACI 说明](https://github.com/SWE-agent/SWE-agent/blob/main/docs/background/aci.md) 把 Agent-Computer Interface 定义为工具和交互格式的组合。其经典设计包含有范围的文件窗口、简洁搜索反馈、编辑时语法检查和明确的空输出提示。原实验中的窗口尺寸是特定模型与任务下的经验，不是今天所有工具的正确常量。

为什么同一个模型换工具界面会变强？假设搜索返回五千行，模型必须先定位候选，再记住位置，随后生成依赖行号的修改。界面若先返回匹配文件，再按需展开，减少的是决策前的无关信息；编辑器若报告精确语法错误，增加的是下一步可以采取行动的反馈。两者都改变了求解过程的信息结构，而不只是界面美观。

但限制也可能妨碍正确行为。跨文件重构中的某个中间文件暂时不合法，逐次编辑立即拒绝可能使有效的整体修改无法表达。现代模型擅长 shell 时，过多特制命令又会增加学习成本。因此 ACI 的可迁移结论是评估动作粒度、反馈与错误恢复；不是永久保留某套历史命令。与 mini 的简化工具面一起分析，才能看见“精心约束”和“减少抽象”的不同适用条件。

## 11. Goose 与企业分叉：公开核心如何变成组织内部产品

[Goose 当前官方入口](https://block.github.io/goose/) 提供桌面 / CLI、扩展和 ACP 互操作方向。本次访问的安装链接已经指向 `aaif-goose/goose`，旧 Block 路径应作为历史入口核查，不能据路径直接判断停更。公开项目与 Stripe 的内部 Minions 也不是同一部署物；后者使用 Goose 的分叉，并叠加组织环境与工作流，详见 [Stripe Blueprint 分析](04-workflows.md)。

这一案例说明采用开源 Agent 的真正工作量。核心循环解决如何调用模型和工具，企业还要绑定仓库、开发环境、凭据、规则、检查入口与代码审查。内部平台已有这些能力时，复用开源核心可能加速交付；若基础设施缺失，下载相同仓库不会自然得到相同端到端效果。

考察分叉应追踪四类差异：上游修复如何同步，企业工具如何选择，组织规则在哪里生效，以及失败后谁能接管。企业公布任务吞吐量可以证明某种使用规模，不能直接证明替代了同等工时，更不能证明公开版本也具备内部工具集合。

## 12. 2026 年选型需要分清产品、SDK、Harness 与协议

Deep Agents / DeerFlow 的装配和运行所有权、OpenAI 托管 Agents API 的环境生命周期，已补入 [06](06-harness.md)；编辑器与 Agent 的 ACP、远端 Agent 的 A2A、面向 UI 的 AG-UI，另见 [11](11-agent-protocols.md)。这些不是给产品列表增加几个名字，而是补齐相邻层的能力边界。

例如“支持 ACP”说明客户端有标准化接入路径，不能推出该 Agent 具备可靠代码修改能力；“提供 SDK”说明可编程嵌入，不能推出拥有完整桌面产品；“托管 harness”减少循环维护，但未必接管自托管机器。对开发者最有用的比较单位，是一次具体任务从输入、执行、成果到恢复的完整责任分配。
