# Skill、Tool 与 MCP：能力组织、协议演进与执行边界

> 调研截止与访问日期：2026-09-16。重点版本：MCP `2026-07-28`；Agent Skills 使用访问日规范。性质：协议与实现资料分析，未安装服务器或执行远程工具。关联：[Harness](06-harness.md)、[工作流](04-workflows.md)、[安全](10-security-recovery.md)。

## 阅读起点：一次代码审查需要哪些“能力”

用户说“审查这个变更，给出有证据的报告”。模型首先需要知道审查的方法：先了解需求，再看差异，追踪调用关系，区分真实缺陷与风格偏好。这一层适合由 skill 表达。它还需要读取文件、搜索符号、取得差异，这些是 tool。若差异来自外部代码平台，宿主需要一个稳定连接方式发现并调用平台提供的能力，这可以由 MCP 承担。

三者相互配合，但没有必然的一一对应关系。一个 skill 可以使用多个本地工具和多个远端服务；一个工具可以服务许多 skill；一个 MCP server 可以暴露工具、资源和提示等不同对象。同样的审查方法换到离线仓库，仍可使用本地工具完成，不必因为没有 MCP 就失效。

组织能力的目标也不是让目录尽可能大。对 agent 来说，真正困难的是在当前任务里发现合适能力、理解输入、得到可用结果，并知道什么时候需要换方法。下面沿这条调用链分析各层的实现。

## 1. 核心判断：三者解决不同问题

Tool 定义可执行动作；MCP 让宿主发现并调用外部能力；Skill 表达如何完成一类工作。工作流负责一次具体任务的步骤、依赖和状态，插件负责分发与安装。将这些对象统一叫“插件”容易启动快，但后面会在版本、权限、失败恢复和产品交互上付出代价。

一个 code-review skill 可以指导先读需求、定位变更、检查高风险路径、形成有证据的问题；它通过文件读取、差异检查等 tool 工作。若读取 GitHub PR，tool 可以由 MCP server 提供；若读取本地工作区，可以直接用宿主内建工具。Skill 无须依赖 MCP 才能成立，MCP 也不限定必须有 skill。

## 2. 从调用接口到能力系统

| 对象 | 主要契约 | 谁持有状态 | 不应承担的职责 |
| --- | --- | --- | --- |
| Tool | 参数 / 结果 schema、错误、取消、作用范围 | 执行后端及业务服务 | 自行决定用户完整目标是否完成 |
| Skill | 触发描述、方法、资源、预期产物 | 通常是可版本化的内容包 | 绕过宿主授权，充当数据库事务 |
| MCP | 能力发现、消息、传输、扩展、认证接口 | 新版协议核心无会话状态；业务仍可有状态 | 自动提供沙箱、消除提示注入 |
| Plugin | 包清单、组件、依赖、来源、安装版本 | 插件管理器 | 等同于所有内容已经可信 |
| Workflow | 实例状态、依赖、分支、交接、完成条件 | 任务 / 调度系统 | 替代节点内部的工具循环 |
| Agent | 在目标和约束下选择行动 | Harness 与模型共同作用 | 通过自称获得授权来扩权 |

这些是本研究的职责划分，不是要求本项目立即建设六套通用框架。对于现有三个只读工具，简单注册与统一策略就足够；新增抽象应对应真实扩展压力。

## 3. Skill 的架构与实现机制

### 3.1 从自然语言规则到渐进加载

Anthropic 在 2025-10-16 的文章中介绍 Agent Skills，并于 2025-12-18 更新为开放标准方向。其关键设计是把可发现元数据、主要指令、详细资源分层，而不是把所有操作说明永久塞进系统 prompt。[原始工程文章](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

[Agent Skills 规范](https://agentskills.io/specification)定义以 `SKILL.md` 为最小入口，使用 YAML 元数据和 Markdown 正文，可附脚本、参考资料、资源。`name`、`description` 参与发现，正文在激活时载入，资源按需读取；`allowed-tools` 当前标为实验性，客户端支持可能不同。文件格式兼容不保证权限语义、触发率和执行效果相同。

可将宿主实现拆成以下步骤：

```mermaid
flowchart LR
    A[扫描已允许的来源] --> B[校验元数据与身份]
    B --> C[生成有预算的目录]
    C --> D[显式调用或语义匹配]
    D --> E[读取指定版本指令]
    E --> F[按需读取资源]
    F --> G[工具调用经统一策略执行]
    G --> H[记录使用版本与成果]
```

这里真正的工程难点不在解析 YAML，而在**选择与约束**：多个描述相似的 skill 谁触发；来自项目的 skill 与用户配置如何区分；相对资源能否逃出包目录；正文更新是否影响正在执行的任务；脚本调用在取消后能否终止。

### 3.2 内容、执行依赖与权限应分别表达

一个格式正确的 skill 可能依赖 `bash`、某个 Node 包、外网账号和已有工程约定。发现阶段只需知道它是否可能适用；激活阶段检查当前环境能否满足；执行阶段再检查具体路径、命令和外部写入范围。否则“安装所有依赖以备将来使用”会膨胀环境，“缺一个可选脚本就禁止全部功能”又会形成过度约束。

本项目未来可以将 skill 内容版本、依赖状态和允许调用的能力分开记录。`allowed-tools` 或正文写“允许执行”的内容是能力需求，不足以自行扩大当前用户授权。对缺失依赖，应显示受影响的步骤和可选替代方法，而不是静默改用其他 provider。

### 3.3 Codex 的公开实现方向

OpenAI 当前文档同样采用渐进加载，并把 skill 作为可复用工作方法的编写格式、plugin 作为可安装分发单位。文档还明确大量 skill 的目录本身需要预算控制，可能截短描述或省略部分条目。这说明“只加载 metadata”也不是零成本方案。[官方 Build skills](https://learn.chatgpt.com/docs/build-skills)

**本研究的推论**：当目录规模变大，应该记录未展示条目、冲突与发现失败；否则用户以为某 skill 已可用，模型实际上没有看到它。给本项目内置的讨论、实现、review、handoff 等少量能力做明确范围，比早期建设复杂技能市场更有价值。

### 3.4 一个 Skill 包从安装到产生结果的完整过程

下面是用于说明的包结构，不是本项目新增的实际 skill：

```text
review-change/
  SKILL.md              适用场景、步骤与报告标准
  references/
    concurrency.md      并发缺陷检查方法
    compatibility.md    接口兼容性检查方法
  scripts/
    collect_diff.py      确定性收集辅助程序
  assets/
    report-template.md  产物模板
```

**发现阶段**只需要知道名称、描述与来源。描述应帮助区分“审查已有变更”和“实现新需求”，而不是笼统写成“提高代码质量”。若两个 skill 的描述都声称适用于一切编程任务，模型很难稳定选择。

**激活阶段**读取具体正文，确定当前变更的任务契约。例如报告必须含问题、触发条件、影响与代码位置；没有发现问题也应如实说明。此时才决定是否读取并发参考材料，不应每次审查都注入所有专题。

**执行阶段**使用工具收集证据，必要时调用确定性脚本。脚本只负责有明确输入输出的辅助工作，不应在隐藏步骤中扩大任务范围。依赖缺失要说明哪个动作不可用；存在等价的内建工具时可采用明确替代，不能把整份 skill 宣称为已经执行。

**交付阶段**检查报告是否支持原目标，并记录使用的 skill 版本。仅成功读取 SKILL.md，不代表模型遵循了方法；只有产物和行为能够说明效果。上述分层符合 Agent Skills 的渐进加载思想，具体运行语义仍由宿主决定。[规范](https://agentskills.io/specification)

### 3.5 内容越长越专业吗：规则、例外与脚本的分工

正文适合保存决策流程和必须关注的条件；详细领域材料放参考文件；重复确定性操作放脚本。若把一百条互有例外的规则直接堆进正文，模型可能在重要规则上失焦，也会增加每次激活成本。

例如“涉及取消时检查子进程生命周期”是方法；某操作系统的具体 API 与例子可以放参考资料；枚举差异文件可由脚本完成。这样不仅节省上下文，还把易变化的实现细节与较稳定的工作原则分开。

Skill 的自动演化也应围绕这些对象分别处理：修改描述影响触发率，修改正文影响决策，修改脚本影响执行行为。一次同时修改三层却只看总体成功率，难以知道哪一层带来收益或回归。相关优化见[自进化专题](03-self-evolution.md)。

### 3.6 同名、覆盖和正在运行的版本

用户安装的 review、项目自带 review、插件提供的 review 可能不是同一个对象。显示名称可相同，内部身份至少需要来源与稳定标识；优先级应由宿主定义。简单按扫描顺序覆盖，会让行为随文件遍历变化。

运行中应引用已经载入的具体版本。用户更新默认 skill 后，新任务采用新版，旧任务可以继续原版或显式重新装载；不应让某个步骤突然读到一套新规则而没有记录。即便底层只有 Markdown，版本问题依然真实存在。

## 4. Tool 设计：决定成败的通常是语义

### 4.1 “把每个 API 包成工具”为什么容易失败

底层 API 按数据库对象设计，用户任务按目标组织。例如用户要“找出最近一次失败的构建原因”，若工具只能分别查组织、项目、流水线、任务、日志块，模型要完成许多无业务意义的中间转换。反过来，一个 `do_everything` 工具虽减少调用，却隐藏范围、执行状态与失败位置。

Anthropic 的工具设计文章强调对真实任务评估工具，关注名称、参数、返回信息与 token 使用，而不是仅证明函数能被调用。[Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)

合理粒度是：一项动作有明确业务含义、权限范围、结果与可重试边界。对本项目，`read_file` 可以接受行区间并返回真实路径标识、版本与截断信息；不应该为了名称好看，把搜索、任意读取、执行 shell 和写文件混在同一能力里。

### 4.2 结果不只是字符串

建议区分四部分：机器可用的数据、供模型理解的简要说明、供用户查看的呈现、供诊断使用的脱敏关联。失败也需区分：参数不合法、权限拒绝、业务未找到、暂时故障、操作已执行但结果丢失。只返回 `success: false` 会使 agent 无法决定是否安全重试。

工具输出超过上下文预算时，优先提供分页 / 引用 / 文件产物与可定位摘要。静默截断会把“搜索结果没显示出来”变成“结果不存在”。读工具可以并发不代表所有工具都可并发；两个写操作存在共同文件或业务对象时，需要显式排序或冲突检测。

### 4.3 调用生命周期

```text
接收完整参数 → schema 校验 → 解析真实目标 → 权限与预算检查
→ 持久化操作身份 → 执行 → 保存结果与证据 → 发布 UI / 模型结果
```

取消发生在任一步都必须有可表达状态。执行前取消可标为未执行；执行后网络中断只能标为结果待核对。模型重新生成同一工具参数，也不能自动证明是同一个业务操作。

### 4.4 用“读取变更”拆解一个可用工具契约

设计一个 diff 工具时，至少要确定比较哪两个版本、是否包含未提交内容、输出是否截断、路径范围以及结果版本。只接受一个 project 字符串并返回大段文本，看似方便，却让后续报告无法说明审查的是哪个状态。

本文建议的概念结构如下，字段用于教学，不是当前项目 DTO：

```text
输入：project_id、base_revision、target_revision、paths、page
结果：resolved_revisions、changed_files、hunks、next_page、truncated
错误：invalid_revision / inaccessible / stale_baseline / execution_failed
```

模型据此能区分“没有差异”和“无法解析版本”。若结果太大，先返回文件摘要和分页引用，模型按风险读正文。报告也可记录实际比较的 revision，之后文件改变时提示证据需要更新。

同样的设计思路适用于搜索：字面匹配、语义检索、跨库聚合不应只用相同的 search 名称掩盖；工具说明应告诉模型何时使用，以及结果有哪些局限。工具 schema 保证参数形状，不能保证问题选择正确。

### 4.5 为何工具数量不是能力指标

一个低层 CRUD API 可能生成几百个工具，却仍要求模型自行理解业务流程；一个高层报告工具可以减少调用，但若把数据选择和推断全部隐藏，用户又无法审查。合适粒度在“用户可理解的操作”和“明确的权限、失败、重试边界”之间取得平衡。

可以用同一组任务比较两种工具设计：选对工具的比例、错误参数、重复调用、输出占用、最终任务完成。若一项复合工具只是把模型看不见的多次错误隐藏起来，调用数下降也不算能力改善。

## 5. MCP 的正式演进与“MCP 2.0”辨析

### 5.1 名称必须精确

本轮检索遇到三类“MCP 2.0”：

- 对 MCP `2026-07-28` 大幅修改的非正式称呼；正式协议仍使用日期版本。
- SDK 自己的主版本变化；SDK 版本与 wire protocol 版本不是同一个字段。
- Webflow 等厂商对自己 MCP 产品升级的名称。Webflow 在 2026-07-21 发布的 MCP 2.0 是其服务能力升级，不能据此判断任意 MCP 客户端使用了哪一版协议。[Webflow 原始发布](https://webflow.com/updates/introducing-mcp-2-0)

此外搜索会出现与 LLM 无关的 MOO Client Protocol。本文只讨论 Model Context Protocol，并使用明确日期版本描述技术事实。

### 5.2 2026-07-28 的变化及其架构含义

[正式变更说明](https://modelcontextprotocol.io/specification/2026-07-28/changelog)与[协议基本结构](https://modelcontextprotocol.io/specification/2026-07-28/basic)显示，本次改变覆盖无状态请求、发现、回传及扩展机制。以下按影响归纳，不作为完整迁移清单：

| 变化 | 要解决的问题 | 客户端 / 宿主应作的设计判断 |
| --- | --- | --- |
| 移除协议级 session 与初始化握手；每请求携带版本和能力 | 连接粘性给扩容与代理带来负担 | 对旧新版分别适配；业务 task 仍需自己保存 |
| `server/discover` | 无握手下仍需了解兼容性 | 把发现失败、版本不支持与认证失败区分 |
| MRTR 与 `input_required` | 服务端处理动作中还需要用户或客户端信息 | 待补输入应成为可恢复状态；响应后重新核对用户约束 |
| Tasks 进入官方扩展 | 长操作与客户端生命周期脱钩 | MCP task handle 映射外部操作，不代替产品 Task ID |
| 列表 / 资源缓存提示及 HTTP 路由信息 | 减少重复发现、方便中间层路由 | 缓存必须区分身份与可见范围；过期后重新发现 |
| Roots、Sampling、Logging 等进入弃用安排 | 精简核心、重新划分能力 | 弃用不是立即删除；不能写死“所有服务器都已迁移” |

**重要推论**：协议无状态仅表示每个请求携带必要协议信息。远端任务、文件编辑、登录状态和用户业务记录仍然有状态。连接断开也不等于副作用消失；不能把新版重发请求的通信要求误作任意写操作可安全重放的保证。

资料本身也有时效不一致：规范总览的扩展说明仍出现初始化协商的旧措辞，而基本协议与变更页明确改为每请求能力信息。实现时应核对具体版本的规范、schema 与一致性测试，不用总览的一句话推翻详细规则。

### 5.3 一次远端调用的各层身份与状态

以读取外部 PR 为例，宿主先确定连接的服务和当前身份，再发现可用能力，把合适工具呈现给模型。模型生成参数后，由宿主校验和执行；远端返回的数据再转换成内部结果。MCP 连接器处于模型与业务服务之间，但业务权限仍由服务端与宿主共同约束。

至少有四种身份不能混用：JSON-RPC 请求 ID 用于配对一次通信；tool_call_id 对应一次模型工具调用；外部操作 handle 用于跟踪可能跨请求持续的业务执行；本产品 task / run ID 关联用户目标与运行。一次用户任务会产生多个调用，一个外部操作也可能需要多次查询。

2026-07-28 基本规范明确每次请求携带协议信息，跨请求业务状态用显式标识引用，连接本身不代表会话。[基本规范](https://modelcontextprotocol.io/specification/2026-07-28/basic) 因此“断开并重连”与“开了一个新业务任务”没有必然关系；将进程生命周期绑定每个聊天也可能造成不必要重启。

若服务返回 input_required，宿主需要保留原请求与待补信息，取得相应输入后按协议继续。这不是工具已经失败，也不是自动获得继续副作用的许可。MRTR 解决消息交互，产品仍需明确用户看到什么、等待是否可取消、输入属于哪个运行。

Tasks 扩展解决长操作状态与结果获取。[官方扩展](https://modelcontextprotocol.io/extensions/tasks/overview) 对接时应把“请求已接收”“任务执行中”“结果可取得”分别显示；不能因为收到任务句柄就向模型报告业务已完成。

### 5.4 版本迁移为何需要矩阵，而不是改一个常量

客户端、SDK、服务器和产品部署可能处于不同阶段。旧服务器仍可能使用旧初始化和结果形状，新服务器按每请求元数据工作。宿主需要依据双方实际版本选择适配逻辑，不能用新规范发布日期假定生态同步升级。

一个可审查的矩阵至少包含协议版本、传输方式、认证模式、发现、结果类型、长任务、取消、恢复。矩阵中的“文档声称支持”“解析兼容”“真实连接通过”应分别记录。仅安装最新版 SDK 不能把全部格子标绿。

协议演进也会影响缓存。工具列表可以缓存，但身份、可见范围、版本变化后旧列表可能失效；工具名称相同，输入 schema 也可能已变。缓存键与失效策略应与能力身份关联，而不是只按 endpoint URL。

### 5.5 2026-08 路线图中仍未解决的事

8 月 22 日官方路线图把 agent 消息、HTTP 传输、身份、返回值与渐进发现、SDK 体验列为重点。Server Card、结果表示和大工具目录问题仍有推进中的部分。路线图描述的目标不等于所有 SDK 与宿主已经支持。[维护者原文](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/)

Skills over MCP 尤其需要谨慎：工作组页面的方向是基于 Resources 的扩展，列出的 SEP 与参考实现状态仍为 In Review，且客户端行为与安装包分发不全部属于该工作组范围。不能把主页出现“Skills over MCP”理解为已经存在完全统一的跨宿主执行规范。[工作组原始章程及状态](https://modelcontextprotocol.io/community/working-groups/skills-over-mcp)

## 6. 三种能力暴露方式的架构比较

### 6.1 全量原生工具

宿主把全部工具 schema 放入模型请求，模型直接选择调用。优点是透明、审计简单、延迟组成容易理解；少量稳定工具非常合适。缺点是目录增大后每轮承担 schema 成本，名称相似时选择难度提高。即使 prefix cache 命中，模型仍需要处理更复杂的能力空间。

### 6.2 动态发现与延迟加载

宿主先暴露搜索工具，检索候选后再载入完整 schema。系统增加的是一个“能力检索”层：注册信息 → 检索索引 → 候选筛选 → 运行时载入。它与文档 RAG 相似，但错误召回会直接影响可执行能力选择。

Anthropic 2025-11 的 advanced tool use 文章同时介绍 tool search、programmatic calling 和 examples，并以 Excel 场景解释大批数据处理价值；它们分别改善发现、执行与参数表达，不能当作一种功能。[原始工程说明](https://www.anthropic.com/engineering/advanced-tool-use)

本项目的设计问题是：搜索得到工具后，权限检查不能被“此前注册过”替代；服务器的描述更新后，旧版本 skill 是否仍适用；断连后是否显示能力不可用。必须观测目录召回率、错误工具选择及额外发现时延，而不只比较 prompt 变短了多少。

### 6.3 Code Mode / 程序化工具编排

Cloudflare 2025-09-26 的 Code Mode 将 MCP 能力映射为 TypeScript API；Anthropic 2025-11 的实践则展示如何在执行环境内组合、过滤数据，减少中间结果反复经过模型。[Cloudflare 原文](https://blog.cloudflare.com/code-mode/)、[Anthropic 原文](https://www.anthropic.com/engineering/code-execution-with-mcp)

例如，读取一批构建日志并计算错误分布时，模型可以写一次程序完成分页和汇总，最后只读取几十条统计。收益来源是减少模型回合与中间 token，而不是 MCP 协议突然具备推理能力。对依赖关系明确的批处理，它很有价值；对每一步都需要用户决定的修改，它可能隐藏过多中间状态。

真正需要补齐的实现包括：受限执行环境、只暴露允许的 capability、单次与累计预算、可中止异步调用、操作级审计、异常时已完成动作列表。生成代码拿到全局网络或文件系统权限，会使细粒度工具策略失效。程序内有十个 API 调用就应记录十个副作用边界，不能只审计“执行了一段代码”。

### 6.4 三种组织方式运行同一批量任务

假设要对 100 个构建结果统计失败类别，并挑出需要人工分析的十个案例。以下数字只是任务规模示例，不是性能实验。

**全量原生工具**：模型看到查询构建、读取日志、分类等 schema，每次决定下一次调用。它容易解释过程，适合需要频繁判断的分支；如果循环完全固定，很多模型往返只是在搬运数据。

**动态发现**：模型先找到“构建查询”能力，载入少量相关接口，再执行后续任务。它节约无关 schema，但查询词不准确可能漏掉正确工具。检索索引需要包含能力语义、输入要求和来源；不能只对函数名做向量搜索。

**程序化编排**：模型生成程序枚举构建、读取必要字段、做确定性分组，只把有歧义的案例送回模型。它把数据处理留在执行环境，减少上下文往返。Cloudflare 的公开设计通过 TypeScript API 与隔离运行环境提供这种组合路径；Anthropic 的材料也展示在代码中处理 MCP 返回数据。[Cloudflare](https://blog.cloudflare.com/code-mode/)、[Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)

实际选择可以混合：动态发现少量工具，再用代码批量读取，最后由模型分析异常。难点是失败可见性：如果第 42 项读取失败，最终统计必须标明未覆盖，而不是把它算成无错误；若已完成部分动作，重试也应只补缺失部分。

### 6.5 能力注册表应该保存什么

成熟的组织方式需要保存的不只是 name 和 description，还包括来源、版本、输入输出 schema、依赖、可用性、执行范围、取消能力和错误类别。模型看到的精简目录是这个注册表的一种视图，不能作为权限事实的唯一来源。

将“已安装”“可发现”“凭据可用”“可调用”“本次允许调用”分成不同状态，可以解释很多产品问题：工具已安装但当前没登录；登录成功但无目标资源权限；有权限但当前任务只授权读取。这些区别应通过明确错误与 UI 呈现，而不是反复让模型尝试。

## 7. 企业案例为何比工具数量更重要

Webflow 的 2026-07 产品升级把网站元素、组件、CMS、分析、分支、角色权限与活动日志结合。其价值不是“有一个 MCP endpoint”，而是 agent 操作能进入已有业务治理和可审查的工作副本流程。[产品发布](https://webflow.com/updates/introducing-mcp-2-0)

可迁移的经验是：外部工具首先应复用业务系统已有权限和审计；宿主仍要表达当前用户任务范围。Webflow 的功能公告不能独立证明修改质量或生产事故率，本文也没有连接真实账号试验。

另一个案例是 Anthropic 的 Excel 程序化调用：大量行数据在执行环境处理，仅把需要判断的结果送回模型。对本项目而言，对代码搜索结果去重、统计失败类别等也有类似潜力，但现阶段三个只读工具尚无足够规模理由立即引入通用 code-mode 子运行时。

## 8. 社区争论及判断

- **MCP 是否该被 CLI 取代**：CLI 便于 agent 使用已有训练知识，也适合本机工具；MCP 提供统一发现与认证连接。两者可以封装同一业务服务。缺少权限和结果语义的 CLI 不会天然更可靠。
- **Skill 是否就是 prompt**：内容可能主要是文本，但分发身份、触发、依赖、资源、版本和宿主行为使它成为一个可维护能力包。也不应为一段简单规则机械建立 skill。
- **“2.0”迁移是否已经统一完成**：官方规范发布、SDK 具备支持、服务器部署新版、宿主使用新版是四件事；需要实测能力矩阵。
- **发现越动态是否越好**：对小目录，检索多一个失败点；对大目录，全量暴露可能更贵。应按本机目录规模与任务分布比较。

这些争论在 MCP 工作组章程、8 月路线图、Cloudflare 与 Anthropic 的原始工程文章中均有直接线索；作者的设计判断不是生态共识。

## 9. 面向本项目的具体设计建议

建议先保持三个独立接口：`SkillCatalog` 描述工作方法，`ToolRegistry` 描述可执行能力，`ToolExecutor` 统一执行校验。它们是职责名，不是要求现在创建空接口。未来 MCP adapter 只负责将远端能力转换成内部描述和结果，不让运行核心依赖 MCP SDK 的全部原生对象。

内置 skill 需要版本化并记录每次任务实际载入内容；任务中途更新默认 skill 不应静默改变已经确认的工作方法。工具身份采用来源命名空间与稳定 ID，显示名不作为唯一权限键；来自不同服务器的 `search` 不应互相覆盖。

最小事件可包含 `tool_call_id`、来源 / 版本、当前项目与任务、策略结果、执行状态、产物引用、用量；敏感参数单独脱敏。遇到网络超时，结果应是“未知 / 待核对”，不笼统变成“失败，可重试”。MCP 的外部 handle、JSON-RPC 请求 ID 和本项目的任务 / 运行 ID 保持独立。

## 10. 何时值得采用

| 真实需求 | 优先动作 | 不宜提前做的事 |
| --- | --- | --- |
| 少量阶段方法可复用 | 内置有版本的 skill 与清晰产物要求 | 建技能市场和自动下载链 |
| 接入多个外部服务 | 确定 MCP adapter、认证和能力缓存 | 重写现有本地工具为外部服务 |
| 工具目录出现选择错误 | 先改命名 / 粒度，再试动态发现 | 仅以目录超过某个固定数自动切模式 |
| 大量确定性中间处理 | 评估程序化编排和隔离成本 | 把任意 `exec` 当成安全替代 |
| 长操作跨进程恢复 | 外部 Tasks 与内部操作台账映射 | 用 RPC 请求 ID 承担完整任务生命周期 |

验证重点是工具选对、参数正确、权限适用、取消清理和未知结果不重放。格式校验通过只说明 skill 可被解析，不能证明 agent 会在正确场景使用它。下一次更新应复核 MCP 新版实际 SDK / 宿主覆盖、Skills over MCP 的 SEP 状态和授权 / 扩展的具体兼容性。

## 11. 2026 年 9 月：能力目录开始与调用者身份一起管理

### 11.1 新协议落到 SDK 时，会出现第二层版本差异

[LangChain 2026-09-03 的 MCP 更新](https://www.langchain.com/blog/mcp-in-langchain-stateless-protocol-elicitation-and-more) 介绍基于 FastMCP 的 `langchain.mcp.MCPAdapter`、无状态协议支持、elicitation 和工具目录缓存。这一入口与旧 `langchain-mcp-adapters` 包不能仅凭名称视为相同实现；文章时点的新 Python 集成为 beta。协议已经发布、SDK 已实现、当前宿主已启用，仍然是三件事。

以需要用户补充输入的工具为例，工具调用暂停后，用户输入是对既有操作的续接，不能当成新的工具请求从头执行。无状态传输减少维持连接的负担，却不会消除操作身份、恢复句柄和业务状态。一个工具支持新协议，也不自动证明旧客户端理解它的等待与完成语义。

本研究建议能力登记保留协议版本、适配器版本、工具 schema 版本和所需扩展，按实际协商结果开放功能。发生兼容性问题时，产品才能说明是 schema 不匹配、扩展不支持还是服务不可用，而不是统一提示“工具失败”。

### 11.2 Connections：凭据类型与凭据所有者是两条轴

[2026-09-09 的 Connections](https://www.langchain.com/blog/connections-managed-credentials-and-per-caller-identity-for-managed-deep-agents) 将命名连接、凭据管理与调用者身份结合，区分 Agent 所有和调用者所有的连接；secret / OAuth 则是另一维度。这是托管产品能力，不能直接归入开源 MCP 协议本身。

例如同一个 `search_documents` 工具为甲、乙两位用户服务，名称和参数完全一样，实际可访问的空间却不同。若只按工具名称缓存结果或目录，甲看到的能力可能被错误用于乙。采用共享服务账号与采用用户 OAuth 的产品体验也不同：前者更容易统一运维，后者更贴近用户已有权限。

对能力组织的具体启示是，目录至少有两个阶段：先决定当前主体可见哪些能力，再决定当前任务需要加载哪些能力。语义检索只负责后者。模型选择某个连接名，不应改变由受信宿主确定的实际调用主体。

### 11.3 目录缓存与在途调用怎样兼容

下面是本研究的工程推演。缓存键可以包含服务、主体、授权版本、协议与工具 schema 版本；具体实现按成本裁剪。运行中授权被撤回时，下一次实际执行仍须判断当前有效范围。缓存 TTL 只能限制陈旧时长，不能替代撤权判断。

若工具描述发生变化，已提交调用应关联提交时的参数 schema；后续回合使用新版本。直接原地覆盖目录会使历史轨迹难以解释：日志显示一个工具名，却不知道它当时要求什么参数、执行什么操作。程序化工具调用也需要这种版本关系，否则生成代码可能基于旧签名运行。

这使“组织方式”的落地点从文件夹命名延伸到能力生命周期：发现、装载、绑定身份、执行、变更与撤回。跨 Agent、编辑器和界面则另有协议职责，详见新增的 [Agent 协议专题](11-agent-protocols.md)，不要把它们都放进 MCP 一栏。
