# 对本项目的参考：从一次任务的入口、执行到下一次接续

> 2026-09-23。本篇汇总新一轮筛选后的结论，依据当前工作区的 M4 进度及实际源码；不沿用 9 月 21 日“尚无 Skill / MCP”的旧判断。它是一份后续设计依据，不启动实现、安装第三方运行时或更改既定产品规则。

## 1. 最值得吸收的不是插件数量，而是完整任务的连续性

本轮最值得优先学习的三条产品路线是：OpenDesign / Archify 把模型能力组织成可编辑成果；Anywhere / BrowserSkill 把启动、取消、退出和恢复做成用户能理解的生命周期；LoopX / 两种 Agent Team 把工作身份与某次会话、某次执行区分开。它们分别改善“完成什么”“执行是否可掌握”“下次怎样接着做”。

这些判断综合了关注度、源码机制、用户问题和本项目适配程度。Star 让 Archify、Distilly、EverOS、MemOS 等新样本进入主线，防止选择只受先前熟悉程度影响；对 wowyuarm 团队、billion-context 等低热度项目则只推荐其中明确可验证的机制。没有取得可比较的付费率、留存或 DSH 企业部署规模，不能给出“工业成熟度第一名”式排序。

## 3. 进入任务：让能力围绕用户要交付的东西组织

### 用户价值与上游证据

OpenDesign 从设计、页面、文档等成果出发，把 CLI 会话放在后面；Archify 给模型结构化规格与生成链，产物可以继续修改。这比让用户先理解 Agent、MCP、Skill、插件、runtime 的关系更容易上手。[工作台分析](02-workbenches.md)、[Skill 与成果分析](05-skills.md)

对于本项目，一个“修改登录页”的任务应自然连到相关文件、预览、差异和运行结果；一个“整理架构”的任务可以留下规格与文档，而非只在回答中出现一张不可维护的图。已有成果区和 Skill 能承接这种组织方式，未必需要新建复杂 artifact 平台。

### 可吸收的最小机制

任务保留用户目标；运行保存真实调用与产物；成果入口显示文件当前状态及其来自哪个 run；下一轮能明确引用该成果继续修改。若某类 Skill 自带生成脚本，保留输入规格和生成说明即可形成可重复工作链。

不要让所有任务填写统一成果表，或把图示检查泛化成编程检查。普通文件编辑已有可靠链路时，无需再包一层产物协议。只有当用户确实反复丢失结果、无法重生成或不知道从哪继续时，这项增量才有确定收益。

## 4. 准备请求：把能力发现、实际加载与效果区分开

### MCP 和 Skill 的共同问题

BrowserSkill 成功使用 Skill 后再露出工具；MCP manager 分开 composition、连接和 schema；SkillCorpus 默认改为按需检索。这说明“安装了”和“本次模型能调用”是不同状态。我们当前 MCP 已在发现工具返回后，将选中 schema 加入下一次请求，并按 session 保存；Skill 也只提供有效目录、用户选择和按需正文。[MCP 当前实现](../../../src/my_agent/mcp_client/service.py)、[上下文与生命周期分析](07-context-and-lifecycle.md)

后续可以优先改善解释：这份材料从哪个项目 / 资源库来，为什么选中，正文或附件是否已可读，修改何时生效。如果使用远端能力目录，需要说明本次失败是无匹配、网络不可用还是附件无法落地，不能一律显示“未找到”。

### 何时才值得加智能路由

Vibe-Skills 的本地选择与 SkillCorpus 的多来源检索分别适合不同规模。小目录优先清楚名称、触发条件、显式选择和无匹配退路；候选很多、名称难记且真实误选频繁时，再考虑查询路由。引入辅助模型会增加请求、延迟和费用，收益必须由同类任务的正确选择率及最终完成情况判断。

作者 benchmark 中的最高 reward / 最低 token 筛选规则已在正文解释，不能直接当作我们采用后会降低 29.6% token 的依据。也不需要为了本次纯研究新建评测平台；真正决定引入时，用能覆盖目标问题的少量真实任务作对照即可。

## 5. 长任务执行：先保持来源，再考虑更复杂的记忆

### 短期上下文与长期记忆应该怎样衔接

dsh-context 的事件投影解释实际请求，billion-context 的压缩块保留原文回读，EverOS / MemOS 再把任务经历提炼成可复用材料。这三层不是同一份“记忆库”。当前任务尚未完成的工具结果首先是执行事实，压缩后的摘要是请求表示；是否值得形成长期事实或 Skill，应该另有选择依据。[记忆分析](04-memory.md)

本项目已有摘要来源与回读，优先保证用户可以从一句摘要找到原始依据，以及知道记忆为什么影响了本次回答。记忆更新有错误时，应能纠正具体记录，不通过清空整个系统解决。多人 / 多端共享尚非当前默认场景，OpenViking、EverOS 服务不能仅因架构完整就变成桌面启动依赖。

### 前台延迟与后台整理

MemOS 把召回期限和后台 capture 分开；EverOS 还考虑新会话召回前旧会话材料是否已 flush。可学习的是显式表达写入与可检索之间的时间差。如果后续用户抱怨“刚说过却查不到”，应先确定是没有记录、尚未索引、检索没命中还是没有放入请求，而不是立即更换向量数据库。

后台整理的失败需要可见，但不能把所有可选记忆处理都塞到主回答之前。跨会话等待可以增加新鲜度，也会增加首个请求延迟，两者要按用户实际感受取舍。

### RSI 应该怎样定位

RSI 值得讨论，但不能用它替代实现说明。Distilly 的资料更新、MemOS 的经验到 Skill、EverOS 的离线反思属于不同层次的反馈循环。要提出更强的递归改进主张，需要解释是否改进了改进机制本身，以及多轮独立任务的收益和退化如何确认。我们近期可采用的方向是“带来源的候选方法 → 人能看懂的修改 → 有版本地再次使用”，不默认让运行时自改写、自动发布或用模型自评分选优。

## 6. 多会话协作：身份与送达语义比角色名字更重要

### 现有基础与上游增量

我们的协作消息已经按 operation ID 去重，先持久保存，在下一请求边界进入接收方；只有完整模型回合消费后再记录 delivered_run_id。查看消息不触发模型，重启也不因未读消息自动开始工作。这已经与本轮多个成熟机制方向一致。[当前收发实现](../../../src/my_agent/collaboration/service.py)

LoopX 的 reservation 区分排队、领取、接纳和退役；Nanmi 的 attempt 约束旧执行回调；wowyuarm 分开长期成员与具体 session。它们提示下一步应优先解决：工作转给谁、接收方哪一次执行用了哪些材料、fork / 换会话后关系是否仍然正确、迟到结果属于哪个 attempt。[协作分析](03-collaboration.md)

### 对用户可见的改进

例如用户让分析任务把结论交给实现任务，应看到消息已保存、在哪次运行被消费、实现产生了哪些成果，以及是否还有需要原分析补充的问题。消息送达不应直接显示“协作已完成”；一个 worker 完成也不等于总任务完成。现有 task / session / run / message 身份足够支撑许多这种关联，不必先引入新的团队控制平面。

只有当用户确实需要长期角色跨多个会话持续存在时，再讨论独立 Member 身份、成员替换和共享任务账本。自动团队、可执行 DAG、远端分布式队列分别是更大的产品选择，不能只因存在多会话就一起加入。

### 不照搬的行为

上游部分团队带自动重试、报告审核或复杂阶段门槛；这些与本项目现有故障停止、最小 summary / outcome、原目录协作规则不同。可以吸收幂等和身份机制，同时保留既定行为。成员连续性也不自动提供共享目录文件隔离，仍需分工范围和写入冲突反馈。

## 7. 工具执行与 UI：可观察，不制造第二份业务事实

BrowserSkill 的截图观察与模型动作分开，队列却共用资源顺序；OpenDesign 在给外层终止结果前 flush 会话；Anywhere 用启动 generation 清理已失效流程。这些都涉及同一个问题：晚到的异步结果不能覆盖新任务的状态，旁观行为不能改变工作本身。[浏览器分析](06-browser.md)

我们可据此检查以后新增的浏览器、预览或 worker UI：它展示哪个 run，资源由谁创建，用户停止后清理走到哪里，重开页面是否只恢复显示而不重放副作用。当前 Trace 已从会话事实投影，应继续复用这一事实源；只有日志量真的造成性能问题时，再增加可重建缓存。

Windows runner 的 `exit` / `close` 区分也有价值。孙进程持有 stdout 句柄时，主子进程退出不保证管道立即关闭；但强行早退也可能丢失最后输出。应按实际执行后端修正对应收尾，而非为全系统增加固定睡眠或通用超时门槛。

浏览器 Agent Window、参数数组、工作目录和 Job Objects 均不能单独代表操作系统文件 / 网络沙箱。本项目默认本机执行与可选沙箱方向保持不变，后续隔离能力以真正的系统边界说明。

## 8. 保存与更新：对当前 Skill 资源适度借鉴，对运行时扩展另行评估

iPolloWork 把扩展版本 artifact 与 workspace 激活投影分开；dsh-market 和 Anywhere 保留配置快照与更外层恢复入口。它们分别解决资源版本归属和宿主可能无法启动的问题。对我们目前的 Skill 文本 / 附件更新，最有价值的是显示来源、当前激活版本、用户是否修改过、下一请求何时采用，以及失败后能否保留原内容。

没有必要立即引入完整插件装配树、远程市场后端和救援进程。只有新增可执行扩展真正会破坏主进程 / 后端启动时，才需要扩大到这种恢复架构。多文件补偿应如实显示部分失败，不能因为有 backup 字段就叫事务；恢复配置也不等于回滚用户项目或外部操作。

市场旧版 profile 误判案例还提醒我们：继续由 Python 管业务元数据、由明确项目身份决定位置，不从启动参数缺失推导一个默认目标去写。M4 已有资源库与项目导入边界，应沿这个职责继续维护。

## 9. 建议顺序：用户收益、改动范围与证据放在一起

以下是设计优先级，尚未变成实施工作项。

| 顺序 | 具体问题 / 用户收益 | 借鉴对象 | 可控制的增量 | 采用前需要的最小证据 |
| --- | --- | --- | --- | --- |
| 优先 | 找到成果并继续编辑，减少跨会话重复解释 | OpenDesign、Archify | 关联现有任务、run、文件与生成输入 | 真实接续任务中能定位并继续修改，已有文件不被错误覆盖 |
| 优先 | 能解释这次请求用了哪些能力 / 资料 | dsh-context、MCP manager、SkillCorpus | 基于既有请求材料与 Trace 增强来源和生效说明 | 一次具体误选 / 不生效问题可以定位到实际材料与配置 |
| 优先 | 协作消息与结果可追踪，fork / 接续不混淆 | LoopX、Nanmi、wowyuarm | 复用既有身份补关联导航与生命周期说明 | 具体交接场景中送达、消费、完成可区分；旧结果不覆盖新运行 |
| 按问题推进 | 更新 / 停止后状态清楚且可恢复 | Anywhere、market、BrowserSkill | 处理真实资源所有权与收尾缺口 | 仅针对遇到的未决启动、迟到结果或更新失败验证 |
| 次级 | 让确认过的方法跨任务复用 | Distilly、MemOS、EverOS | 生成可审阅的候选 Skill，保留来源和版本 | 后续任务确实使用且减少重复探索，没有由自评替代结果 |
| 规模触发 | 大量能力中找到合适选项 | Vibe-Skills、SkillCorpus | 可解释检索 / 路由，控制额外请求 | 本地目录确有误选问题，收益超过延迟和成本 |
| 场景触发 | 网页操作 / 预览验收 | BrowserSkill、dsh-browser | 先明确浏览器会话与项目 / run 归属 | 有真实网页任务需求；取消、页面所有权与结果清楚 |
| 后置 | 常驻团队、跨端共享记忆、多引擎平台 | LoopX、OpenViking、iPolloWork | 单独产品设计，不混进局部优化 | 明确多端 / 多运行时用户需求及可维护成本 |

## 10. 工业价值与演化路径的最终判断

从源码和使用报告看，生态中最有工程内容的进展常发生在成功路径之外：请求发出但结果未知、安装完成但新版本没有运行、队长会话已 fork、记忆已写但还不能检索、图已生成但未通过交付检查。这些问题解释了为何成熟产品逐步增加身份、版本、日志、取消和恢复边界。

本项目当前已具备核心执行与资源基础，下一阶段更适合沿真实使用问题加强这些边界。它可以逐步从“会话完成一次操作”发展到“任务保留成果与依据，再由多个会话接续”，而不需要先成为通用插件平台。对于企业采用规模、作者性能数字或强 RSI，证据尚不足的地方继续保留限制；对于可读源码中的明确机制，则可以立即作为后续方案比较依据。
