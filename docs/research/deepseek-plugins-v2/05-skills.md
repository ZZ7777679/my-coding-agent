# Skill 怎样产生实际价值：成果生产、经验蒸馏与能力检索

> 2026-09-23。本篇分析 Archify、Distilly、Vibe-Skills 和 SkillCorpus 的固定源码。Star 为本轮统一快照，版本和阅读范围见 [证据登记](09-evidence.md)。未安装或运行这些项目，也未重跑作者评测。

## 1. 从“装了很多 Skill”到“完成了一件事”

Skill 通常是一份可按需加载的任务说明，连同脚本、模板和参考资料构成一个能力包。它不是模型的新权重，也不自动成为宿主可以可靠调度的工作流。实际使用至少要经过四步：找对能力、理解输入、执行方法、保存可检查的结果。大量插件只解决第一步的目录展示，用户仍需要自己判断其余三步。

这次选择四种不同路线：Archify 把自然语言意图变成有结构的图示成果；Distilly 把人的材料整理成工作方法和 persona；Vibe-Skills 组织任务与已有能力之间的选择；SkillCorpus 则处理更大规模的收集、去重、检索和附件交付。它们的关注度分别为 70,122、24,978、3,412、665 Star。这个差距说明成果与场景表达值得研究，但不能证明后一种基础设施价值更小，也不能把整个仓库的热度归因于 DSH 适配器。

| 项目 | 用户得到什么 | 核心状态 | 主要确定性边界 |
| --- | --- | --- | --- |
| Archify | 可打开、编辑、导出的架构 / 流程图 | 结构化规格、候选 HTML、交付回执 | schema、布局与产物检查、最终文件替换 |
| Distilly | 可复用的工作方法与人物表达资料 | work / persona 文档、元数据、版本备份 | 文件生成、按章节更新和回滚；内容提炼仍依赖模型 |
| Vibe-Skills | 当前任务适合使用哪些已安装能力 | 能力目录、路由结果与理由 | 本地评分、显式选择、弱匹配分支 |
| SkillCorpus | 从多来源找到适合任务且能读到附件的 Skill | 语料记录、索引、来源、bundle 缓存 | 去重、排序、检索期限和资源路径解析 |

## 2. Archify：模型负责表达，程序负责把表达变成成果

### 2.1 仓库按“能力包—工具链—宿主适配”组织

固定提交 `8809b273c278a813a47fa37698864779c0d4cf08` 的核心包是 `archify/`，其中 `SKILL.md` 告诉模型如何选择图种、准备输入及交付；`schemas/` 定义结构；`renderers/` 实现不同图种；`bin/archify.mjs` 提供统一命令；`scripts/` 提供检查等辅助能力。`integrations/deepseek-harness/` 是独立的薄适配层，而非另写一个 Agent 循环。核心 package 为 `2.17.0-dev.1`，DSH 适配包为 `0.2.0`，不能把开发分支版本称作已经发布的稳定版。

DSH 的 `cordis.patch.yml` 加入 filesystem Skill provider，通过 profile 对应的 `createRequire(baseUrl)` 解析已安装包的 `package.json`，再定位包内 `skills`。这里的设计重点是“从包身份定位资源”，不是把宿主工作目录和安装目录硬拼起来。这样用户切换项目时，Skill 附件仍属于同一个已安装能力。[适配声明](https://github.com/tt-a1i/archify/blob/8809b273c278a813a47fa37698864779c0d4cf08/integrations/deepseek-harness/cordis.patch.yml)、[能力入口](https://github.com/tt-a1i/archify/blob/8809b273c278a813a47fa37698864779c0d4cf08/archify/SKILL.md)

### 2.2 从用户请求到结构化规格

用户提出“解释这个服务架构”后，模型首先识别适合 architecture、workflow、sequence、dataflow 或 lifecycle 哪一种表达，再读取该图种的 schema、共用规则及示例。它不需要把整个仓库的所有渲染实现放入上下文。模型产出 JSON 规格：节点、连接和语义由模型组织，布局、样式和交互由对应渲染器处理。

这是一种有价值的职责切分。直接让模型生成完整 HTML，样式、坐标、连线和语义一起变化，局部修改容易牵动整个成果；保留规格文件后，“新增一个审批分支”可以先修改图的结构，再重新渲染。仓库中的 workflow 新旧规格处理、编译和几何计算，也表明它在向可维护的图示工具链发展，而不是只积累更多提示词模板。

但结构有效不等于架构理解正确。schema 能发现字段、类型或连接问题，不能单独证明模型没有遗漏一个服务。带源码证据的产物仍需检查证据是否支持图中陈述，不能把回执中的 verified 扩大解释为所有设计事实都已被证明。

### 2.3 交付是一条有失败边界的流水线

`deliver` 的关键流程是：保存本次规格快照 → 在输出目录建立临时候选 → 调用渲染器 → 检查候选产物 → 解析检查回执 → 读取候选字节及可选源码证据 → 再次解析目标路径 → rename 为最终输出 → 按需打开。渲染失败、检查失败、回执解析失败及提交失败分别报告；候选没有通过前保留已有成果。[交付实现](https://github.com/tt-a1i/archify/blob/8809b273c278a813a47fa37698864779c0d4cf08/archify/bin/archify.mjs)

冻结规格的意义在于，回执描述的是实际参与渲染的那份输入，而不是命令结束时可能已经改变的源文件。检查候选再替换，减少了用户拿到半成品或旧成果被失败运行覆盖的情况。同目录暂存和最终 rename 是单个成果文件的提交边界，不能说它为整个项目、多个附件和浏览器打开操作提供了事务。

### 2.4 对本项目的价值

它值得优先研究的原因是用户可以马上辨认结果：一张可复用的图，而非新增一个不知何时该用的按钮。我们已有 Skill 附件导入和成果展示，可借鉴“规格文件 + 可重复生成命令 + 最终产物”的表达，让后续修改接续原成果。

不需要因此给所有 coding 任务新增九项检查或强制图示报告。Archify 的检查服务于它自己的图形交付契约；移到一般编程任务时，应只保留与实际产物有关的检查。MIT 允许的复用仍需保留来源和许可，本轮只判断机制与产品价值，没有证明本项目中渲染效果或调用成功率。

## 3. Distilly：把个人材料变成可维护的能力资料

### 3.1 它解决的需求与 persona 的位置

Distilly 从早期 ColleagueSkill 方向扩展到不同 Person Profile 场景。用户提供工作文档、沟通材料或公开内容，系统提炼工作方式以及人物表达，之后以 Skill 形式复用。吸引力来自“让已积累的方法继续帮助做事”，不等同于通用长期记忆，更不能把生成的 persona 当作一个人的真实心理模型。

固定提交 `b830d3dcbde006370f141155795b89021e3a947b` 的仓库包含统一 `SKILL.md`、分析 / 构建 / 合并 prompts、Python 材料与文件工具。分析和写文件分开：前者主要依赖模型遵守提示，后者负责确定的目录、文档和版本行为。`SKILL.md` 的版本为 `1.0.0`，这是能力包标记，不是所有工具独立发布的版本。[入口](https://github.com/titanwings/distilly/blob/b830d3dcbde006370f141155795b89021e3a947b/SKILL.md)、[提示组织](https://github.com/titanwings/distilly/tree/b830d3dcbde006370f141155795b89021e3a947b/prompts)

### 3.2 材料如何经过分析进入能力包

使用流程先确定对象与材料范围，再分析工作规则和 persona，之后由构建提示生成内容。`skill_writer.py` 把结果组织成工作文档、persona 文档、主 Skill、元数据及 manifest。主入口可以引用细分资料，避免每次使用都把所有原始材料和分析中间结果重新放入上下文。

这种分层有实际意义：工作方法回答“怎样处理这类事”，persona 回答“用怎样的风格表达”。混在一个自由文本提示里，更新表达偏好容易意外改写工作原则。分文件后能够分别修订，也方便说明当前答案用了哪些资料。仓库中关于 persona 优先级的描述属于给模型的行为指导，不能代替宿主权限规则或当前用户指令。

### 3.3 更新不是简单追加，也不是可靠的语义合并器

更新入口先读取元数据，计算下一版本，备份当前主要文件，再分别合并 work / persona patch 或应用 correction，最后重写产物。`merge_markdown_patch` 的实际手段是按 Markdown 二级标题定位章节，替换同名部分或追加新章节。这样比无界追加容易维护，但标题相同不表示内容语义完全对应；“冲突时询问用户”的要求主要写在 merger 提示中，并非文件工具能自行识别全部语义冲突。[写入与更新](https://github.com/titanwings/distilly/blob/b830d3dcbde006370f141155795b89021e3a947b/tools/skill_writer.py)、[合并提示](https://github.com/titanwings/distilly/blob/b830d3dcbde006370f141155795b89021e3a947b/prompts/merger.md)

版本工具保留有限历史，并可复制回旧产物。这里有可恢复性，但主要文件是顺序写入 / 复制，不能称为多文件原子提交。模型生成过程中可能出现不准确归纳，版本号增加只说明发生了更新，不能证明能力变强。[版本管理](https://github.com/titanwings/distilly/blob/b830d3dcbde006370f141155795b89021e3a947b/tools/version_manager.py)

### 3.4 演化与本项目参考

最有价值的可迁移部分是：把一次任务里经过确认的方法整理成独立候选 Skill，保留资料来源、纠错记录和历史版本，再由后续任务选择使用。我们已有记忆纠错及 Skill 编辑，真正的增量是两者之间可解释的转换，而非再造一个 persona 管理中心。

应区分三种演化：补充个人资料、修改任务方法、改变运行系统本身。Distilly 主要在前两层；它没有因此证明递归自我改进（RSI），也没有提供能力持续提升的受控评测。用于团队方法沉淀的工业价值是推断，不能由 24,978 Star 直接推出企业留存或生产覆盖规模。

## 4. Vibe-Skills：选择能力需要理由与退路

### 4.1 仓库已从脚本入口向共享运行核心迁移

固定提交 `ddcaa2affca93c1efe026d008b6b93709e5fb7e2` 中，原 `scripts/router/invoke-pack-route.py` 已是薄入口，实际 CLI 位于 `apps/vgo-cli/`；旧的 runtime-neutral contract 路径也转发到 `packages/runtime-core/src/vgo_runtime/router_contract_runtime.py`。因此只阅读旧脚本会误以为系统没有实现，或把已迁移逻辑当成当前主入口。

核心目录构建能力目录并统一输出路由结果，宿主集成和 CLI 使用这份逻辑。它的设计意图是减少不同 Agent 各维护一套选择规则，而不是让某个特定 DSH UI 独占能力组织。[当前路由核心](https://github.com/foryourhealth111-pixel/Vibe-Skills/blob/ddcaa2affca93c1efe026d008b6b93709e5fb7e2/packages/runtime-core/src/vgo_runtime/router_contract_runtime.py)

### 4.2 当前请求怎样选出能力

`route_prompt` 先定位宿主 / 目标目录并生成已安装 Skill 目录，按任务词、能力、领域和名称等信息计算本地分数，再以来源优先级、次序和身份稳定排序。显式请求某个已安装 Skill 与自动选择走不同分支；显式目标不存在时返回这一事实，而非假装匹配成功。

自动路由还看最高分与次高分的差距。强匹配可直接给出推荐；弱匹配进入需要宿主判断、近似候选或组合能力的分支；没有本地候选则保留明确的无匹配结果。因此，至少这条当前实现不能概括为“每次调用另一个 LLM 来挑 Skill”。本地路由可以节约辅助模型调用，但词项和规则对表达变化的泛化能力仍需实际任务验证。

对用户有意义的输出不仅是 Skill 名称，还有为什么选中、是否明确请求、有哪些近似候选以及是否根本没有匹配。这些信息可以解释一次错误选择，也支持用户纠正下一次使用方式；不必把它们全部变成执行前的确认表单。

### 4.3 作者评测显示了什么，又不能说明什么

作者公开的 full-skills-comparison 基于 SkillsBench 1.1 的 87 个默认任务，比较整理后的 Skill 集合与其治理方案。研究材料说明：232 个实例按目录名形成 195 个唯一名称，包含 15 个重复目录与 8 个同名异内容冲突，冲突取字典序第一份；82 个任务两侧有数值 reward，81 个有完整 token 记录。作者报告平均 reward 从 0.503 到 0.714，约提高 **21.1 个百分点**，95% bootstrap 区间为 0.101—0.323；总 token 降低约 29.60%。[作者评测方法与结果](https://github.com/foryourhealth111-pixel/vibeskills-benchmark/tree/main/studies/full-skills-comparison)

关键限制是，同一条件存在多份有效记录时，材料明确选择最高 reward，再在该 reward 下选择最低 token。这不是所有尝试的平均，也可能低估真实调用成本。该研究使用 V4.1.0、DeepSeek V4 Flash-VE 和 OpenHands；有任务级 CSV，但未公开完整原始轨迹。本轮没有重跑。因此可把它视为“能力治理可能有收益”的作者证据，不能称为独立复现，也不能把 21.1 个百分点预测到本项目当前模型、网关和 DSH 适配。

### 4.4 对本项目的吸收尺度

我们当前已有九项预装 Skill、在线导入和用户选择，不需要为了能力数量好看就引入整套框架。先借鉴可解释的匹配结果和无匹配退路，观察真实用户是否确实经常选错能力；目录规模和误选问题增长后，再决定是否需要统一路由。仓库中复杂治理规则、审查链和复合模块也不能自动转化为本项目新的运行门槛。

## 5. SkillCorpus：从目录质量到请求时检索，再到附件可用

### 5.1 两条链共同组成仓库

固定提交 `7b3a0eaec5594b7f6cb301189c3d626f15409ed0` 需要分成离线语料链与在线宿主链。`skillcorpus/aggregate` 发现 / 收集仓库；`curate` 解析、筛查、评分、去重、分类、嵌入和存储；`match` 准备匹配模型的数据、训练、评估及服务；`skillcorpus_plugin/engine-typescript` 才是本篇重点的 DSH 检索实现，包名 `@evermind-ai/dsh-skill-search`，版本 `0.4.0`，Apache-2.0。

语料侧保留来源 URL、路径、许可、内容身份、分类与质量等数据，不只有 name / description。对于同一个根 Skill 下的嵌套 SKILL 路径，收集器会避免把附件能力重复计数；近似去重还综合质量、来源权重和新旧关系。质量分数是整理算法的判断，不能改名为用户效果分。[整理流水线](https://github.com/EverMind-AI/SkillCorpus/blob/7b3a0eaec5594b7f6cb301189c3d626f15409ed0/skillcorpus/curate/pipeline.py)、[数据模型](https://github.com/EverMind-AI/SkillCorpus/blob/7b3a0eaec5594b7f6cb301189c3d626f15409ed0/skillcorpus/core/models.py)

### 5.2 当前 DSH 默认是按需检索，不能只信文件头注释

`src/index.ts` 顶部仍以每轮检索描述系统，但当前配置默认 `mode: on_demand`，注册 `skill_search` 工具；只有显式 `auto` 才进入 `agent/pre-step`，根据最近用户文本搜索，并把来源标记和 Skill 身份连同内容加入本次请求。两个模式互斥，以免同一轮搜索与注入两次。

按需模式让模型在确实缺少方法时支付检索成本，缺点是模型必须意识到需要找能力；自动模式有助于发现用户和模型都不知道的能力，但每轮都可能增加等待和不相关材料。需要结合真实任务决定，而非把“自动”视作必然更先进。能力正文作为请求材料进入模型，也没有获得修改宿主规则或扩大执行权限的资格。[入口与模式分支](https://github.com/EverMind-AI/SkillCorpus/blob/7b3a0eaec5594b7f6cb301189c3d626f15409ed0/skillcorpus_plugin/engine-typescript/src/index.ts)

### 5.3 检索流水线怎样把候选变成能用的资源

引擎按以下顺序运行：重新校验本地目录状态 → 可选查询改写 → 并行搜索本地与远端来源 → 按来源权重融合排名 → 获取正文 → 去除完全相同正文 → 解析本地附件引用 → 可选 LLM 筛选 → 限制最终数量 → 下载 / 展开真正入选的远端 bundle → 解析最终资源路径。

其中 RRF 融合的是各来源排名，不要求 BM25 与远端向量得分具有相同数值范围。可选筛选会参考当前可调用工具，以免推荐一个必须依赖宿主不存在能力的 Skill。查询改写仅改善检索词，不承担判断是否禁止检索的职责。先选择再下载 bundle，避免为大量最终不会使用的候选付出下载与解包成本。[检索核心](https://github.com/EverMind-AI/SkillCorpus/blob/7b3a0eaec5594b7f6cb301189c3d626f15409ed0/skillcorpus_plugin/engine-typescript/src/engine.ts)

附件处理尤其有现实价值：一个 Skill 的说明写着运行 `{baseDir}/scripts/x.py`，如果只注入正文而没有让脚本落到可访问位置，就只是“看起来接入了”。它先解析本地引用再筛选，避免把真实存在的本地脚本误判为不可用；远端落盘失败可能保留未解析正文，同时记录诊断。因此上层必须能区分匹配成功与资源准备完整，不能仅凭返回正文宣称已可执行。

### 5.4 性能、失败与模型成本

各来源搜索失败被隔离，慢服务有期限，诊断记录来源、阶段和耗时；一个目录不可用不应拖垮全部检索。但是最外层 `hits()` 还会捕获异常返回空数组，所以移植时应保留具体失败信息，避免把网络故障显示成“没有匹配 Skill”。本项目对实际调用故障已有停止规则，不能未经决定照搬上游的整体降级语义。

`skillcorpus/match` 目录另外提供 bi-encoder、reranker、查询合成和训练评估。这些属于可选的匹配模型建设路线，不是 TypeScript 插件每次运行都必然启动一套本地 GPU 模型；检索指标如 nDCG / MRR 也不能等同于编程正确率。[匹配系统说明](https://github.com/EverMind-AI/SkillCorpus/blob/7b3a0eaec5594b7f6cb301189c3d626f15409ed0/skillcorpus/match/README.md)

## 6. 四种路线的演化与本项目的优先顺序

这些项目展示的演化不是统一走向“更多 Agent”。Archify 从提示包向可重复生成的成果工具链发展；Distilly 从一次蒸馏向版本化资料维护发展；Vibe-Skills 从零散脚本向共享选择契约发展；SkillCorpus 从目录向语料质量、在线检索与完整附件交付发展。上述判断来自当前目录、兼容入口和文档描述，不是完整发布历史或商业发展史。

对本项目，近期最有价值的是让 Skill 使用后留下可接续成果，以及让来源、附件与生效版本可解释；接下来才是把确认过的方法沉淀为候选 Skill、改善错误选择。大规模在线路由和自动演化需要真实误选率、任务成功率与额外延迟支持。本篇没有取得可核实的 DSH 插件企业部署规模，不能用测试目录、作者 benchmark 或 Star 代替生产采用事实。

与记忆系统中的 Skill 生成一样，这些方案可以构成“观察—整理—修订—再次使用”的局部反馈循环。要讨论更强的 RSI，还须说明改进对象、评价信号、错误反馈、版本选择和多轮收益是否持续；单次生成、版本递增或模型自评均不足以完成这条论证。
