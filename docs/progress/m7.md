### 诊断与修复

- 实际提示来自 `main/backend.ts` 的 32 个待响应请求容量，Python 普通 RPC 同时按控制队列处理。打开会话自动发出的历史、Goal、上下文、记忆和侧栏读取会反复解析同一完整日志；全局信息／活动运行轮询没有在途去重，其他组件只丢弃迟到响应但仍重复派发。慢读取因此可能积压，并非用户又启动了任务。
- 在当前开发数据根只读测量最大旧日志：6,820,093 字节、741 条事实，完整解析约 0.560 秒，上下文／记忆读取分别约 0.638／0.590 秒。未输出正文、请求模型、修改个人记录或启动其工作；这些时间是本机样本，不代表所有历史的表现。
- `SessionStore` 增加按文件身份、大小和修改时间失效的解析缓存，追加前失效，缓存列表与调用者独立；原损坏前缀和保存错误语义保留。缓存大小集中在 `defaults.json`，32 MiB 以原日志字节计量，仅决定淘汰，不拒绝或截断大日志；不是实际 Python 堆内存硬上限，不生成 hash／新执行门槛。
- 同一实际日志复测首次解析 572.44 ms，随后两次 0.95／0.79 ms；这是重复磁盘解析的改善，不是声称完整首开界面耗时只有 1 ms。上下文查询同时复用已组装历史和 token 估算，避免同次查询重复计算。
- 全局轮询增加在途去重。上下文、子任务、Goal 和侧栏复用一个轻量刷新 Hook：同组件一项在途读取，变化合并为最后一次刷新，失效回包不覆盖新选择，Goal 恢复轮询从请求完成后计时。记忆列表仅展开相关面板时读取，普通会话自动召回逻辑不变。
- 修正输入区 ContextMemory／Workers、侧面板 Checkpoints／Trace／Changes 的同级重复 React key。会话历史读取错误与用户操作错误分开，读取成功清除旧忙碌提示；没有调高 RPC 队列、增加自动模型重试或隐藏真实读取失败。
