# M7 自进化模块：独立审查与上游实现对照

日期：2026-10-20。范围：本地 `dev` 相对 M6 同步基线 `ded8b1d` 的 M7 实现及必要集成。此文记录审查，不代表下面的问题已经修复或新设计已经实现。

用户本次明确授权多个子 Agent。三个 GPT-6.1 Sol high 分别负责产品体验、稳定性与数据一致性、上游实现核验；主 Agent 阅读相关实现、核验实验产物并合并结论。本轮未修改产品代码、调用真实模型、使用个人会话或提交 Git。

## 1. 结论与根因

当前模块更接近“给定一个资源，用模型生成替换正文，再采用／恢复”的资源编辑器。这个定向闭环确实存在，但用户希望的“根据运行经历发现问题，再改进多个相关资源”尚未打通。

**需要具体身份的是落地修改，不是开始复盘。** 当前实现把一个候选的保存粒度，提升成了整个分析任务的输入限制：

- `GenerateEvolutionCandidate` 继承必填单一 `target`；`EvolutionJob` 只关联一个 `candidate_id`。
- 生成提示要求只审指定资源；输出只能是 `title / rationale / after`。
- 复盘没有可用工具，不能主动查其他资源、进一步读取遗漏的证据或发现应修改哪个对象。
- 默认目标为项目根 `AGENTS.md`。多选 Trace 只扩大同一个资源的参考材料，不会自然形成多个改进对象。
- 自动复盘也要求反馈已携带目标；仅保存“这些调用很费力”这样的反馈，当前不会自动发现应改哪个资源。

因此，用户必须先替系统完成归因、定位资源和拆分任务。上一轮修改解决了“能选哪些材料、实际带入多少”，没有解决“拿这些材料要完成什么工作”。已有定向测试和真实 Go 短样本证明的是选定资源闭环，不是开放式复盘的可用性。

## 2. 确认的问题

P1 表示核心使用路径受阻或实际写入状态不可靠；P2 表示重要体验、来源或效果表达缺陷。设计缺口与可复现缺陷分别标注，不把所有产品取舍叫作 bug。

| 编号 | 优先级／证据 | 问题与影响 | 最小修正方向 |
| --- | --- | --- | --- |
| R1 | P1，设计缺口／静态确认 | 必须先选单一资源才能分析；多工具、多个 Skill 或规范共同导致的问题被迫拆成多次人工定向改写，且默认落到 `AGENTS.md` | 默认从问题与证据发起复盘，输出多个发现和建议资源；保留“指定资源优化”为快捷入口；各候选仍可独立采用／恢复 |
| R2 | P1，完整路径静态确认 | 项目 A 的工具故障 Trace 不能用于 Harness 源码项目 B；留在 A 只能改 A，切到 B 后看不到 A 的证据且后端拒绝跨项目来源 | 分开证据项目和修改目标项目；显式转交已选证据，写入继续约束在选定源码项目，不笼统删除写入边界 |
| R3 | P1，隔离实验复现 | 自动采用已进入文件提交线程时点击停止，接口已返回 `cancelled`，文件随后仍变化；候选停在 `draft / pending_action=apply` | 停止时收回在途写入并记录实际结果；已进入提交阶段不能只取消等待它的协程，再宣告停止完成 |
| R4 | P2，隔离实验复现 | 自动从 Trace 提炼并采用的记忆没有携带真实会话／序号来源，回退源运行后记忆仍有效 | 宿主把实际证据来源写入既有记忆来源关系，接入 M6 失效机制；多来源保留集合，不要求模型补证明 |
| R5 | P2，隔离实验复现 | 候选实验通过后再编辑正文，旧版 `improved` 仍作为当前候选的结果展示 | 比较关联实际被测正文版本；旧结论保留为历史，新版显示尚未比较，不增加强制重测门槛 |
| R6 | P2，前后端静态确认 | 主改进页导航卸载会丢输入与选材；切候选覆盖草稿。实验保存比较又会递增 revision，前端编辑器不刷新，保存遇到 `EVOLUTION_CHANGED`，重新打开再次覆盖草稿 | 按项目／候选保留草稿；作业结束刷新元数据与版本，正文无冲突时保留编辑内容；真实冲突再展示差异 |
| R7 | P2，条件路径静态确认 | 开启自动复盘后，保存反馈已启动生成，但 UI 只提示“反馈已保存”；用户再点生成会重复请求，同一目标自动采用时还可能相互冲突 | 保存返回关联作业，显示已开始生成；相同输入已有作业时提供查看／停止，明确“重新生成” |
| R8 | P2，输入链静态确认 | 优化工具使用说明时，目标正文只有本地追加的说明（首次为空），没有保证提供工具的真实 description、schema 和能力边界；复盘又无法主动读取。容易从失败调用反猜工具契约 | 将实际工具定义作为只读依据，明确区分“使用经验”和“实现修复”；允许进一步读取所需资源，不把工具名视作足够上下文 |
| R9 | P2，设计缺口／静态确认 | 整个会话按旧到新填入字符预算，后段失败、纠正或成功结果可能被省略；虽然已如实显示省略数量，但没有跨运行的问题聚合或继续调查机制 | 先做事件／问题目录，按本次关注点读取相关片段并保留覆盖情况；预算不足时增量处理或返回明确未分析范围，不把“所选会话”当作“已全面分析” |

### Hermes Agent：更接近日常使用的学习入口

核对提交 `1f91fb386a60f5589146b05ee88e911bb58120e8`：

- [桌面入口](https://github.com/NousResearch/hermes-agent/blob/1f91fb386a60f5589146b05ee88e911bb58120e8/web/src/pages/SkillsPage.tsx#L212) 把目录、URL 和自由文本组成 `/learn` 请求交给聊天执行，体现界面和普通 Agent 共用同一工作链。

- [Curator 实现](https://github.com/NousResearch/hermes-agent/blob/1f91fb386a60f5589146b05ee88e911bb58120e8/agent/curator.py) 还处理资源使用与维护。应区分确定性的陈旧／归档和默认关闭的模型合并功能，不能说它默认完成了跨 Trace 的语义问题聚合。参见 [官方使用说明](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator)。

**取用点**：用户说经历／问题，系统寻找对象；先读取既有资源再决定修改；前台普通 Agent 和后台维护复用资源能力。这里核实的是已存在的代码和界面，不是本机真实模型运行或统计效果。

### Hermes 独立 self-evolution：定向优化实验，不是通用产品入口

提交 `0a929e3aa20e15cf04dc7c28492a7d41a5139125` 的 [状态表与入口](https://github.com/NousResearch/hermes-agent-self-evolution/blob/0a929e3aa20e15cf04dc7c28492a7d41a5139125/README.md) 仅把 Skill 标为已实现；工具描述、提示、实现代码和持续循环仍为规划。CLI 指定一个 Skill，再组织样本、候选和评价。

### GEPA：组件与评价闭环，不能代替产品的问题发现层

核对提交 `8f287de942f41a6d1e0e7e5b2d576247c4bedee9` 的 [`optimize_anything`](https://github.com/gepa-ai/gepa/blob/8f287de942f41a6d1e0e7e5b2d576247c4bedee9/src/gepa/optimize_anything.py)、[执行／反馈适配接口](https://github.com/gepa-ai/gepa/blob/8f287de942f41a6d1e0e7e5b2d576247c4bedee9/src/gepa/core/adapter.py#L91) 与 [反思候选执行](https://github.com/gepa-ai/gepa/blob/8f287de942f41a6d1e0e7e5b2d576247c4bedee9/src/gepa/proposer/reflective_mutation/reflective_mutation.py#L265)。其工作需要优化对象／目标和 evaluator；执行反馈帮助提出、评价及选择候选。[组件选择器](https://github.com/gepa-ai/gepa/blob/8f287de942f41a6d1e0e7e5b2d576247c4bedee9/src/gepa/strategies/component_selector.py)可以轮换一个或选择全部组件，没有“只能优化单文件”的一般规则。它也不自带本项目所需的桌面问题发现体验；多个替代变体与一次复盘发现多个问题是两个维度。

**取用点**：比较结果必须对应实际被测候选，执行反馈要可用于下一步改进；优化目标与评价证据要能追踪。不能只移植一次反思请求，就称已经复用了候选搜索与选择过程；也不需要为了记录偏好让每次操作先运行一套评测。

DGM 仍作为代码自修改的研究参考保留，本次没有重新验证其完整运行。它不能替代桌面交互或长期稳定性的证据。

## 4. 应怎样重新组织，而不是继续堆选择框

建议保留现有资源存储、候选、采用／恢复和独立作业，调整它们的连接方式：

1. **默认入口是“复盘这些经历”**：用户描述问题或期望，选当前会话、若干运行、反馈或明确项目范围。具体资源是可选约束，不默认等同于 `AGENTS.md`。
2. **先形成发现，再定位资源**：用实际 Trace、诊断、资源目录和工具定义，输出问题、证据、不确定之处及建议修改对象；一个问题可关联多个工具／Skill／规范。允许没有值得修改的结论，不强迫产出替换正文。
3. **同一复盘关联多个候选**：例如一处工具参数说明、一份 Skill 和一条错误记忆，属于同一问题但各自有差异、状态、来源及恢复。单资源候选可保留，无需先写通用插件框架或跨文件事务引擎。
4. **分析与落地按已有范围推进**：明确要求优化时可继续生成相关候选；现有自动采用策略仍按资源种类生效。只分析的请求停在报告。不要再增加逐项表格、反复确认或强制评分作为前置条件。
5. **区分证据位置与代码位置**：在业务项目遇到 Harness 缺陷时，带所选证据转到已指定的 Harness 源码项目；显示准备改哪里，保留原证据，不要求用户复制 Trace 文本重新建一套材料。
6. **明确闭环状态**：分析中、待补充依据、候选已生成、采用／停止／恢复的真实结果，以及后续使用是否有证据。比较属于哪个版本必须可见；返回来源页面再回来不丢草稿。

最短用户场景应是：“复盘这几轮里反复失败的工具调用，改进相关工具使用方法。”系统定位实际问题并提出相关资源，而不是反问用户先从几十个工具里挑中根因。定向维护某份 Skill 的原入口仍有价值，可作为另一种明确意图。

## 5. 修正顺序与不应增加的负担

1. 先修 R3–R6 的写入终态、记忆来源、比较版本与草稿问题，避免新的复盘流程建立在不可靠状态上。
2. 打通 R1、R2、R8：问题驱动复盘、多候选关联、工具真实定义、证据项目与目标项目分离。
3. 处理 R7、R9：合并重复操作链、按问题组织证据及实际分析覆盖。
4. 使用两个简短场景检验：同一批 Trace 关联两个资源；业务项目故障进入 Harness 源码修正。保留已验证的单资源路径，不重新无差别验收全仓库。

本次审查没有理由新增逐工具审批、信任开关、hash 回传、强制全量测试、固定评分或默认多 Agent。实际基线变化时防止覆盖用户修改、工具参数边界和真实项目写入范围仍有用途，应放在对应写入边界一次处理。重点是减少无效限制、补齐来源与生命周期，而不是给用户增加流程。
