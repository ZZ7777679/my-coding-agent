# 当前 Harness：三个用户视角的体验评价

> 日期：2026-09-22。评估对象是当前 dev 工作区及最近的桌面构建，包含尚未提交的 M4 / OAuth 增量。用户授权本轮测试和评价，后续再决定修改；本轮没有修改产品代码或提交 / 推送。
>
> 本轮体验与证据复核完成。结论：已走通的主链路可用，本轮没有发现 P0 / P1 级缺陷；发现一项确定的状态 / 错误提示缺陷，以及环境信息和若干入口表达问题。下面明确区分缺陷、体验建议和覆盖限制。

## 结论与优先顺序

1. **先修准确性**：服务停止后保留无效预览按钮并给出错误排查建议（UX-01）。这是本轮最明确的产品缺陷。
2. **再补用户和模型需要的环境事实**：默认本机执行无需新增门槛，但应更容易知道实际用了哪套 Python（UX-02）。真实样本已出现由信息不足引起的兼容性绕路。
3. **随后改善入口和列表**：首会话入口、Skill 两种选择、成果顺序、协作约定提示、角色标识（UX-03 至 UX-07）。这些功能都能走通，主要影响发现和理解成本。
4. **Trace 调整由使用偏好决定**：保留已确定的浮层与详细记录设计，可优化先摘要后 JSON 的层次；不将窄窗覆盖本身当成故障。

三个角色的共同判断是：目前适合已有基本概念的用户开始使用，主要问题已从“功能链路是否存在”转向“入口、状态与结果能否被快速理解”。这是本轮小样本的评价，不代表真实长期任务质量已经验证。没有据此增加运行审批、检查门槛或硬编码限制。

## 评估方式

三个子 Agent 分别模拟不同用户目标，由主 Agent 交叉核实并合并问题。这是 Agent 模拟用户的探索性评价，不是外部真人访谈，也不是全部功能已经验收的证明。

| 角色 | 用户目标 | 主要范围 |
| --- | --- | --- |
| 首次使用者 / 资源接入用户 | 知道从哪里开始，把已有能力接入项目 | 项目选择、设置、环境、Skill、MCP 与失败恢复 |
| 日常编码用户 | 完成任务，看懂正在做什么和修改结果 | 会话、思考、工具摘要、程序、diff、Trace、停止与恢复 |
| 长期项目负责人 | 多次会话持续推进任务 | 工作流、角色协作、Goal、上下文、历史、记忆与重启 |

桌面测试使用真实 Electron、IPC / RPC、存储及文件 / 程序工具，模型由现有测试装配替换。主 Agent 另通过生产后端使用真实 OpenCode Go 两模型评估一个普通自然语言编码任务。所有项目、数据和产物均在 `.artifacts/tests/`；没有接触个人会话、真实外部账号或修改系统网络。

问题分为实际缺陷、体验摩擦和待验证推断；仅按具体影响确定优先级，不用主观总分替代证据。角色不是独立统计样本，单次模型结果也不作模型排名。

## 已核实问题

### UX-01：已停止的服务仍提供“打开预览”，失败提示指向错误原因

- **类别 / 优先级**：实测缺陷，P2；影响服务停止后的常用操作与排错。
- **步骤**：在会话启动网页服务 → 停止服务 → 点击仍显示的“打开预览”。
- **实际**：卡片已显示“已停止”，但按钮仍可点；返回“操作未完成，请检查目录或重新打开应用”。服务确实已经停止，目录与重启并非所需修复。
- **预期**：根据当前服务状态提供动作；停止后应说明服务需要重新启动，避免保留必然失败的打开按钮。
- **证据**：`.artifacts/tests/persona-coding-JMRufq/observations.json` 的 `stoppedPreviewButtonCount=1` 和 `stoppedPreviewResult`；日常编码视角的截图与报告另列。
- **原因定位**：`ProgramCards.tsx` 简版只检查 `current.url`，完整版同时检查 `status === 'ready'`；主进程 `agent:program-open` 明确拒绝非 ready 状态。主 Agent 已复核这三处代码与实际输出。
- **最小建议**：对齐简版 / 完整版的状态显示并提供准确失败说明，不增加审批或新的执行门槛。

### UX-02：默认本机环境可直接运行，但用户和模型难以提前知道实际 Python

- **类别 / 优先级**：实测信息缺口，P2 建议；不是本机默认执行模式本身的错误。
- **步骤**：未登记 / 绑定环境的空项目，请求创建并运行小型 Python 加法器。
- **实际**：界面显示“本机工具（默认，无需导入）”；`execution_environment` 返回空环境目录、空绑定及运行参数，没有实际 Python 位置与版本。DeepSeek 先读取该工具，仍写了 `list[str]`，执行时才遇到默认 Python 3.8.8 的兼容错误；随后改成 `typing.List` 并运行通过。
- **证据**：`.artifacts/tests/persona-onboarding-first-DP6I9u/04a-default-execution-environment.png`；`.artifacts/tests/persona-coding-live-db334674ec3b/report.json` 中环境工具、真实 stderr、修复与后续 stdout。默认 Python 实际解析到本机已有环境，行为符合现有约定。
- **最小建议**：在默认环境附近提供按需查看实际工具 / 版本的入口，将已知环境信息交给模型；不强制导入、不强制升级 Python、不在每次运行前重复探测，也不把应用自身 3.13 要求套到用户项目。

### UX-03：创建任务及首会话后，开始对话的入口不够醒目

- **类别 / 优先级**：实际体验摩擦，P3。
- **实际**：只填目标即可成功创建任务及首会话，但主区域进入长任务概览表单；「打开 / 补齐首会话」在表单下方，侧栏已有「新会话」。新用户需要再定位一次入口才能开始输入。
- **证据**：首次使用报告 ONB-1；`.artifacts/tests/persona-onboarding-first-DP6I9u/06-after-create-task.png` 与 `07-first-session.png`。
- **最小建议**：让「创建任务与首会话」导航到已创建会话，或在任务页首提供醒目入口；仍不自动调用模型。

### UX-04：Skill 两种勾选的含义需要用户记住页首说明

- **类别 / 优先级**：实际体验摩擦，P3。
- **实际**：左侧无可见文字的勾选表示本会话持续使用，右侧「启用」表示允许按需使用；滚动后说明不在视野，容易混淆。左侧有可访问名称，保存与重启正常，不是选择失效。
- **证据**：首次使用报告 ONB-2；`.artifacts/tests/persona-onboarding-first-DP6I9u/09-skill-selection-controls.png`。
- **最小建议**：使用可见列标题或行内文案区分「本会话持续使用」和「允许按需使用」，保留现有两种语义。

### UX-05：修改成果列表按随机身份排序，难以判断先后

- **类别 / 优先级**：实测展示顺序摩擦，P3。
- **实际**：同一次场景先创建 `src/main.py`、再修改它、最后创建 `app.py`；成果列表显示为创建 src → 创建 app → 修改 src。各条 diff 内容正确，但列表顺序不能表达操作顺序。
- **证据**：日常编码截图 `.artifacts/tests/persona-coding-JMRufq/13-narrow-changes.png`；`changes/store.py` 的 `list()` 遍历按 UUID 文件名排序的记录。主 Agent 已核对排序实现。
- **最小建议**：按已记录的时间 / 操作序号排序，或明确提供排序依据；不另建修改日志，不增加写入校验。

### UX-06：协作消息发送处没有说明约定尚未保存

- **类别 / 优先级**：实测操作引导摩擦，P3。
- **实际**：选中同任务的目标会话后，普通消息可以填写并点击发送；未保存协作约定时才收到 `COLLABORATION_NOT_LINKED`，草稿仍保留。保存约定后消息与 handoff 能正常执行。
- **证据**：长期项目负责人独立报告及 `.artifacts/tests/persona-long-tasks-workflow-KvhVpI/`。
- **最小建议**：发送区域就近显示「尚未保存协作约定」及相应入口。事先明确角色 / 范围是用户已经确定的规则，应保留；该报错不是需要删除的多余安全检查。

### UX-07：多会话列表隐藏角色，难以快速找到合作者

- **类别 / 优先级**：实测信息展示摩擦，P3。
- **实际**：建立了不同角色的会话，但侧栏和阶段会话关联列表主要显示标题，尚未开始的角色会话都可能叫「新会话」；确认谁负责什么需要进入更多详情。角色数据与协作并未丢失。
- **证据**：长期项目负责人独立报告与上述工作流产物。
- **最小建议**：列表显示简短角色标签或角色与标题组合，减少反复进入详情；不自动增加正式会话或替用户改角色。

### 可选取舍：Trace 的摘要层次与小窗口对照

日常编码角色在 960×650 原生窗口实测：对话区宽 736 CSS 像素，Trace 浮层覆盖 620 像素。关闭后输入正常、没有页面越界。工具详情包含完整事实 JSON，技术身份与内部状态较多，用户要多读一些才能定位结果。

窄窗口浮层是已确定方案，原始 JSON 移入 Trace 也是用户明确选择；因此这里**不算布局故障或方案未落实**。可以优先让动作、结果、错误、差异链接先出现，原始 JSON 再展开；是否增加可调宽度，取决于用户是否经常需要小窗口同时对照。证据与具体建议见日常编码独立报告，不作为阻断修复。

## 真实模型补充：普通表达的小任务

用户表达为：在空项目做标准库 `add.py`，接收两个整数并求和，实际运行 `2 3` 与 `-2 5`，最后简短说明文件、用法和结果。没有提供工具名、参数 JSON、解释器绝对路径或“标准答案”代码。

| 项目 | GLM-5.3-Flash | DeepSeek V4.1 Flash |
| --- | --- | --- |
| 文件与实际结果 | 创建 `add.py`，两次 exit 0，输出 5 / 3 | 初次遇到 Python 3.8 注解兼容错误，自行修正后两次 exit 0，输出 5 / 3 |
| 模型 / 工具次数 | 4 次请求，3 次工具 | 首轮 6 次请求，9 次工具；显式接续另 2 次请求 / 2 次工具 |
| 交付答复 | 已给出文件、用法和真实结果 | 本次有限样本内未给出最终答复；接续时回读文件并保存项目 Python 版本记忆 |
| 可下结论 | 小型真实文件创建 / 本机运行 / 交付链路通过 | 核心文件与执行链路通过；该样本交付效率值得继续观察 |

**必须保留的评估限制**：首版评估脚本将每个模型分配为 6 次请求，DeepSeek 因此在已完成两次正确运行后遇到测试侧预算截止。随后用原总预算剩余 2 次显式接续；最终仍达到本次测试预算，不能将此称为产品默认 25 次上限的问题，更不能证明不受该测试限额时无法完成。原失败 / 接续记录全部保留，没有将缺失最终答复写成完整通过。本轮总共 12 次模型请求，累计活动时间约 59 秒；自动后台记忆提取关闭以限定本次编码观察，但正常记忆工具仍可调用。

这条样本也显示：现有工具没有再以 hash、项目信任开关或额外逐工具审批阻断正常创建 / 编辑 / 本机执行。只证明本场景，不推断所有场景无问题。

源码入口为 `tests/models/persona_coding_live.py`；报告、生成代码和会话事实均在 `.artifacts/tests/persona-coding-live-db334674ec3b/`。真实模型观察和桌面替身测试分别记录，不拼成一条并未执行过的真实端到端桌面场景。
