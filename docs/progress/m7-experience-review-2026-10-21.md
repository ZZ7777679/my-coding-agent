# 经验与改进：多视角独立审查

日期：2026-10-21。审查基线：`dev`／`3f617c8`。第 1–5 节保留审查时的问题与证据；用户随后授权的十二项修复已完成并定向验证，见第 6 节。本地修改尚未提交／推送。

用户明确授权三个 GPT-6.1 Sol high 子 agent 独立审查，分别负责操作体验、记忆与证据利用、运行稳定性与过度约束。主 agent 核对重要调用链、合并重复项，保留此前本地接线分析与无关调研资料。本轮未修改产品代码、读取个人会话、调用真实模型或提交／推送 Git。

## 1. 总体判断

模块已经能够从问题和选定经历出发，先筛选线索、按需读取证据，再形成多个发现和候选；不再是上一轮只能指定单个资源的编辑入口。现场复盘、独立定制、证据浮层、独立预算和候选采用／恢复均有真实实现。

主要不足集中在三处：

1. **流程接续有断点。** 失败后重试、重启后的中断状态、早期记录查找、页面切换后的选择以及准备阶段停止尚未一致贯通。
2. **实际范围与所见范围有偏差。** 定向目标仅由提示词限制；现场范围在保存反馈的支路可能丢失，多候选的独立性也不完整。
3. **记忆主要作为资源，还未成为改进的接续依据。** 调查无法按正文发现经验，部分来源关联遗漏或过宽，过往比较／采用／恢复结果没有方便的检索回路。

这些问题可以在现有服务中逐项修正，不需要新的工作流引擎、经验数据库、逐项审批或强制评分系统。

## 2. 问题清单

P1 表示可能改到用户未选择的资源；P2 表示流程受阻、范围／来源不准确或重要设计缺口。静态确认与隔离复现分别标注，优先级不是统计发生率。

### R1 · P1 · 定向改进可能越出已选择的资源

- **触发：** 用户指定优化 `tool_guidance/read_file`，模型却返回项目规范 `AGENTS.md` 的提案；项目开启了规范自动采用。
- **观察：** 隔离的真实服务与离线模型运行后，作业为 completed、候选为 applied，未选中的 AGENTS.md 实际被改写。
- **原因：** [investigation.py](../../src/my_agent/evolution/investigation.py) L608–609 仅在提示词声明定向范围；L644–658 直接按模型提供的目标保存，L667–675 按目标种类自动采用，没有在接纳边界与已选真实资源身份收束。
- **方向：** 在既有 `submit_review` 接纳处比较规范化资源身份，不一致时交回模型修正。开放式调查仍可产生多个目标；不增加人工审批。

### R2 · P2 · 重启后的中断调查不能按原作业接续

- **触发：** 应用异常退出，磁盘留有 running 作业，重启后从该调查生成候选。
- **观察：** 真实编排加内存替身返回列表 `interrupted`、详情 `running`，接续报 `EVOLUTION_REVIEW_RUNNING`。
- **原因：** [service.py](../../src/my_agent/evolution/service.py) L87–90 只修正列表投影；[investigation.py](../../src/my_agent/evolution/investigation.py) L114 按磁盘状态拒绝接续。
- **方向：** 列表、详情和接续统一判断真实活动作业。中断记录允许用户显式接续，继续保留“不自动重放副作用”。

### R3 · P2 · 关联候选生成失败／取消后缺少原条件重试

- **触发：** 从发现列表生成候选，遇到连接失败、预算到达或用户停止，再点击原按钮。
- **静态确认：** [Evolution.tsx](../../apps/desktop/src/renderer/src/Evolution.tsx) L901–904 无条件复用 `proposalJobs`，L917 在接纳时保存映射；后续只能跳回旧作业。顶部重新发起调查不等于重试这次候选生成。
- **方向：** 保留查看旧结果，并提供“重新生成关联候选”，复用原调查冻结范围和所选发现。活跃作业仍去重，已结束作业不能永久挡住重试。

### R4 · P2 · 一个候选采用冲突使后续独立候选未被保存

- **触发：** 一次输出两个合法候选，首个自动采用遇到 `EVOLUTION_TARGET_CHANGED`。
- **观察：** 真实 `investigate` 加内存替身的结果为 failed，仅首个候选保存，第二个提案未落盘。
- **原因：** [investigation.py](../../src/my_agent/evolution/investigation.py) L644–675 按“保存一个→立即采用”循环，首项冲突直接进入整个作业的异常处理。
- **方向：** 先保存独立候选，再分别处理采用；已知写入前冲突只反馈相应候选。真正 I/O／保存故障仍按既有规则停止，不通用吞错继续。

### R5 · P2 · 大范围本地准备没有可停止身份，并占用全局接纳锁

- **触发：** 从整个任务／项目发起复盘，需要读取、投影和筛选较多历史。
- **静态确认：** [service.py](../../src/my_agent/evolution/service.py) L251–296 在全局 `accept_lock` 内先完整准备材料，再创建作业 ID 和任务；[investigation.py](../../src/my_agent/evolution/investigation.py) L615 的时间预算只覆盖后续模型循环。部分本地检索使用 [worker.py](../../src/my_agent/worker.py) 的共用单写者线程。
- **影响：** 准备期间缺少可操作的停止入口，其他项目的改进接纳也会排队；长筛选还可能延迟业务存储队列。未进行大历史延迟测量，不宣称已测得具体卡顿时长。
- **方向：** 先创建“准备中”作业，将准备纳入进度、取消和时间预算；锁只保护去重／登记，纯计算移出存储写线程并支持取消。不要用固定会话数上限解决问题。

### R6 · P2 · “保存反馈→自动复盘”可能丢失现场继承范围

- **触发：** 从“复盘此会话／任务／项目→自定义”进入，开启自动复盘，不另行手选 Trace，保存反馈。
- **静态确认：** [Evolution.tsx](../../apps/desktop/src/renderer/src/Evolution.tsx) L493–499 只提交手选 `references`，未带 `origin`；[service.py](../../src/my_agent/evolution/service.py) L206–213 自动生成也没有继承范围。UI L506–512 却将返回作业关联到含原范围的输入。
- **影响：** 界面仍显示现场范围，自动作业实际可能有 0 条 Trace；用户难以知道分析依据发生了变化。
- **方向：** 反馈保存、自动生成与普通启动共用范围解析，作业关联使用实际接纳的输入快照。

### R7 · P2 · 页面导航丢失发现勾选，恢复后变为全选

- **触发：** 多个发现中只选部分，离开页面再回来。
- **静态确认：** [Evolution.tsx](../../apps/desktop/src/renderer/src/Evolution.tsx) L100、L119、L852 的 `findingSelections` 没有进入 [EvolutionDrafts.ts](../../apps/desktop/src/renderer/src/EvolutionDrafts.ts) 的草稿，重新挂载为空后回退为全选。
- **影响：** 所选改进范围变大，也可能无法命中此前部分发现对应的候选生成作业，造成重复工作。
- **方向：** 沿现有草稿按调查身份保留选择；组合身份按稳定集合计算，不新增持久化框架。

### R8 · P2 · 较早调查没有有效分页／定位入口

- **触发：** 项目超过默认最近 30 个作业，想找尚未生成候选的旧调查或查看候选的来源调查。
- **静态确认：** [store.py](../../src/my_agent/evolution/store.py) L204–211 总是截取最近 `query.limit` 个作业，`before` 仅作用于反馈／候选。前端“更早记录”不解决作业分页；[Evolution.tsx](../../apps/desktop/src/renderer/src/Evolution.tsx) L360–363 的定位仅查当前 DOM，不在列表就没有动作。
- **影响：** 数据仍在磁盘，用户却找不到。这里是分页接线不完整，不是“30”这个页面大小本身有错。
- **方向：** 作业历史提供分页／检索；按 ID 跳转时按需读取并展开，不默认加载全部历史。

### R9 · P2 · 经验检索只看标题／ID，难以利用已有记忆

- **触发：** 相关条件只写在记忆正文或标签，标题比较笼统。
- **观察：** 真实 MemoryStore 条目正文含 `SENTINEL_IN_BODY`，资源调查搜索该词返回 `matched_count=0`，按已知 ID 读取则能拿到正文。
- **原因：** [investigation.py](../../src/my_agent/evolution/investigation.py) L414–429 只检索 `label + identity`；[service.py](../../src/my_agent/evolution/service.py) L136–149 只将记忆标题作为标签。调查没有使用普通会话已有的相关记忆召回。
- **方向：** 复用 MemoryStore 的正文／标签／主题检索与有效性、项目过滤，先返回相关经验线索，再按需全文读取；没有记忆或检索失败不挡住调查。

### R10 · P2 · 从记忆派生的自动经验可能丢失来源关联

- **触发：** 调查读取记忆 A，生成并自动采用新记忆 B，模型没有自行填写 `source_ids`。
- **观察：** B 的 `source_ids=[]`、`trace_sources=[]`；更正并停用 A 后，B 的 `stale` 仍为 false。
- **原因：** [investigation.py](../../src/my_agent/evolution/investigation.py) L445–455 将实际读取记忆存成一般 resource 片段；[resources.py](../../src/my_agent/evolution/resources.py) L236–274 仅采集 Trace 和反馈目标，漏掉这些记忆读取身份。
- **方向：** 宿主保存实际读到的记忆 ID／修订，并复用 `source_ids` 与既有失效传播；不依靠模型抄写身份，也不强制所有候选必须先读取记忆。

### R11 · P2 · 作业读过的全部 Trace 被混作每条候选的依据

- **触发：** 同次复盘发现两个独立问题，生成各自经验；其中一个问题的源运行随后回退。
- **静态确认：** [investigation.py](../../src/my_agent/evolution/investigation.py) L639–658 为全部候选赋同一 sources；[resources.py](../../src/my_agent/evolution/resources.py) L232–244 又以整个作业已读 Trace 组装自动记忆来源。记忆存储将这些来源视为共同输入，任一来源失效可连带影响无关经验。
- **方向：** 作业审计保留全部材料，候选依据按发现分别关联；与宿主真实读取记录对齐，未知关联如实表达。引用不完整不能变成新的停止门槛。

### R12 · P2 · 已尝试的改进没有形成方便检索的学习接续

- **静态确认：** 比较、采用、恢复有持久记录，但调查工具没有相应历史检索入口。除目标本身是记忆外，这些结果没有普遍关联回可召回经验，见 [service.py](../../src/my_agent/evolution/service.py) L366–386、L427–479。
- **影响：** 新调查能看到资源的现状，却不容易知道过去为何这么改、哪些方案失败过、为何恢复；可能重复调查和生成被放弃的方案。
- **方向：** 先让已有 EvolutionStore 记录可按资源、问题和结果查找，再把值得复用的结论与原候选、资源版本、比较结果关联进原记忆库。采用成功不等于效果改善，缺少后续证据时保持“效果未知”。

## 3. 建议的改进路线

### 第一组：让一次复盘能够稳定做完并接续

修 R1–R8：从接纳准备开始可见、可停止；范围一路保留；失败后从原调查重试；重启和旧历史可找回；候选各自保存与反馈。无需再要求用户先填目标、报告、评分或重新选择全部材料。

### 第二组：让已有记忆参与问题筛选

以 R9–R11 为重点，复用现有记忆服务：问题与所选 Trace → 相关经验线索 → 原始证据查证 → 分别关联的发现和候选。保留经验的有效范围与资源版本，纠正能够传递；不把所有记忆正文默认塞入每次复盘。

### 第三组：让改进结果能被下一次使用

处理 R12：已有改进记录检索 → 复用结论选择性沉淀 → 日常任务／后续复盘召回。优先记录“在什么条件下，试过什么，观察到了什么”，允许用户直接纠正／停用；不要将统计评分当作保存偏好或正常开发的条件。

```mermaid
flowchart LR
  A[问题与选定经历] --> B[检索相关记忆和过去改进]
  B --> C[选择线索并按需回读 Trace]
  C --> D[发现与独立候选]
  D --> E[编辑、比较、采用或恢复]
  E --> F[记录真实结果和可复用经验]
  F --> B
```

图中“相关记忆与过去改进检索”“选择性结果回流”为建议完善项；不能把这张目标流程当成当前已经完整实现。

## 4. 应保留的设计与排除项

- 现场与独立页共用作业，允许先调查再确定多个目标；不再报告旧版“强制单一工具”问题。
- 本地检索所选公开正文，模型按需读正文；所选、推荐、实际已读和完整阅读分别表达，覆盖率不作完成门槛。
- 跨项目证据与写入目标分开，冻结截止位置，普通任务不因维护失败改成失败。
- 预算以 `null` 表达不限；**`input_chars` 只控制初始正文**，UI 高级说明与材料面板已明确其作用，不应据累计回读超过它再增加总阅读硬门槛。
- 内容版本绑定比较，旧结果标注过期；取消时等待已经开始的写入收回；采用与恢复保留真实状态和后续用户修改。
- 人工采用记忆作为用户确认、免来源回退，是现有明确语义，不将其与 R10 的自动派生来源遗漏混同。
- 没有发现需要新增逐工具审批、强制测试／评分、固定项目规模限制或第二套经验库的依据。真正要修的是范围、生命周期、分页、来源和检索接线。

## 5. 验证方式与边界

- 操作体验视角：阅读 UI、状态／参数流及既有桌面用例；本轮未重跑真实桌面，所以 R3、R6–R8 是源码路径确认，不标成用户界面实测。
- 记忆／证据视角：项目 `.venv` Python 从标准输入执行短小隔离代码，使用临时目录中的真实存储／服务与离线模型；观察 R1、R9、R10。临时文件随实验结束清理，没有保留新的测试脚本或产物，也未改仓库产品文件。
- 稳定性视角：`python -B` 标准输入中的内存替身调用真实编排，观察 R2、R4；不写业务文件。R5 为锁／队列／任务接纳调用链分析。
- 主 agent 交叉核对上述关键代码及旧审查修复，合并定向范围重复发现，排除“初始字符预算被累计回读突破”的误报。
- 本轮没有全量回归、真实模型请求、个人数据测试、大历史性能测量或长期效果评估。隔离机制复现证明对应条件路径，不代表真实模型一定会产生该输出，也不代表所有用户操作已验收。
- 以上是审查时的验证边界；用户随后授权的修复与新验证见下节，原证据不改写。
