## 发现

### R1 · P1：运行中修改子 agent 配置会造成事件循环忙转

- 位置：`src/my_agent/delegation/service.py:157`；消费者为 `_watch`、`_drive` 和 `result`。
- 触发：已有子任务运行，用户关闭子 agent 开关或调整并发数。`configure` 对当前 `self.changed` 调用 `set()`，但没有像 `_signal` 那样替换 Event。
- 后果：后续循环一直取得同一个已置位事件，`await changed.wait()` 立即返回；活动父会话的 `_load` / `_owner` 也不会真正挂起，导致后端事件循环忙转，其他请求、流式返回和停止操作无法正常调度。与“关闭只拒绝新委派，已有子任务继续”的说明不符。
- 最小方向：复用同一种事件通知方式，唤醒当前等待者后让下一轮等待新的事件；不靠 sleep、额外轮询上限或超时掩盖问题。
- 证据：真实应用装配和离线模型，子任务等待期间执行 `workers.configure(enabled=False)`。探针观察到同一 Event 持续置位、无新状态变化连续等待 33 次；为避免真正挂死，在第 32 次起主动抛出探针异常停止循环。该注入产生的 `RUN_INTERNAL_ERROR` 是探针终止副作用，不能另算产品缺陷；原始问题由重复立即返回的等待路径证明。

### R2 · P2：用户级记忆的纠正 / 遗忘没有传播到其他项目的派生内容

- 位置：`src/my_agent/memory/store.py:229`、`:254`。
- 触发：全局用户记忆被项目 B 的知识页通过 `source_ids` 引用，之后从项目 A 编辑或遗忘这条用户记忆。
- 原因：`invalidate` 与 `forget` 用 `find(project_id, ...)` 枚举派生内容，该查询只包含当前项目与用户级条目，漏掉项目 B。
- 后果：项目 B 的派生页不标为 stale，遗忘后仍可被召回；与“来源改变停用派生注入”和遗忘清理的约定不符。
- 最小方向：读取和召回继续保留项目范围；对已授权修改的来源 ID，内部失效传播遍历全部相关派生条目。无需向量库、图引擎或模型审核。
- 证据：隔离存储创建用户级来源和 B 项目派生条目，从 A 更新来源后 `stale=false`；随后忘记来源，B 的正常 `find` 仍返回派生条目。

### R3 · P2：继续子任务失败时返回上一轮成功回答

- 位置：`src/my_agent/delegation/service.py:330–347`，重点为 `:333–334`。
- 触发：同一 worker 首轮成功，用户 / 父模型明确继续它；新一轮模型连接失败，尚无新的助手正文。
- 原因：`answer` 从整个子会话倒序取最近正文，没有像下面的报告查询一样限定 `value.run_id`。
- 后果：worker 状态虽为 failed，但 result 是旧成功回答；该 result 随后成为父运行的失败说明，掩盖真正的连接错误。违反工具提示中“实际子记录决定结果”和本轮结果归属。
- 最小方向：正文与报告均限制到本次 run；本次没有正文时使用本次失败原因，旧答案仅留在历史中。
- 证据：两轮真实应用调度、离线模型第二轮抛出 `MODEL_CONNECTION_FAILED`；worker 的结果和父运行 message 均为 `OLD successful child result`，不是注入的 `second child request failed`。

### R4 · P2：可选子 agent 配置损坏会阻断普通对话

- 位置：`src/my_agent/sessions/service.py:643–644`，对应 `delegation/service.py:84–89`。
- 触发：某会话的 `workers.json` 损坏，重新加载后提交普通对话，用户没有请求委派。
- 原因：每次普通运行接纳前都强制 `delegations.prepare`，读取 / schema 错误直接向外传播。
- 后果：尚未调用模型即返回 `DATA_INVALID`，将可选子 agent 的配置问题升级为所有会话执行的前置门槛。这里确实存在用户要求避免的过度阻断，与 context / memory 对可选数据不可用的局部处理不一致。
- 最小方向：保留损坏文件与真实诊断，暂时使该会话的委派能力不可用；不阻断不依赖委派的普通运行，也不自动重置配置或假装保存成功。
- 证据：隔离会话写入损坏的 `workers.json`，清除该配置缓存以模拟首次加载；`sessions.start` 普通对话直接抛出 `DATA_INVALID`。

### R5 · P3：设置文案 / 注释把 CLI 和桌面误分成两种上下文计量

- 位置：`apps/desktop/src/renderer/src/RunSettings.tsx:19`、`src/my_agent/runtime/loop.py:109–110`。
- 当前文案称“兼容字节预算（CLI 与材料预览；桌面对话按 token 管理）”。实际 CLI 的对话入口调用 `build_sessions`，同样装配 ContextService 和 window_provider；字节硬门槛只保留给未注入 window_provider 的底层调用。
- 最小方向：按真实职责描述为“材料预览 / 辅助请求字节预算；主对话由上下文策略管理”，底层回退注释也描述装配条件，不用 CLI / 桌面区分。无需再实现两套预算。
- 证据：静态追踪 `cli.py:286/373/390` → `bootstrap.py` → `sessions/service.py` → `runtime/loop.py`。
