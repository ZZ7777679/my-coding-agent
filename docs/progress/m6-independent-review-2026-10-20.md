### R1：回退必须区分“原先不存在”和“起点未覆盖”

- 位置：[checkpoints/store.py](../../src/my_agent/checkpoints/store.py)，`capture` 第 78 行、`finish` 第 182–183 行；实际删除路径为 `reverse` 第 316–317 行与 `write` 第 395–396 行。
- 触发：项目已有 `existing.txt`，起点被 `.gitignore` 忽略；一次请求只取消忽略规则，没有创建或修改该文件。前快照不包含文件，却标为 `discovery_complete=True`；后快照发现它后，将其视为从无到有。
- 影响：检查点显示 `ready` 且 `issues=[]`，预览生成删除差异。用户选择该文件并允许恢复“命令／外部程序产生的变化”后，会删除请求开始前就存在的内容。默认不恢复此类来源缩小了触发范围，但没有修正错误基线。
- 实证：使用生产 `CheckpointStore.begin/finish/preview/reverse/write` 在隔离目录复现，删除后 `existing_file_after_apply=false`。不是完整桌面点击流程，也没有调用模型。报告：[result.json](../../.artifacts/tests/m6-state-review-c983c72a29df47328e8b98f5041904a6/result.json)，内含步骤、调用方式和对照结果。
- 对照：文件大小与总字节预算导致的省略已有显式 `omitted` 记录；两种对照均没有生成删除恢复，不重复计为缺陷。
- 最小修复方向：为起点存在性保留足够信息，或用起点发现规则识别未知覆盖。后续新发现但不能证明起点不存在的文件，不生成“删除新文件”的恢复；说明未覆盖的具体文件。不要扩大为全局恢复审批或阻断无关文件。

### R2：免提权启动不能依赖改写所有祖先目录的 DACL

- 位置：[execution/sandbox.py](../../src/my_agent/execution/sandbox.py) 第 351–356 行；第 306–307 行调用 `SetFileSecurityW`；第 401–408 行撤销授权。
- 触发：项目位于 C 盘，或 E 盘项目绑定 C 盘 Python／Conda 前缀、额外目录。`path.parents` 包含卷根，启动无条件向每个祖先写入遍历／属性权限，不先区分已有访问能力是否足够。
- 影响：当前账户若不能修改 `C:\` 的 DACL，会在真正启动命令、终端、Git 或解释器探测前得到 `SANDBOX_ACCESS_FAILED`。代码虽不再弹 UAC，仍把修改受保护系统目录权限变成了普通沙箱开发的前置条件。
- 附带清理问题：授权前先写日志本来用于崩溃恢复，但失败后又无条件向同一不可写目录撤销尚未成功加入的 ACE，可能再次失败，保留 profile／恢复记录并在下次启动继续报错。此为同一问题，不另计数量。
- 实证：执行审查者在本宿主仅用 `CreateFileW` 请求 `WRITE_DAC`（共享 7、`OPEN_EXISTING`、`FILE_FLAG_BACKUP_SEMANTICS`），立即关闭成功句柄；`C:\` 返回 `ERROR_ACCESS_DENIED(5)`，`E:\` 允许。没有修改 ACL、创建沙箱主体或提权。本轮未用 C 盘实际启动失败租约；启动失败及清理后果来自上述 OS 事实与生产调用链的组合判断。
- 历史证据边界：此前使用 E 盘隔离 Python 副本的真实运行仍有效，但不能推广到 C 盘工具链／全部正常用户目录；“不调用提权入口”不等于“所有正常环境免提权可运行”。
- 最小修复方向：只对实际缺失的祖先访问能力补授权，避免要求所有祖先可写 DACL；清理时核实本租约 ACE 是否存在，没有成功授权时不要求写回。继续保留先记账后授权的崩溃恢复语义，不通过重新加 UAC、全局放权或静默退回 direct 解决。

### R3：采用工作方式必须同步当前图的分配与删除状态

- 位置：[tasks/service.py](../../src/my_agent/tasks/service.py) 第 122 行；[spaces/work_graph.py](../../src/my_agent/spaces/work_graph.py) 第 43–59 行展示其影响。
- 触发一：给已有节点分配成员，保存当前工作方式，再采用到同一任务。模板实例会重新映射成员身份，但只替换 `planned_items`，旧 `assignments` 继续覆盖新定义。
- 影响一：当前图引用不在新团队中的旧成员。桌面显示“待分配”，新成员的请求上下文也无法正确归属该节点。离线 RPC 报告确认 `snapshot_owner != displayed_owner` 且 `owner_exists=false`。
- 触发二：删除 `build` 后，显式重新采用包含它的工作方式。模板快照和 `planned_items` 包含该节点，但旧 `removed_work_ids` 继续将它过滤。
- 影响二：采用返回成功，实际图仍为空；不仅是显示刷新问题，后端工作图投影同样为空。
- 实证：通过现有离线 fixture 和真实 RPC 完成 capture/save/apply/work_graph；没有起桌面或调用真实模型。[负责人报告](../../.artifacts/tests/review-workstyle-57e5ba716160438cae2fc66e1b609646/report.json)、[删除标记报告](../../.artifacts/tests/review-workstyle-57e5ba716160438cae2fc66e1b609646/removed-report.json)。
- 最小修复方向：显式采用时同步重映射／替换模板节点的当前分配与删除投影；历史保留在原 `TaskFact`。不要以保留历史为由继续让过期的当前状态覆盖新配置，也不要用要求用户逐项手动清空来规避。

### R4：没有 Run 身份时不能把全会话 Trace 标成“本次运行”

- 位置：[SpaceChat.tsx](../../apps/desktop/src/renderer/src/SpaceChat.tsx) 第 270–279 行；[Trace.tsx](../../apps/desktop/src/renderer/src/Trace.tsx) 第 367–374 行。
- 触发：成员忙时，新群聊消息接纳失败，卡片有 `session_id` 但 `run_id=null`，仍提供“本次运行 / Trace”。点击后将 null 传给 Trace，查询语义是整个会话。
- 影响：用户看到之前或正在进行的其他请求轨迹，容易误以为这条失败消息已执行过工具。排队／尚未接纳的卡片静态上也走同一入口。
- 实证：现有 TeamModel fixture 保持一次运行，再发送新消息得到 `RUN_BUSY`、`run_id=null`；使用 UI 相同的 Trace RPC 参数返回 9 条记录，属于两个其他 Run。[报告](../../.artifacts/tests/review-queued-trace-53e1927649f5477fbbc48f0608030fd6/report.json)。这是后端复现和前端调用链核对，未执行原生桌面点击。
- 最小修复方向：只有拿到真实 `run_id` 才允许打开“本次运行”；此前显示等待接纳／无运行记录。若仍提供全会话 Trace，应另行准确命名，不能悄悄扩大查询范围。
