## 本轮发现

- `models/types.py` 与 `runtime/events.py` 仅提供草案；不存在模型客户端、工具循环或会话事件存储，不能把 M0 的握手成功视为模型调用成功。
- `rpc/server.py` 顺序读请求、执行、写响应；`apps/desktop/src/main/backend.ts` 只接受带已知 ID 的响应。接入长任务必须增加独立运行任务与通知分发，否则停止请求被阻塞，事件会被当成协议错误。
- 现有普通 RPC 等待 8 秒，诊断 60 秒；模型请求应另有可配置预算，不能只扩大所有 RPC 超时。
- 现有项目与配置会持久化，对话尚未实现。M1 应同时规划历史保存和重启查看，延续用户对 E 盘数据与桌面可用性的要求。

## 形成的阶段建议

- M1 包含自己的单任务 Python 循环、Go 双模型、三个只读工具、桌面对话与工具记录、停止 / 预算、同模型追问和 E 盘会话历史；CLI 与桌面共用服务。
- M2 聚焦打包，M3 保持编辑 / diff / 应用边界，M6 处理不完整任务的修复与继续；历史查看和重新连接视图在 M1 即实现。只细化 M1，没有预建 M2–M8 的详细文档。
- 先做共享服务与最小读文件闭环，再尽早接入 Go，随后补齐读取、长任务协议和桌面；按成果推进，不设固定工期。
- 验证按改动选择最小直接证据，真实双模型回合设独立预算；不每步重复全量 M0 回归。历史完整性、路径与凭据边界保留，普通可恢复请求失败不等于会话永久不可用。
- 本轮复核已识别下一阶段的硬编码风险：短 RPC 超时用于长模型调用、可选搜索工具作为启动前置、固定上下文能力、预算初值强制为唯一值。方案定义覆盖与降级入口；这属于设计复核，不冒充尚未编写的 M1 代码审计。实施相关模块时及阶段收尾再核对实际代码。
