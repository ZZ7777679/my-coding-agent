## 2. 沙箱：先明确隔离对象，再选择一个首发后端

沿用已确定的产品行为：项目默认直接运行，用户按项目选择沙箱。授权范围内正常运行，不增加逐命令审批；不能启动所选沙箱时说明实际原因，不静默改成直接执行。详细历史讨论见 [运行环境与沙箱](runtime-environments-and-sandbox.md)。

建议首版覆盖项目命令、持续服务和交互式终端及其子进程，使 Python、Node、PowerShell／CMD 的执行范围一致。沙箱配置表达项目路径、所选运行环境、额外数据路径、临时目录与网络能力；只提供实际后端能够执行的选项。

必须在细化设计时列清其他入口：文件工具、Git、LSP、本地 MCP 都可能访问文件或启动程序，不能只限制 `run_command` 就称为整个 Agent 已隔离。文件访问应使用同一项目范围；会执行项目代码的入口需走隔离执行或明确显示尚不支持。模型请求由受信宿主处理；远端 MCP、浏览器和外部服务是否受该隔离约束分别说明，不能由本地沙箱开关推导远端行为。

| 候选 | 适用性与成本 | 当前建议 |
| --- | --- | --- |
| Windows 原生 AppContainer | 可用于未打包 Win32 程序；有机会复用本机解释器，但须实际解决依赖路径、缓存、子进程、终端和本地服务兼容 | 优先做小范围可行性验证；尚未选为最终实现 |
| Docker 容器 | 环境和挂载边界明确；需要引擎、镜像和容器内依赖，不能把本机 Windows Conda／venv 直接当成 Linux 容器环境 | 作为主要备选，与用户对环境复用的要求一起取舍 |
| Windows Sandbox | 临时 Windows 环境，支持目录映射和网络设置；需准备其中的工具和宿主通信 | 暂不作为第一选择，不同时开发三个后端 |

微软说明未打包应用可以进入 AppContainer，但应用要管理 profile 与所需资源访问；这并不证明本项目的 Conda、ConPTY 或服务已兼容。[官方说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-for-legacy-applications-)

Windows Sandbox 支持映射宿主目录，写入可写映射的文件会留在宿主；关闭沙箱并不撤销这类修改。因此沙箱与回退仍需分别实现。[配置与映射](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

Docker Desktop 在 Windows 有不同引擎后端与系统要求，应检测用户实际环境，不把 Docker／WSL 的安装变成所有项目的启动条件。[Docker 官方文档](https://docs.docker.com/desktop/setup/install/windows-install/)

进入实施后的首个技术决策依据：选定环境运行一个脚本、启动并访问本地服务、创建和停止子进程、使用交互终端、核实授权内外文件访问。仅创建受限进程或设置工作目录不算沙箱交付；原生路线若兼容成本过高，再据具体证据选容器，不靠不断添加提示框补偿。

## 3. 回退：代码检查点与对话重新开始

### 用户已确认的两个入口

1. **只恢复代码**：选择修改／请求／检查点，查看影响并恢复文件；对话保留，下一次请求告知模型哪些文件已恢复。
2. **恢复代码＋从指定消息重新开始**：恢复对应代码起点，返回该消息之前的有效对话，允许修改提问后继续；保留原分支记录、Trace 和恢复来源。

建议以一条用户请求为主要可见粒度，保留已有单次修改恢复；Goal 内可以有更细的 Run 检查点，不把全部 Goal 工作绑成一次不可分回退。模型工具层与桌面使用同一恢复服务，不让模型自行拼接 `git reset` 充当产品回退。

### Git 的角色与覆盖范围

- 产品面向用户的是“检查点”，无需远端。原项目已有未提交内容也要进入正确起点，不能简单等同于 HEAD。
- 不因开启回退强制初始化项目 Git，不移动用户分支，不污染用户暂存区；项目 Git 开关与回退开关分别表达用途。
- 继续复用当前修改记录。为了捕获命令产生的文件变化，需要补请求前后的文件状态记录；仅把多条 `change_id` 打包不能覆盖 shell 写入。
- 底层优先比较现有存储扩展与 Git 对象／独立索引快照，选一个可维护的主路径。暂不确定“双后端”，也不自动在关闭 Git 的项目里创建隐藏仓库。
- 明确新文件、删除、移动、二进制、忽略目录和大文件的覆盖方式；未保存的文件不能显示成“已完整恢复”。依赖目录、数据库和外部服务状态不默认为代码快照的一部分。

Git 能分别恢复工作区和索引，默认恢复源也不同；“回到请求前”需要 Harness 自己建立起点和范围，不能用一个默认 `git restore` 代替。[Git restore 文档](https://git-scm.com/docs/git-restore)

### 与协作、上下文的连接

- 默认反转选定范围的修改，保留用户和其他会话之后不重叠的编辑；有重叠时只呈现具体受影响文件，不能把一次局部冲突升级成全项目不可用。
- 共享目录的前后快照不天然证明修改来源。命令／外部程序的写入来源未知时如实显示，不归功于某个 Agent，也不默认覆盖其他成员工作。
- 恢复前记录当前可恢复状态，使误点后能撤销恢复；执行中显示逐项真实结果，不宣称多文件原子事务。
- 对话重新开始需要切换有效历史，排除被放弃分支的回答、工具结果及覆盖该分支的旧摘要；保留原记录用于查看。不能只在 UI 隐藏消息。
- 当前项目规范、实际文件和用户现有设置仍是事实。共享任务状态及长期记忆不能随某次会话回退被整体删除；需要区分过期的来源结论和其他会话仍使用的信息，恢复后向模型提供简短说明。
- 文件恢复与对话切换的先后、部分失败以及相关写入仍在进行时如何处理，在接口设计中明确；失败不能显示全部恢复成功或自动重放命令。

## 4. 工具与 Skill：本地全登记，请求分层加载

**不建议在规模增长后，仍把所有工具定义和所有 Skill 头无条件发送给模型。也不建议把每个读文件动作都藏在检索后面。** 本地扫描、索引和缓存可以覆盖全部已启用能力；模型上下文只装配本次实际需要的内容。

| 层 | 建议进入请求的内容 | 目的 |
| --- | --- | --- |
| 常驻核心 | 常用文件、搜索、编辑、执行及必要控制工具的实际 schema；精简能力类别提示 | 高频编码直接开始，不额外找工具 |
| 当前工作集合 | 用户选定、当前阶段需要、模型已发现的工具定义与 Skill 内容 | 连续工作保持稳定，不在每轮重新检索 |
| 扩展能力目录 | 可搜索／分页浏览的内置扩展、MCP 与 Skill 索引 | 按问题发现，随后加载精确 schema 或正文 |

具体建议：

- 复用现有 MCP 发现机制的思路，扩展内置工具发现；Skill 增加检索／浏览入口，继续由 `load_skill` 加载正文。统一来源身份与显示方式，不把方法文档和可调用函数强行变成一种对象。
- 小型项目启用目录可继续全量发送简短头；大型库只呈现当前选用项、相关候选和可用类别，剩余内容随时可搜索或分页展开。用户明确指定 Skill 时直接加载。
- 初版先用名称、描述、标签及任务上下文检索，不要求向量数据库或额外模型路由请求。检索无命中可以扩大范围、浏览分类，不能把 Top K 之外的能力判成“不存在”。
- 活跃集合保持稳定顺序；任务阶段变化或用户选择时调整，允许卸载已不需要的正文与定义。能力发现与权限分别处理，不把“尚未加载”变成永久拒绝调用。
- “只加载一次”指不重复发现和追加历史正文，不意味着无状态模型 API 从此不需要相关定义。下一请求仍按实际活跃集合组装，缓存命中也不代表材料不占上下文。
- 上下文面板分别列出核心工具、已加载工具、Skill 目录／正文、估算占用；实际材料清单与发出的请求一致。离线估算和 provider 返回的总输入量明确区分。
- 选择全量短目录或按需策略，依据实际目录开销、额外往返和任务效果；可调整配置，不写死工具数量上限，也不因 1M 窗口就忽略无关材料。

Agent Skills 官方集成文档推荐以名称和描述支持发现，正文按需加载；这是小目录的合理基线。对大目录再增加检索，是本项目的扩展建议。[Skill 集成](https://agentskills.io/client-implementation/adding-skills-support)

Anthropic 的工具搜索采用延迟加载，并保留经常使用的工具；官方也指出发现步骤会增加延迟。因此本项目借鉴分层策略，不直接照搬其 API 字段或内部评测收益到 OpenCode Go 双模型。[工具搜索与取舍](https://www.anthropic.com/engineering/advanced-tool-use)

## 5. 重点模块优化：记忆优先

用户明确将记忆等重要模块的优化纳入本阶段。建议围绕实际使用效果改进已有服务，不另建一套记忆运行时；下列为拟议工作项，具体接口和算法尚未定稿。

### 已有能力与待核实的质量问题

[记忆服务](../../src/my_agent/memory/service.py)、[存储](../../src/my_agent/memory/store.py) 和 [设置／条目](../../src/my_agent/memory/types.py) 已提供来源、作用域、修订、有效时间、替代关系、用户编辑／固定保护以及停用和遗忘。后台提取提示也已区分用户陈述、模型猜测与工具事实，不能再次把这些能力列成完全缺失。

当前自动召回以最后一条用户消息作为查询，结合词法匹配、结构信息与可选关系扩展；因此“继续”“按刚才的做”等短输入可能缺少任务线索，需用样本核实。自动带入按条数和字符预算选择，超长正文直接取片段；默认 `recall_limit=8`、`recall_chars=6000` 已可配置，不能仅因存在默认数值就认定为不可调整的硬编码。要评估的是召回命中、干扰、内容完整性和成本。

### 建议纳入的工作项

| 方向 | 拟议改进 | 可观察结果 |
| --- | --- | --- |
| 召回质量 | 联合当前问题、任务目标和近期有效主题构造简短查询；区分项目知识与跨项目偏好，减少近义重复及无关固定项挤占 | 简短接续、换一种说法仍能找到相关知识；无关项目知识不带入 |
| 记忆生命周期 | 复用已有按 ID 纠错、替代与失效机制，补齐实际漏处理场景；显示来源、适用条件和修订。用户纠正后下一请求采用新版本 | 已否定结论不反复出现；临时工具故障不沉淀成长期能力限制 |
| 与回退联动 | 区分当前有效对话与保留的旧分支；阻止后台维护把放弃分支当成新事实。对源自被回退代码／对话的自动记忆标记待重新核实，排除其未经确认的自动注入 | 回到旧消息后，不会被后续错误结论再次带偏；用户手写或其他来源支持的共享记忆不被整体删除 |
| 材料加载 | 优先带入完整、简短且独立可理解的条目；长正文用有语义的短说明和读取入口，避免机械截断条件。与摘要、任务事实和 Skill 去除重复，并统一解释 token 预算 | 实际请求中的记忆可读、相关；面板显示的内容与发送内容一致 |
| 用户与模型接口 | 复用记忆管理及实际材料面板，展示本次用了什么、为什么带入、来自哪里；提供修改、停用、遗忘、查看历史和按需读全文 | 用户能直接纠正错误，模型能找到相关条目并更新，而无需重复人工确认 |

回退后的处理按来源和受影响条目进行，不用整库扫描、全部记忆审批或重新提取阻塞前台。只恢复代码时同样需要检查依赖被恢复代码状态的自动结论；回到消息重新开始还需要让维护游标和有效分支一致。对于多来源条目，应保留仍成立的内容，不能仅因一个来源位于旧分支就永久删除。

语义检索／重排可以作为召回优化的候选：先用现有索引与轻量查询改进覆盖真实漏召回，再比较新增方案的收益、延迟、依赖与维护成本；不预先承诺向量库，也不把新依赖或额外模型请求变成正常对话前置条件。后台维护继续独立记录状态，失败不能把已成功的编码任务改成失败。

建议用少量定向样本判断改进：短句接续、同义提问、用户纠正旧结论、两个项目知识区分，以及回退后旧分支不再污染请求。核对实际请求材料、误召回和额外请求成本，不能只以保存条数增加说明效果更好。

记忆与下面的材料装配、回退、协作简报共同设计，复用同一份有效来源和请求材料记录。

## 6. 纳入 M6 的既有模块升级

用户明确允许此前发现的问题及提出的模块优化一起进入本阶段。以下收敛为阶段工作项，不再仅列作“以后考虑”；已有观察、尚未验证的风险和主动增强分别记录。具体问题调查未复现时保留证据缺口，继续独立工作，不为了关闭清单无限回归。

| 编号 | 工作项与范围 | 当前依据／证据状态 | 交付结果 |
| --- | --- | --- | --- |
| O1 | 执行、保存与故障接续：工作图保存、程序终态落盘、迟到响应与切页后的状态 | 已记录偶发保存失败；后续通过，根因未定位。不能直接认定现已修复 | 修复可复现问题；区分实际执行结果与保存结果。恢复已知记录时不重跑命令，保存失败保留草稿／输出和明确入口 |
| O2 | 双模型与流式状态：长响应来源、首字分段耗时、GLM／DeepSeek 切换后的原生续接字段 | 长场景未通过是已有事实；原生字段不兼容只是待核实风险，短闭环已通过 | 请求前装配、连接、思考、正文、工具参数与本地消费计时可辨；按真实协议处理模型切换，保留历史与已发请求归属 |

### 上下文与后台压缩的具体取舍

- O3 与第 4 节能力发现一起实施；相关材料减少必须同时观察实际输入量、回读次数、首字和任务完成情况。保留工具调用／结果配对、最新用户纠正和有效项目规范，不以减少字符数为唯一目标。
- 保留现有 **800K 自动压缩点**及可调绝对 token 参数，不重新加入固定保留百分比。稳定材料排序与缓存观察只能依照实际服务反馈，不能承诺固定命中率或缓存时长。
- O4 交付为可选模式，沿用原同步模式。固定完整交互切点后，后台处理旧前缀，新事实追加在尾部；仅在下一请求边界采用结果。
- 回退后来自旧有效分支的在途摘要不得覆盖新分支；停止、切换模型、重复整理及重启都使用已有作业身份和历史切点处理，不要求模型回传 hash。
- 输入接近实际容量时仍需等待压缩或返回明确容量问题。独立后台压缩失败保留原历史和可见错误，在容量允许时继续前台；主模型、实际执行和保存故障仍按既有规则停止。实施前将这一独立维护语义明确对齐现有规则，不默默吞掉错误。
- 摘要并发有真实请求和费用，计入现有计量；小样本通过不称为 800K 实测完成，未验证的规模保留说明。

### 工作方式复用的具体边界

沿用“模板蓝图 → 项目默认 → 任务快照”。模板保存逻辑角色、阶段、图关系与 Skill 引用；不包含旧会话／Run 身份、个人绝对路径、凭据或运行产物。项目默认只影响新任务；已有任务显式套用时保留原历史。

桌面提供任务中的“保存为工作方式”、工作流管理中的组合预览／编辑／导入导出，以及项目默认选择。套用模板不自动执行任务、不自动新建其他正式会话，不要求用户先组完整团队才能开始普通工作。缺少某项 Skill 时可定位来源和补充，其他能力继续使用。

现有工作图继续配合协调会话、Run／Goal、委派和等待执行。本轮优化导航、材料与复用；把工作图改成通用任务调度引擎是独立架构变化，暂不因“优化旧模块”自动纳入。

## 首批实施取舍

- 沙箱采用 Windows AppContainer，项目与所选运行环境按明确目录授权；同配置复用主体至应用退出。按 2026-10-20 用户纠正，命令、终端和预览均不提权；本地 HTTP 经同主体 TCP 转发进程和继承管道接入宿主随机端口，使用运行卡片返回的 URL，不改系统回环／防火墙规则。失败不回退到直接模式。本地 Git 与 Python 探测复用同一沙箱进程后端。浏览器为独立的隔离站点上下文，不宣称受项目进程沙箱覆盖；尚不兼容的本地 MCP／LSP 在能力发现时明确说明，未派发调用反馈给模型选择其他工具，实际启动／执行失败仍停止。实验边界见 [沙箱稳定性实验](sandbox-stability-experiments.md)。
- 沙箱修复以免提权、不阻塞开发为约束：不设置新的默认资源配额，不改变 direct／联网／项目可写取舍。环境继承补充凭据名称与含密码的连接配置识别，设置页允许按变量名显式传入项目所需配置；不保存变量值，不向项目程序传本应用模型密钥。普通开发环境仍采用继承后筛除，不使用全局允许列表。租约恢复按独立记录清理，坏记录保留并报告，不跳过其他可恢复租约。
- PowerShell 使用显式 provider 工作目录；祖先目录不继承的遍历／属性授权仅为兼容增强，系统拒绝该增强时记录未授予并继续真实启动，不要求能修改卷根 DACL。项目／运行时等实际目录授权仍必须成功。沙箱下 PowerShell 位置初始化遭权限拒绝时，命令与普通交互终端使用项目 PSDrive，`ProviderPath` 和原生 cwd 保持真实目录；`Get-Location.Path` 可能显示 `MyAgentProject:\`。祖先 ACL 使用不传播更新；授权先记录唯一主体，退出清理时只撤销实际存在的本租约 ACE，不为从未写入的授权再次写 DACL。
- 回退快照保存在应用数据根，不依赖 Git、不改暂存区；内容地址仅作内部去重。覆盖范围遵循文件发现和可调大小预算，依赖／忽略文件不默认纳入，预览显示遗漏。保存被忽略的文件／目录入口，不额外遍历其内容；起点未知的文件不能按“新建”生成删除恢复，Windows 大小写变动按路径身份比较。旧快照缺少覆盖字段时同样保留未知起点文件，不阻断其他可恢复文件。恢复逐文件执行、保留不重叠后续修改，并生成撤销恢复的起点；有重叠冲突时保留该文件。恢复对话保留原事件、排除旧分支，并按来源使自动记忆失效，不把后台候选更新校验用于用户的显式回退。
- 回退记忆采用来源失效区段：只写入当前会话受影响的序号范围，读取／召回时投影有效性，不在回退时扫描或改写整库正文。用户确认条目和有独立有效来源的知识保留；停止在途维护不隐式加载完整记忆管理页。来源不连续的混合文件写入显示未知，不把一次文件工具调用视为整个文件的作者证明。
- 组合工作方式保存流程、角色关系、工作定义和 Skill 引用。项目默认只影响未来任务，当前任务显式采用；复制时重映射成员身份，不携带运行结果和会话绑定，不自动创建成员会话。采用时按模板节点身份替换定义、重建当前分配，清除这些节点的旧完成投影和删除标记；其他工作与共同信息保留，旧事实继续留在版本历史。新团队中不存在的旧负责人显示待分配，不按同名角色猜身份。缺失可选 Skill 只报告资源问题。
- 群聊的“本次运行 / Trace”必须有真实 Run 身份；未接纳时显示等待，失败／旧记录无 Run 时显示无运行记录，仍可进入会话。不能把 null Run 悄悄当作整个会话的轨迹。
- 当前成员保留职责和直接依赖／反馈，远端工作提供索引；阶段只带当前正文及阶段短目录。完整内容仍经已有任务／工作读取入口获取。
