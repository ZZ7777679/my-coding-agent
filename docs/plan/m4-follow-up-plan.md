# M4 后续：可靠执行、工具可用性与实际使用收尾

> 日期：2026-09-30。状态：用户授权后的本轮定向实施与验证已完成，长任务响应和一次程序保存失败的剩余限制保留；实际结果见 [阶段进度](../progress/m4.md) 与 [差异审查](../progress/m4-follow-up-review.md)。下文保留设计依据，不将所有未测场景称为已验收。
> 依据：[M4 实施方案](m4-implementation-plan.md)、[M4 实际进度](../progress/m4.md)及本地保存的实验记录。
> 本轮是用户手动交接后的规划；不把另一会话的计划或未完成交接视为新的执行事实。

## 1. 本次判断

M4 的 Trace、Skill、MCP / 临时浏览器与任务工作流已经有首版和联合验收，随后也完成了左侧管理、在线 Skill 导入、精选预装资源、常用 MCP 和 OAuth 增量。接下来主要应把这些能力用于可靠的实际任务，而不是继续增加模块数量。

最优先的问题是 **模型请求长时间收到数据，却迟迟没有完成可执行的工具调用或回答**。参数纠错和资源使用体验则是范围较小、可以独立推进的工作。采用以下顺序，不设固定工期：

| 顺序 | 工作 | 用户能感受到的结果 |
| --- | --- | --- |
| 1 | 长响应定位与针对性处理 | 能看清当前等待什么，减少有证据可修的本地耗时或无效生成 |
| 2 | 工具参数说明与可修正反馈 | 参数用错时得到具体纠正信息，继续完成任务 |
| 3 | Skill、MCP、工作流实际使用收尾 | 从导入、启用到真实调用的关系明确，已有功能协同使用 |
| 4 | M4 差异审查与交付整理 | 当前实现、文档和验证证据一致，形成可提交版本 |

第 1 项需要先得到根因证据，不能承诺靠一项提示或开关一定解决。第 2 项已有实际错误证据，可在不依赖新网络实验的情况下先完成小范围修复。

## 2. 已有基线与证据限制

### 已完成，继续复用

- Trace 的失败请求归属、请求跨度，以及失败请求实际 usage / cache 的保存与展示已修复；当前公开协议为 **v6**。
- 实验已有轻量来源 manifest；不再引入第二套评测或日志框架。
- MCP 已在派发边界按发现到的 schema 返回具体参数错误；真实服务失败仍按原规则处理。不另加工具审批、信任开关或重复校验。
- SkillHub 原生下载、预览、项目导入和重启读取已有证据；skills.sh / GitHub 来源路径继续存在。
- 临时浏览器、模板快照、任务阶段及既有协作有开发验收；不能将这些已完成项重新列为待实现。

### 尚未证实的优化

9 月 30 日的 10 组 GLM 对照共 87 个新请求，仅一组 Run 正常完成；部分产物 oracle 通过不等于 Run 完成。实现阶段限定、减少工具菜单、简短提示、参数示例和批量编辑没有获得稳定效率收益，暂不改变产品默认策略。

这些样本中模型请求跨度累计约 3247.8 秒，工具执行跨度约 7.5 秒。它们是不同口径，不作严格耗时分账，但足以说明当前应优先定位模型请求链路。若干超时请求约 1 秒内收到响应头，接近 300 秒仍收到数据；这与 TLS 握手失败、连接完全没有响应的情形不同。持续数据究竟主要是思考、正文、工具参数还是其他流事件，以及本地消费是否拖慢，仍需进一步拆分，不能先归因给模型或网络。

核对原始 `tool.started` 后，4 次 `read_file` 错误均传入了未知字段 `limit`，并使用字符串值；当前正确字段是整数 `lines`。旧记录将其简称为“整数参数问题”不完整，本方案以原始调用为准。

主要证据位置（Git 忽略的本地产物）：

- `.artifacts/tests/optimization-ab/summary.json`：对照汇总。
- `.artifacts/tests/optimization-ab/<组名>/report.json`、`data/sessions/<会话>/events.jsonl`：配置、请求与真实工具调用。
- `.artifacts/tests/ticket-experiment-bb064a92e68a/`：原编码、重启接续与 oracle 记录。

本轮仅复核上述已有材料，没有新模型调用或性能测试。真实个人 OAuth 授权、800K 长输入性能及安装包验收仍不能称为已通过。

## 3. 第一批：长响应与失败接续

### 3.1 先缩小根因，再选修复

复用 `models/go.py`、`models/timing.py` 与现有请求 / Run 事实，按请求检查以下环节：

1. 请求发送、响应头、首个流事件、首段思考、首段正文与完整工具调用。
2. 流事件类别及其数量 / 数据量；收到工具参数片段与参数完整可执行分别记录。
3. 思考 / 正文展示回调、持久化与事件发送的耗时；检查逐片段等待是否产生明显背压。
4. 实际结束原因：输出截断、整次请求超时、传输中断、Run 预算或用户取消。

已有字段够用则直接读取，不重复造状态系统。缺少的计时先在定向诊断中补齐；确需长期展示的事实才进入现有事件与协议。诊断不保存另一份完整对话或 Trace。

根据证据选择最小改动：

| 发现 | 对应处理 |
| --- | --- |
| 本地回调 / 落盘明显拖慢流消费 | 在现有链路中合并必要更新，保持事件顺序、实时可见与终态保存 |
| 模型持续生成思考，长时间不发完整调用 | 核实 OpenCode Go 对该模型实际支持的思考 / 输出控制，再做单变量试验；不发送猜测参数 |
| 输出额度被耗尽 | 解释真实额度与结束原因；评估可调配置和分步产出，不能只无限增大超时 |
| 主要耗时确实在远端且无可用控制 | 明确限制与证据，让用户显式调整配置或下一请求模型；不宣称本地已解决远端延迟 |
| 没有持续内容，或传输中断 | 使用现有网络诊断和错误分类，仅修真实缺陷，不改用户 VPN / 系统代理 |

不把模型思考首字称为回答首字，不把网络到字节称为可执行工具已到达。服务端未返回的用量继续显示未知。

### 3.2 用更简单的任务验证

先使用一个空白隔离项目：创建单文件 Python 计数脚本 → 执行一次 → 用户追加一个很小的修改 → 沿原会话修改并执行。无需多格式 CSV、HTML 筛选和大量异常分支。

GLM 与 DeepSeek 使用各自正常配置和同一任务，作为两个独立样本；单变量候选与自身基线比较，不将模型间差异当成 Harness 优化收益。记录回答首字、首次实际写入、完整调用耗时、总完成时间、已知用量和失败原因。模型请求跨度与真正工具执行时间分别保留。

优先分析已有失败，不重复大批基准。重复样本仅用于确认新发现或候选收益；真实请求预算在实际实施时明确，实验配置不写成产品固定限制。一次成功不能认定稳定提速，一次失败也不能认定某种策略无效。

### 3.3 桌面可理解、可接续

检查现有桌面失败状态是否足以解释上述区别，缺什么补什么：

- 主对话保留简短失败事实；Trace 展示该请求实际接收情况、耗时和已有用量。
- 思考持续到达但调用未完成时显示真实状态，不笼统标为连接失败或工具正在执行。
- 失败保留已保存文件与历史，停止原 Run / Goal；用户沿原会话明确接续。沿用现有模型和预算入口，下一请求采用用户更改后的配置。
- 不自动重放结果未知的写入 / 命令，不增设接续审批或证明表；已有行为正确则不重写。

交付标准是根因或剩余限制清楚、对应修复有证据、用户能够理解并接续，不要求所有服务端延迟都由本地消除。

## 4. 第二批：工具接口与参数纠错

重点是帮助模型正确使用现有工具，不是增加检查层。

- `read_file` 的描述明确 `start_line` 与 `lines`，给一个紧凑正确例子，如 `{"path":"main.py","start_line":1,"lines":50}`。`list_files` / `search` 的 `limit` 不混入读取接口。
- 复用程序工具已有的字段错误表达方式，让只读 / 文件工具返回字段位置、具体错误与必要正确示例，代替只有“参数不符合 schema”的反馈。
- 未知字段要指出不支持；类型不符要指出预期类型。不静默丢弃字段、全局转换类型或扩大合法工具集合。
- 可修正的参数反馈继续交给模型选择下一调用，不中止 Run / Goal；真实执行、模型与保存故障保持既有停止规则。
- MCP 沿用刚完成的派发边界修复，只核实反馈能进入模型与 Trace，不再叠加校验。

用已保存的 4 次调用复现反馈，并检查一个正确的 `lines` 调用和一次模型修正后的接续。最低必要离线场景通过后即交付；只有离线无法回答的问题才追加真实模型调用。其他工具仅在发现同类缺陷时修改，避免全工具描述膨胀。

## 5. 第三批：把 Skill、MCP 与流程真正串起来

这批关注“如何使用”，不重复建设管理页面。

### 5.1 导入、项目启用与模型使用

在现有左侧资源管理中检查三个事实能否清楚区分：资源已导入、已对当前项目启用、当前请求实际加载 / 调用。缺失说明或状态就补齐，不把安装成功写成使用成功。

- Skill：选择一项适合小任务的现有专业 Skill，沿原站预览 → 项目导入 → 任务使用，确认来源、有效版本、附件路径、`load_skill` 与实际材料清单一致。
- MCP：先复用已有 Context7 做一次有用途的文档查询，观察发现 → 选中工具 → 调用 → Trace；浏览器沿用当前 Playwright 服务，无需安装新提供方。
- OAuth：本地授权链路已有验证。个人账号仅在用户选择对应服务与账号后实测；这不成为匿名查询或普通编码的门槛。
- Skill 内容可用与其方法是否有帮助分别评价；不以下载量、模型声称遵循或 Trace 中出现名字替代使用效果。

### 5.2 任务工作流与协作

继续用项目 → 任务 → 会话及模板快照；阶段是长期工作位置，Plan / Goal / 常规是会话工作方式。检查阶段切换、已有会话关联、结果来源与任务接续是否在桌面上清楚表达。

默认模板必须允许直接实现、跳过或返回阶段。Review 反馈不是自动修复授权，单个 Goal 完成也不自动结束任务。不增加产物存在、评分、强制报告或图完整性门槛。

此前已有完成 Run 的交接与重启不重发验证，不为“再验收一次”扩大协作实现。只有这个使用场景实际暴露的新缺口进入修复。

### 5.3 一个简短联合样本

在空白项目中使用项目 Skill 和默认流程直接实现单页计数器，启动服务，由临时浏览器点击一次并保存截图；用户主动使用已有角色的 Review 会话，授权一个小修改。最后在 Trace 查看 Skill、写文件、命令和浏览器调用。

这与原 M4 联合场景保持一致；复用已通过步骤，只重点补查本轮调整和在线导入资源真实使用的缺口，不全套无理由重跑。重启检查仅涉及本轮改变的持久化关系，浏览器站点状态仍不恢复。

以最近一次已上传 Git 版本至当前工作区的 **M4 差异** 为审查边界，优先看本轮修改与核心调用链，不无脑全仓重查。

1. 新定位的本地阻塞已修复；不能本地解决的服务端限制明确记录。
2. 参数错误能被理解并修正，正常任务不会因额外门槛被中止。
3. 新增使用调整在桌面可体验，Skill / MCP 使用记录与实际请求一致。

Git 提交 / 推送在用户要求后执行；当前大量未提交的 M4 修改保持原状。本方案不代替提交授权。
