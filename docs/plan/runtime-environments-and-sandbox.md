# Windows 项目运行环境与可选沙箱（设计讨论稿）

> 更新：2026-09-17。用户已确认默认方向与可折叠运行卡片；具体接口、原生沙箱实现与交付拆分仍待细化。本文记录设计，尚未扫描、导入、安装或执行本机项目环境。
>
> 本文细化 [初版设计稿](harness-initial-design.md) 5.5 节，并替代 [总规划](coding-agent-from-zero-plan.md) 原先“首个执行后端必须是 Linux 容器”的安排。实际实现仍以 [进度总览](../progress/README.md) 为准。

> 2026-09-18 实现补正：移除独立项目信任开关。用户选定项目后，常规执行默认使用本机工具；没有环境配置文件也可执行，不要求先打开设置、保存绑定或额外确认。特定解释器按需选择，执行方式在启动时取快照。下文早期讨论中的“可信项目”不代表还需登记信任状态；旧 `trusted` 字段仅兼容历史数据，不再控制执行。实际验证见 [M2 进度](../progress/m2.md#无环境配置项目被信任开关阻断2026-09-18完成)。

## 1. 已确认的方向

- 先在 Windows 下跑通，复用本地 / 项目已经配置好的环境；WSL 的直接执行入口后置。
- 在设置中统一登记和管理 Python、Conda、uv、Docker 等已有环境 / 工具，再供项目选择。用户已将此前的 CUDA 更正为 **Conda**，本轮不加入 CUDA / GPU 管理需求。
- 用户进一步明确：导入后为项目选一个默认环境即可，项目下任务和会话默认沿用；初版不要求再配置多套命名方案或会话级环境覆盖。
- 运行过程在会话中使用简单的可折叠运行卡片展示，收起看命令与状态，展开查看输出及运行详情。
- 用户已选择本机直接运行、沙箱按项目选用；落实为**选定项目后默认可执行，不再另设信任开关**。直接运行在界面明确显示未隔离，不把工作目录、虚拟环境或进程管理称为安全沙箱。
- 默认仍在原项目目录工作，不因运行、并发或启用权限设置自动复制项目、创建分支。
- 本轮讨论不授权实际命令执行、安装环境、修改系统设置或 Git 推送；也未选定所有沙箱技术或承诺其兼容性。

## 2. 设置中怎样统一管理

建议在现有设置中增加“执行环境”，包含环境列表、项目绑定和执行权限。三部分使用同一后端服务，但职责分开：环境说明使用什么工具和依赖，项目绑定说明当前项目选哪一套，执行权限说明进程能访问什么。

| 登记对象 | 记录与展示 | 运行时的用途 |
| --- | --- | --- |
| Python / venv | 解释器位置、环境根、实际版本、来源和检测状态 | 选定解释器执行项目代码；已有项目 `.venv` 可作为候选 |
| Conda | Conda 安装入口、环境名称与完整 prefix、环境中的 Python 信息 | 指定该 Conda 环境启动程序，保持其必要环境设置 |
| uv | uv 可执行入口、可管理的 Python / 项目环境、缓存与项目配置关系 | 管理或调用项目环境；uv 本身与某个 Python 环境分别登记 |
| Docker | CLI、选定 context / endpoint、引擎可达性和平台；后续关联镜像 / 项目配置 | 用户选择容器执行时使用；登记 CLI 不等于已能执行容器任务 |
| 其他项目工具 | 按实际需要补充 Node / npm 等工具入口 | 不把“Agent 自己用 Python”变成被开发项目只能用 Python |

这里的“导入”优先指登记已有环境的引用，不搬运整个环境、不自动安装依赖。导入 `environment.yml` 作为创建配方，与登记本机已经存在的 Conda 环境分开；前者会产生安装行为，不能在选择文件时直接执行。

建议操作为“发现已有环境”“手动添加”“检查可用性”“绑定到项目”“移除记录”。自动发现只查明确的工具入口和项目位置，不递归扫描整台机器。删除登记项不删除 Python、Conda 环境、Docker 镜像或用户代码；被项目引用时显示影响并提供重新绑定，不暗中换一个环境。

状态至少区分：路径已登记、工具可执行、环境可用、项目运行已验证，以及当前不可用 / 尚未检查。版本查询不代表依赖完整，导入成功也不代表某个任务运行成功。检查按需进行，不将完整诊断、联网或所有环境都可用设为应用启动条件。项目设置提供按需查看已保存环境实际 Python 路径与版本的入口，Agent 也可调用 `inspect_python` 获取同一事实；普通执行不以这项检查为前置条件。

### 2.1 项目怎样选择

**用户已确认简化为：设置中导入已有环境 → 项目设置选择默认环境 → 项目内任务与会话默认沿用。** 初版只需要一个清楚的默认环境选择器，显示名称、类型、位置与可用状态，保存后重启仍保留。项目内已有 `.venv` 可以作为导入候选，不要求用户每次对话重新选择。

此前提出的多层优先级、多个命名运行配置和会话级覆盖不进入初版必需范围。2026-09-18 根据 [DSH 对照](runtime-checks-dsh-review.md) 简化：可信项目未绑定时直接使用本机工具，无须先登记“系统环境”；需要特定解释器时再绑定。显式绑定失效仍说明原因，不悄悄改用别的解释器。普通工具变量继承现有配置并筛除凭据形名称及应用自身变量，不再用固定白名单截断环境。

更改项目默认环境或信任影响下一次接纳的启动；已经接纳的启动使用该次快照，不在准备记录保存后再次审批。正在运行的进程保持原环境，不自动重启；需要立即终止时使用停止入口。

切换沙箱设置也只影响后续启动的进程，不能将已有直接运行的程序瞬间变成受限进程。需要立即切换时，先停止并清理相关受管工作，再由用户明确接续；不因切换开关自动重跑命令或唤醒已经停止的 Goal。

本机绝对路径、环境身份与项目绑定保存到选定应用数据根，由 Python 单写者维护。项目内 `.venv` 等路径可相对项目根解析；共享到 Git 的配置只包含可移植的需求或相对路径，不提交个人安装位置和凭据。移动项目后重新解析相对绑定，跨机器缺少环境时重新匹配，不复制旧机器的路径假装可用。

项目声明可以推荐环境与运行命令，不能自行扩大文件 / 网络权限。注册工具、应用配置、运行授权仍来自受信入口；不会因为仓库文件写了某个 `conda` 路径就直接执行它。

### 2.2 Python、Conda 与 uv 的调用方式

- Python / venv：优先使用选定解释器的实际路径，不依赖当前终端恰好激活了什么，也不通过修改系统 PATH 切换环境。应用自身的 CPython 3.13 + uv 基线与目标项目环境分开；用户项目可以使用自己的 Conda 和其他实际兼容版本。
- Conda：官方提供 `conda env list --json` 列举环境，以及 `conda run` 在指定环境执行程序。建议保存 Conda 安装身份与环境 prefix，避免同名环境混淆；参数、工作目录和实时输出支持按实际版本核对。Conda 的启动包装与必要激活行为属于受控执行过程，不在只读发现时逐个激活环境。[环境列表](https://docs.conda.io/projects/conda/en/stable/commands/env/list.html)、[运行命令参数](https://docs.conda.io/projects/conda/en/26.3.x/commands/run.html)
- uv：`uv run` 默认会维护项目环境；单纯检查或使用已有环境时，要明确是否允许同步、下载或修改锁文件。可选择直接调用已有解释器，或按实际命令使用 uv 的 `--no-sync` 等机制；安装 / 同步是明确动作，不能藏在“导入 / 检查”后面。[uv 运行命令](https://docs.astral.sh/uv/concepts/projects/run/)、[锁定与同步](https://docs.astral.sh/uv/concepts/projects/sync/)
- 包管理命令：区分运行代码和修改依赖。当前目标已包含必要安装时按既有授权推进；对共享环境的安装与使用按资源协调，不改其他项目使用的环境来消除当前报错。

不保留跨任务共用的“已激活 shell”作为环境事实来源，避免任务 A 的 Conda / PATH 状态污染任务 B。环境变量按本次配置构建，业务所需秘密经明确的项目凭据引用提供；不把应用模型密钥、整个宿主环境或 Conda 中保存的秘密批量导出到 UI / 日志。

### 2.3 Docker 与 WSL 的范围

Docker 可进入统一管理列表，但默认 Windows 本机运行不依赖 Docker 启动。没有 Docker 只影响选择容器的项目；Docker 已安装但引擎未运行，与未安装分别展示。导入和检查不自动启动引擎、拉镜像、开启 Windows 功能或修改网络。

Windows 下 Docker Desktop 有不同后端；本应用后置的是直接选择 WSL 分发运行项目的能力，不因这个决定修改用户已有 Docker 的底层配置。所选 Docker context 的实际 endpoint、平台与本地 / 远程属性应明确展示，不能因为外观是本机 CLI 就假定代码一定运行在本机。[Docker Windows 安装与后端说明](https://docs.docker.com/desktop/setup/install/windows-install/)

Linux 容器中的环境与宿主 Windows Conda / venv 不是一份可直接互换的环境。选择容器时另外确定镜像、依赖和目录映射；不会把已经导入的 Windows 环境标为“自动导入容器成功”。

## 3. 沙箱怎样安排

### 3.1 默认本机直接运行

用户已经选择这一默认方式用于可信项目。程序使用当前 Windows 账户的执行上下文，应用负责参数构造、工作目录、必要环境、日志、超时、取消、来源记录和进程清理；界面显示“本机运行 · 未隔离”。

内置文件工具仍遵守项目范围和基线检查，普通已授权动作不逐项确认。但任意 Python、Conda、shell 或项目程序通常具有当前账户的文件与网络访问能力；工具层的路径校验、清理环境变量或选择 cwd 不能让任意子进程自动获得同样的访问限制。不能在直接模式承诺“进程只能访问当前项目”或“操作系统阻止读取应用数据”。

建议使用 Windows Job Objects 管理所属进程组与资源，结合实时输出、句柄回收和停止入口。Job Objects 提供进程组控制，进程安全权限还需另外设置；它不是文件 / 网络沙箱。子进程脱离、外部服务和取消范围需要在实施时按所支持方式验证，不把停止一个 shell 记成完整清理。[Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

### 3.2 可选的 Windows 原生沙箱

建议优先验证基于 AppContainer 的受限进程后端：由受信启动组件建立受限身份，配置必要资源访问，再启动项目命令。Microsoft 文档说明未打包的 Win32 应用也可使用 AppContainer；文件、注册表、进程与网络权限分别受其机制影响。这是实现候选，尚未在本项目验证 Conda / uv 的兼容性。[AppContainer 与传统应用](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-for-legacy-applications-)、[隔离能力](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)

面向用户建议表现为项目级“本机沙箱”配置：

| 设置 | 建议行为 |
| --- | --- |
| 项目文件 | 根据当前工作允许读取或读写原目录中的已授权资源；保留敏感路径处理和并发基线，不自动复制整个项目 |
| 环境与工具 | 对运行所需解释器、依赖和原生库授予必要读取 / 执行访问；环境写入按安装 / 同步需求另外表达 |
| 临时文件与缓存 | 使用专属运行目录与明确选择的缓存范围，不因此开放整个应用数据根或个人目录 |
| 网络与本地服务 | 按实际后端能力提供关闭 / 开放及本地服务选项；细粒度域名限制需要额外实现，不能靠 AppContainer 名称宣称已经具备 |
| 额外路径 | 例如项目需要的外部数据目录，可按项目登记读 / 写范围；必要时通过 HITL 调整，已授权范围不反复询问 |
| 生效状态 | 展示实际生效的后端和权限；初始化失败或不兼容时停止该执行，不静默退回直接运行 |

上述是待验证目标，不是 AppContainer 天然只允许表中路径的保证。需要核对默认资源可见性、路径 / 链接、继承权限、网络能力、Conda 启动及其 DLL / 子进程依赖；修改访问控制时仅管理自身所需授权，不授予整个磁盘，不覆盖用户和其他任务已有 ACL。权限设置与清理需可追踪，不能把关闭 UI 开关等同于权限已回收。

原生沙箱与 Job Objects 可一起工作：前者限制访问，后者管理生命周期。具体 Win32 调用、是否需要独立启动组件及打包方式留待小范围可行性验证；当前不提前引入新框架或给主应用管理员权限。

### 3.3 Windows Sandbox 与 Docker 沙箱

Windows 自带的 **Windows Sandbox** 是另一种方案：它提供单独的临时 Windows 环境，可以配置映射目录和网络。基于这种使用方式判断，它需要额外准备运行依赖，不适合直接等同于“在现有 Conda 环境上勾选权限限制”。建议保留为后续隔离实验方案，当前不作为默认开发入口。[Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)、[配置说明](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

Docker 在用户选择容器环境时，可通过挂载、用户、能力和网络等配置形成对应边界；不能把“使用了 Docker”自动当作隔离充分。仍需核对实际授权资源，不将 Docker socket、宿主凭据目录或特权能力默认暴露给项目。容器与原生沙箱不是任意叠加的选项，UI 只展示该执行后端实际支持的策略。

## 4. 实际使用过程建议

1. 在“设置 → 执行环境”发现或手动添加已有 Conda / venv、uv 等；只登记引用，必要时运行轻量检查。
2. 在项目设置中选定环境。可信项目默认显示本机直接运行；无需为了普通任务先安装容器或创建副本。
3. 用户提出代码任务后，按本次明确的目标执行；工具卡片显示环境、目录、命令、输出和进程状态。
4. 用户希望限制某项目的访问时，选择可用的沙箱配置，查看并调整项目 / 环境 / 额外路径及网络范围；没有实现的后端显示未提供，不能使用假开关。
5. 已配置范围内继续工作；超出范围且确实需要用户决定时使用 HITL。实际执行故障按既有规则停止运行和 Goal；修好配置或关闭沙箱不自动重放未知副作用，等待明确接续。
6. 运行结束保存结果和使用的环境。脚本执行与持续服务的区别、输出 / 停止入口及接续建议见 4.1 节；不以“命令已启动”宣布开发目标完成。

初版优先完成本机环境登记、项目绑定和真实运行 / 输出 / 停止，再按项目选择补充沙箱能力。沙箱可行性验证与日常本机路径分开推进；不支持沙箱只影响需要沙箱的执行，不能让已选择的本机直接模式因缺少 Docker / WSL 而不可用。

### 4.1 程序启动后怎样管理（场景说明与建议）

这里指 Agent 替用户启动的项目程序，例如一个 Python 脚本或网页预览服务。应用需要知道它还在运行还是已经结束，持续显示输出，并能在用户要求时停止对应程序；用户不需要为此理解操作系统进程术语。

| 用户请求示例 | 建议的产品行为 |
| --- | --- |
| “运行这个数据处理脚本” | 使用项目默认环境启动，逐步显示输出；结束后保存结果、退出状态与生成文件入口 |
| “执行已有测试，告诉我结果” | 显示实际输出和检查结果；测试正常执行但未通过仍按既有规则先报告，没有相应修复授权不改代码 |
| “把网页启动起来给我看看” | 启动预览服务，显示运行状态；取得实际就绪依据和地址后再提供打开入口，保留服务供用户访问，不一直等它退出才回答 |
| “停掉刚才那个服务”或点击运行卡上的停止 | 只停止该条记录对应、由应用管理的程序及相关子进程；不按进程名称 / 端口批量结束用户自己启动的程序 |

**用户已确认采用简单的可折叠运行卡片。** 每条命令对应会话中的一张卡片，初版展示约定如下：

- 收起时显示命令摘要与实际状态；运行中的卡片保留“停止”入口。
- 展开时显示完整命令、所用环境、工作目录和实时输出；结束后显示实际结果。服务有已确认的访问地址时再提供打开入口。
- 折叠只改变显示，不停止程序或丢弃输出；再次展开接续查看。同一条记录持续更新，运行状态与任务是否完成分别表达。

具体布局按上述简单交互细化。项目内找回活动程序的轻量入口仍为建议；卡片不需要额外的复杂进程管理页面，也不加入环境导入表单。

下列生命周期方向随后在 4.2 节由用户确认：已交付服务在应用内保留、退出时停止、重启不自动拉起。具体清理契约与退出界面按以下建议继续细化：

- 普通脚本结束后保存输出即可，不自动重启；实际启动 / 执行故障仍停止当前运行及 Goal，清理归属于失败工作的资源。
- 用户要求启动供其查看的服务时，回复结束或切换会话后继续保留，并保持可见的停止入口；“正在运行”“已就绪”与任务完成分别表达。未能确认就绪时如实显示，不假定出现进程就代表网页可用。
- 停止某个命令、停止当前 Agent / Goal 和退出应用各自作用于明确范围。当前工作尚未交付的临时进程随取消清理；已交付供用户使用的服务保持自己的记录，不被另一会话的停止按钮误杀。完整归属细节在执行契约中收敛。
- 应用退出沿原有“停止任务并退出 / 返回应用”的规则处理活动工作，不新增隐形后台守护；重启可查看历史，但不自动重启旧程序。用户自己启动的程序不归应用退出清理。
- 长期服务不套用一次性脚本必须尽快退出的判断；等待、日志读取和停止不阻塞桌面交互，也不因轮询状态额外调用模型。共享端口 / 环境的冲突按已有资源规则处理，不自动结束外部服务来腾位置。

这些是产品行为走读，未启动程序或执行验证；并不新增所有项目必跑测试、固定服务寿命或后台保活要求。

### 4.2 停止 Goal 与退出应用时程序怎样处理（默认保留方式已确认）

用户接受子 agent 判定方向后，继续下一项产品讨论，并明确选择“应用内保留，退出时停止”：切换会话或停止 Goal 时，已交付使用的网页 / API 服务继续运行；真正退出应用时停止，重启不自动拉起。本节记录该默认决定，具体管理入口、退出文案与清理契约继续细化，尚未实施。

以“帮我修改页面，并启动给我看”为例：修改完成、预览实际就绪后，Agent 可以交付地址并结束当前回复，用户仍能访问页面。程序记录保留来源项目、任务、会话和启动请求，但供用户使用的服务，其生命周期可以超过单次 Agent 运行；Goal 完成与服务退出分别表达。

建议按请求目的区分临时执行与持续使用：跑一次脚本、构建或检查通常属于当前工作的临时执行；用户要求启动供其查看 / 调用的网页或 API，在取得实际就绪依据并展示运行入口后，记录为保留使用的服务。Agent 为自己验证而临时启动的服务，不因出现端口或就绪日志就自动变成长期保留；需要另行决定时才询问，明确请求不重复确认。

| 用户动作 / 状态 | 当前决定与实现建议 |
| --- | --- |
| 回复结束、折叠卡片或切换项目 / 会话 | 已交付使用的服务继续运行，卡片保持真实状态；离开页面不等于停止 |
| 停止当前 Agent / Goal | 停止后续动作，清理所属在途临时命令与子工作；已经交付使用的服务保留独立停止入口 |
| 点击某张运行卡的“停止” | 只停止该记录实际管理的程序及所属子进程，显示结果；不批量停止同名进程或其他会话服务 |
| 正常退出应用 | 已确认退出时停止本应用管理的程序，保存记录；建议有活动工作或托管服务时列出影响，提供“停止并退出 / 返回应用” |
| 再次启动应用 | 恢复历史与上次退出 / 中断状态，不自动重新执行旧命令或拉起服务；异常退出留下的未知状态先核对，不能仅凭历史记录显示正在运行或已停止 |

项目中建议提供一个轻量“运行中”入口，汇总其活动卡片并可回到来源会话，避免切走后找不到停止按钮；沿用原可折叠卡片，不新建复杂管理页面。输出与进程状态由执行后端管理，状态刷新本身不额外调用模型；项目服务自身的模型调用仍按其实际行为计费，不能由本条推导为免费运行。具体工具契约与可靠清理方式在实施时验证。

上述保留只针对已正常交付的服务，实际调用 / 执行故障仍按既有规则停止对应运行和 Goal，清理尚未交付的临时工作；已完成 Goal 不因服务后来退出而自动复活或重新修复。服务自身异常退出如实展示并报告影响，不能自动重启。退出清理不接管用户在应用之外启动的程序。

**本轮确认结果**：采用应用内保留、退出时停止的默认方式；停止 Goal 即停止已交付服务，以及退出后继续后台托管，均不作为初版默认。停止服务仍有明确入口，初版不增加后台守护。用户选择已记录，无需再次询问相同默认行为；可靠清理与异常退出核对需要在实施时落实。
