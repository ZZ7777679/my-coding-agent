# M3 独立设计审查

> 日期：2026-09-18。范围：M3 总体、压缩、记忆、协作及技术吸收五份方案，结合相关 M2 代码静态核对。
>
> 初次结论：三个模块的职责划分可以保留；发现 **4 项 P1、5 项 P2**。不能据此前“文档检查通过”认为功能链路已经完整。下文保留原审查证据，代码行号为当时位置。
>
> 后续状态：同日 [M2 上传前检查](m2-release-review.md) 已修复 R2、R5，并修复 R1 的等待中插话问题；R1 的持久等待 / 时间计量仍待设计。余下 **3 项 P1、4 项 P2** 继续按 M3 修订，详见文末跟进。

## 1. 审查口径

优先检查用户能否连续完成工作，再看结构和技术名称。判断依据依次为用户已确认的产品行为、[项目规则](../../AGENTS.md)、五份 M3 方案和实际接入代码。没有要求每个内部函数提前设计完，但跨模块状态、数据来源和执行预算不能只靠实现时猜测。

- **P1**：影响本阶段主要使用流程，应在实现相关能力前确定处理方式。
- **P2**：特定场景的缺口或不必要耦合，随对应模块修正，不阻塞无关工作。
- “现有行为”来自可定位的代码分支；“设计缺口”表示文档未形成可实施的完整约定，不表示尚未开发的 M3 已经实测失败。
- 本次没有修改业务代码、重跑原用户会话或执行产品回归；没有重新验证全部第三方资料或宣称第三方算法效果。本次关注本地方案能否落地。

## 3. 逐项发现与最小修正

### R1 · P1：明确协作等待怎样让出和接续执行

**位置：** [协作计划](m3-collaboration-plan.md) 第 88–106 行；[协作结果等待](../../src/my_agent/collaboration/service.py) 第 475–503 行；[运行计时](../../src/my_agent/sessions/service.py) 第 638–685 行；[Goal 等待投影](../../src/my_agent/goals/state.py) 第 168–171 行。

方案要求“等待不轮询、结果接续、插话先答再继续”，但没有落到已有运行状态上：现在 `read_collaboration(wait=true)` 会一直挂在工具调用中；Goal 插话只设置 `yield_requested`，运行循环要等这个工具返回后才检查。`remaining_seconds()` 使用从 Run 开始累计的时间，现有 `outcome=wait` 又专指需要问题的 HITL。

**触发场景：** A 等 B 编写说明，用户在 A 问一句当前设计原因。照搬已有等待工具时，A 不会及时让出；B 较慢还可能先耗尽 A 的 Run 时间。若直接复用 `report_work(outcome=wait)`，又会被解释成等待用户，而不是等待 B。

**最小修正：** 协作等待成为可持久化的明确等待原因，关联原工作目标和请求 ID；登记等待后让出执行槽，结果到达或用户插话通过现有调度恢复。它不等同于工具失败、Goal 完成或 HITL。接续保留累计请求 / 工具预算，写清被动等待和并行 worker 的时间如何计量，不能靠新建 Run 重置额度，也不能在父子视图中无意重复计算并发时间。无需引入通用工作流引擎。

**必要验证点：** 在受控的未返回协作请求下插话，能够回答；结果随后只接续一次，取消后不接续。用可控事件即可，不需要真的等到超时。

### R2 · P1：删除“请求形成环就禁止”的旧约束

**位置：** [协作计划](m3-collaboration-plan.md) 第 90、106 行；[请求接纳](../../src/my_agent/collaboration/service.py) 第 180–207 行；[工具错误分类](../../src/my_agent/runtime/loop.py) 第 166–198 行。

新方案允许发出请求后继续独立工作，只对实际互相等待作反馈。现有代码却拒绝任何发回委派祖先的工作请求，并把所有 `preparing / queued / running` 请求都当成等待边；它没有区分“请你做事”与“我现在必须等你”。`COLLABORATION_CYCLE` 也不在可修正反馈中，因此拒绝还会升级为运行失败。

**触发场景：** A 请 B 写说明，自己继续另一个独立步骤；B 在已安排角色范围内请 A 补充一个接口解释。A 没有等待 B，仍会因往返关系被拒绝。此处检查的是图的形状，不能据此判定实际死锁。

**最小修正：** 取消按委派祖先或全部在途请求推断死锁的前置拒绝。只有准备进入等待时，检查正在生效的等待关系；形成实际互锁就返回可调整的反馈，保留已接受工作，让模型改变顺序或提供材料。保持用户既有角色范围与同会话顺序执行即可，不新增全图审核。

**必要验证点：** A 发出请求但不等，B 可以回问；A、B 真正互等时后一个等待返回原因，整个 Goal 不因这次未执行的等待请求被判失败。

### R3 · P1：补齐“历史已经太大”的压缩入口

**位置：** [压缩计划](m3-context-compaction-plan.md) 第 76、94–100、114、129 行；[旧上下文方案](context-management-plan.md) 第 102–130 行；[当前请求字节检查](../../src/my_agent/runtime/loop.py) 第 73–77 行。

方案定义了提前触发和压缩后的目标，但没有明确**摘要请求自身**的输入构造和超窗处理。保留旧 checkpoint、待折叠事件、系统 / 工具前缀再附总结要求，不保证这份请求能够装进当前模型。80% 提前准备只帮助持续在线积累的新历史，无法覆盖第一次整理一个已经很长的 M2 会话、用户调小容量或新尾部突然增长的情况。

**触发场景：** 老会话第一次使用 M3，发送窗口已经超过本地预算；或者历史是在较大输入容量下形成的。直接把超长前缀发送给同一个模型总结，仍可能触发原字节检查或服务容量拒绝；“自动整理”不能解决自己的输入过大问题。

**最小修正：** 先为摘要调用计算实际可用输入，包含提示、工具定义及输出预留；先外部化可归档观察，再选可容纳的完整历史片段，必要时分段增量推进到目标切点。每次真实调用照常计量，不能无限重试；最新输入不丢弃。如果确实是一个不可缩减的必要输入过大，指出该材料，而不是把所有长会话都拒绝。主请求预算检查应消费已组装的窗口，不在整理前先否决原始全量历史。

**必要验证点：** 用超过配置容量的旧历史样本，检查实际摘要请求和下一主请求均能容纳、工具配对与尾部仍完整。无需通过长时间付费聊天构造。

### R4 · P1：把会话中的明确决定送进任务工作记忆

**位置：** [记忆计划](m3-memory-plan.md) 第 23–41 行；[协作计划](m3-collaboration-plan.md) 第 118–122 行；[任务字段](../../src/my_agent/tasks/types.py) 第 15–28 行；[报告同步](../../src/my_agent/tasks/store.py) 第 186–239 行。

方案反复要求使用“最新任务状态”和“用户确认约束”，但目前 `TaskFields` 由用户在任务界面维护；报告只更新 `TaskWork`，不能覆盖目标、约束与决定。新增“各成员最新报告”能够保留进展，却不能自动建立从用户聊天决定到共享任务事实的通路。自动记忆也明确把任务临时约束排除在长期记忆之外。

**触发场景：** 用户在 A 中确认“本任务改为只用标准库”，没有额外进入任务面板填写。B 随后收到安排或新建会话，只刷新原任务字段及最近报告，不能保证获得这条已确认决定。仅写“新要求优先”没有解决新要求如何到达 B。

**最小修正：** 增加简洁的任务更新动作，或扩展既有报告的可选更新项，将明确的共享决定连同原消息来源加入任务工作概览。用户明确决定直接记录；模型建议保持建议身份；不默默覆盖用户手写字段，不要求每轮填报告或再次批准同一句话。临时会话意图和任务级决定需要区分，但不另起分类模型或逐条审查器。

**必要验证点：** 在 A 聊天中作出任务级纠正，B 下一次请求可见；该决定不被错误推广为所有项目的永久偏好。

### R5 · P2：长结果应分页或外部化，不应使读取变成致命故障

**位置：** [协作读取工具](../../src/my_agent/collaboration/tools.py) 第 200–245 行；[默认容量](../../src/my_agent/defaults.json) 第 38–40 行；[错误分类](../../src/my_agent/runtime/loop.py) 第 178–198 行；[压缩计划](m3-context-compaction-plan.md) 第 24、146 行。

当前历史页仅在多于一条时缩页。单条大消息或 `read_collaboration` 的完整结果超过 `max_tool_bytes` 后返回 `TOOL_OUTPUT_LIMIT`，运行循环将其当作不可恢复故障。默认模型响应容量大于工具返回容量，所以一个成功生成的回答也可能无法作为协作结果读回。

**影响：** 模型和程序没有出错，只读展示太长却导致任务停止。新方案提到通用归档，但没有明确把这两个已有的前置拒绝点列入改造；若只在它们之后归档，拿到的已经是错误而非原结果。

**最小修正：** 在结果生产 / 读取边界返回状态、短内容和可继续读取的引用 / 偏移；单条记录也能分段，完整正文仍持久保存。用户输出预算继续限制单次装载量，无需取消预算；读取范围过大或局部材料不可读交回模型调整，不上升为整个任务执行失败。复用归档接口，不为每种工具再建一套大小审查。

**必要验证点：** 读取一个合法但超过单次工具预算的协作结果，能获得首段及后续入口，Run 不因此失败。

### R6 · P2：取消记忆变更对整份 checkpoint 的自动重建依赖

**位置：** [压缩计划](m3-context-compaction-plan.md) 第 150 行；[记忆计划](m3-memory-plan.md) 第 182–190 行。

方案让 checkpoint 记录曾使用的记忆，并在纠正 / 遗忘后“必要时”从原始事件重建，但没有定义如何知道摘要吸收了哪个条目的哪句话，以及何时必须重建。仅有 memory ID 无法确定它是否已被回答转述，原聊天又可能本来就包含同一事实。

**影响：** 一个普通笔记变更可能触发扫描或重做长会话摘要，扩大调用、等待和失败范围；从保留的原聊天重建也不能保证不再包含同一事实。这与“忘记记忆不等于删除聊天”的正确范围说明不一致，容易在实现时演变成新的语义审查和有效性门槛。

**最小修正建议：** 遗忘直接作用于记忆正文、索引、派生关系 / 知识页和请求注入缓存；纠正从下一请求明确使用最新事实。摘要不以记忆引用失效为由整体停用或要求先重建，不把“所有历史都不再提到这件事”作为普通遗忘的承诺。保留聊天语义仍受最新明确要求约束；用户主动要求重整摘要时再走普通整理流程。此建议需要同步修订方案，不能只在实现中悄悄降低现有文字承诺。

**必要验证点：** 改正 / 删除条目后，下一请求没有继续注入旧记忆及自动派生页，且没有因此额外强制发起一次全历史摘要。

### R7 · P2：给默认自动贡献确定首次处理起点

**位置：** [记忆计划](m3-memory-plan.md) 第 103–111、184、196–208、214 行；[总体兼容说明](m3-implementation-plan.md) 第 129–131 行。

方案默认贡献项目记忆，只处理“尚未处理的区间”。但老会话没有提取游标，首次启用时所有旧事件都可以被解释为尚未处理；文档没有区分从启用点开始积累与回填全部历史。单次整理额度只能限制某一次作业，不能说明这些历史是否应该进入默认队列。

**影响：** 升级后的一次普通工作可能带出大量后台提取；关闭后重新开启也可能补跑用户原以为不会参与记忆的区间。它不一定阻塞前台，但会产生难以理解的额外调用。

**最小修正：** 默认从首次启用后的新工作开始，记录启用边界；暂停贡献期间的记录不自动补跑。用户需要整理旧历史时通过现有手动入口选择范围。任务当前状态照常直接读取，不需要靠收费回填才能让旧任务继续使用。避免引入固定天数、条数或每次启动全库扫描。

**必要验证点：** 有大量旧记录的项目第一次启用记忆，不默认排出整库提取任务；显式选择旧区间仍可整理。

### R8 · P2：解除协作与记忆实验之间的顺序绑定

**位置：** [总体实施顺序](m3-implementation-plan.md) 第 145–157 行；[协作计划开头](m3-collaboration-plan.md) 第 3 行；[技术吸收范围](m3-technology-adoption.md) 第 138 行。

总体按 A → B → C → D 推进，C 必须交付关联记忆和知识页两个实验，D 又写成复用 A–C 后进入。协作结果送达、等待接续和 worker 并不依赖模型生成的关联图或知识页，这属于交付顺序中的不必要耦合。

**影响：** 同时打磨多个实验的数据结构、遗忘传播和界面，会让三个核心模块迟迟不能联通。默认关闭并不能消除它们在开发顺序上的成本。

**最小修正：** A 的材料 / 当前事实基础完成后，先形成压缩、最小可维护记忆和协作闭环；关联 / 自动知识页在 M3 内随后交付，保留实际可用入口及小范围对照。仍然实现用户要求的三个模块和已列实验，不把可选实验做成协作基础能力的前置条件。经验手册继续只是普通条目的视图，不新增独立引擎。

### R9 · P2：项目移动后的记忆恢复需要重关联入口

**位置：** [记忆存储计划](m3-memory-plan.md) 第 83 行；[项目重新选择](../../src/my_agent/projects.py) 第 156–195 行，特别是第 179–185 行。

方案写明“项目移动后沿项目登记身份恢复”。当前 `open(path=...)` 仅在目录 identity 相同且**旧登记路径仍然可用**时复用项目；原目录移动后，旧路径不可用，即使同盘移动保留文件系统身份，也不能通过这个条件。重新选择可能生成新 project ID；跨盘复制更不能依赖原目录身份。

**影响：** 记忆虽然按 ID 存储，用户重新选目录时却关联不上旧 ID，连同任务 / 会话一起表现为另一项目。把记忆路径改成 ID 本身不足以兑现迁移承诺。

**最小修正：** 给失效项目提供“重新定位目录”，由用户对已有 project ID 选择新根，保留原数据关系；不自动按名称或相似代码合并项目。如果本阶段不提供此入口，就收窄文档为“数据按项目身份保存，移动后尚需明确重关联”，不能写成现成功能。另将第 87 行含糊的“项目目录下 views”明确为应用数据根内的项目记忆子目录，避免被理解为写入用户代码目录。

**必要验证点：** 对隔离样本移动目录并重新定位，原 project ID、任务与记忆仍关联；不用复制真实项目或移动应用数据根。

## 4. 硬编码与过度校验专项判断

| 项目 | 审查判断 | 处理方向 |
| --- | --- | --- |
| 80% / 55% / 20% 整理比例 | 目前是集中、可调的工程起始值，未被写成合法输入唯一条件 | 保持建议性质；解决 R3，不能以这几个比例替代摘要输入容量处理 |
| 默认 2 个 worker | 可调并发量，超出排队 | 可以保留；不是超过两项就拒绝整个任务 |
| Go 地址、双模型、E 盘根 | 用户明确的产品选择，目录可覆盖 | 不作为本轮无意义硬编码删除 |
| 全部在途请求不得形成环 | 比真实互相等待更严格，已存在误拒绝路径 | 按 R2 删除这个前置约束 |
| 长读取超过单次预算就停止 | 把可分页的数据问题升级成执行失败 | 按 R5 改为分段 / 回读，不另增一层审批 |
| 遗忘后判断整份摘要是否可信 | 缺少可靠局部依据，容易长成跨模块反复审查 | 按 R6 缩小操作范围，取消自动重建依赖 |

## 5. 推荐的简单结构与交付顺序

保留现有三类服务，不因引入研究机制而增加一套运行核心：

| 职责 | 最小边界 |
| --- | --- |
| 请求组装 / 压缩 | 从事实、checkpoint、近期交互及引用组装可发送窗口；不管理任务真相、不判断记忆语义是否正确 |
| 任务工作信息 | 保存用户字段、明确共享决定、各成员最近进展；给所有会话提供当前事实 |
| 记忆 | 本地条目与检索，后台增量更新；经验 / 时间关系是字段或视图，知识页是派生材料 |
| 协作 | 既有角色、请求 / 消息、明确等待和结果接续；worker 复用现有 Session / Run |
| 模型调用与预算 | 复用同一 Go 客户端和计量路径，目的和所属工作明确；不复制多套网络 / 审批逻辑 |

L0 / L1 / L2 可以先只是一个轻量材料描述中的短说明、可选概览及原文引用，不需要单独的注册框架、内容路由 DSL 或三个存储引擎。

建议顺序：

1. 共同输入：明确共享决定的写入、成员进展、归档和有界回读。
2. 压缩闭环与基础记忆：可容纳的摘要输入、保存 / 恢复、显式记住、检索 / 修订 / 忘记。
3. 协作闭环：等待 / 插话 / 结果接续；删除过宽的循环限制，再接可选 worker 与两种上下文方式。
4. 同一 M3 内加入自动记忆维护、轻量关联和知识页实验，观察额外调用与实际帮助。
5. 用一个空白计数器项目串起流程，必要的竞态 / 容量问题用少量可控事件覆盖。

这是一组修订建议，不在本次审查中擅自改写原方案或启动功能实现。尤其不需要先做完整知识图谱、自动评审系统或新的安全策略引擎才能推进。
